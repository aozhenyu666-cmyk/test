# 回路：设计说明

这份文档回答三个问题：这个项目最合理的形态是什么，第一阶段要验证什么，以及当前实现里每个关键取舍的理由。

---

## 1. 结论

**形态**：一个原生 Android App。它的核心是一个确定性的闭环引擎，负责“行动 → 观察 → 偏差 → 干预 → 更新”；大模型只是其中一个可选的判断层。它不是聊天机器人，也不是待办清单。

```
             声明行动（做什么 / 为什么 / 多久 / 怎么验证 / 是否允许强干预）
                                   │
                                   ▼
 ┌────────────────────────────── core（纯 Kotlin，无 Android 依赖）──────────────────────────────┐
 │  事件日志（只追加）──重放──▶ Situation（当前局面 = 工作记忆）                                │
 │        ▲                         │                                                         │
 │        │ 每个判断都是一条事件      ▼                                                         │
 │  Engine.tick / answer ──▶ Assessor：预期 vs 观察 → Deviation（偏差，一等数据）               │
 │                          Policy：何时再看、问什么、用多大力度（每个决定都写明理由）            │
 │                          LlmJudge：只把用户写的一句话理解成选项之一（可选）                   │
 └──────────────┬───────────────────────────────────────────────▲────────────────────────────┘
                │ Effect：干预 / 撤下检查                         │ 观察 + 干预的真实结果
                ▼                                               │
 ┌──────────────────────────── app（Android 适配层）───────────────────────────────────────────┐
 │  AndroidPlatform：UsageStats 读前台 App 和使用时长；如实报告当前真正可用的能力               │
 │  LoopService：前台服务，每 15 秒推进一次；常驻通知显示“现在在做什么”                         │
 │  AlarmManager：进程被杀后在下一个关键时间点拉起；BootReceiver：重启后恢复                    │
 │  Notifier / CheckInActivity：检查的提问和回答；GuardService：无障碍，送回桌面               │
 │  每次干预后回头确认：VERIFIED / NO_EFFECT / FAILED / UNAVAILABLE，两分钟后再评估行为效果     │
 └────────────────────────────────────────────────────────────────────────────────────────────┘
```

**为什么必须是原生 App**：主动在合适的时机重新出现，需要通知、精确闹钟和前台服务；知道现实里发生了什么，需要 `PACKAGE_USAGE_STATS`；施加约束，需要无障碍服务。Super Productivity 插件运行在网页环境里，这些能力一项都拿不到，旧 README 里也写明了这一点。所以插件适合做“计划层”，执行闭环必须放到原生端。

**为什么第一阶段不建立在 Operit AI 或 Shizuku 上**：第一阶段要证明的是闭环本身稳定、可验证，而每多依赖一个外部组件，就多一种“这次没发生、系统却不知道”的失败方式。

- Shizuku 在非 root 设备上，每次重启后都要重新激活（无线调试）。这正是“状态不会轻易丢失”的反面。
- Operit AI 是通用 Agent，闭环的状态必须由我们自己持有。

这两者都适合以后作为执行器接入（见第 6 节），但不适合做地基。

## 2. 第一阶段验证什么

只验证一件事：**一个意图能不能被陪着走完十分钟。**

具体来说，就是下面这个循环能不能在真实的一天里自然地反复发生：

> 声明行动 → 系统记住局面 → 一段时间后主动出现（或在偏离时提前出现）→ 拿到用户回答和客观观察 → 判定偏差 → 更新局面 → 记录 → 决定下一次什么时候看

这个循环被写成了自动化测试，作为项目方向的回归基准：

- `core/src/test/.../LoopTest.kt` 里的 `tenMinutesWithADriftInTheMiddle`：
  1. 学习课程 10 分钟，第 3 分钟切到 B站；
  2. 系统在偏离满 2 分钟时主动出现，问题里同时有“学习课程”和“B站”；
  3. 用户回答“偏了，现在回去”，3 分钟后短间隔复查；
  4. 两分钟后评估这次干预的效果为“回到了目标”；
  5. 10 分钟到点时确认结果，整轮记录完整。
- `robotest/.../AppFlowTest.kt` 里的 `theLoopRunsOnAndroid`：同一个场景，但跑的是真实的 Android 组件。主页点“开始”→ 前台服务 tick → UsageStats 里出现 B站 → 弹出检查通知 → 点通知按钮回答 → 到点后在检查页点“完成了”→ 回顾页显示这一轮的偏差。

**真机上用一两周后，看这几个数**（都在“回顾”页里，也可以导出日志自己算）：

| 问题 | 指标 | 说明闭环不自然的信号 |
|---|---|---|
| 系统能不能及时发现偏离？ | 偏离开始到检查出现的间隔 | 明显大于设定阈值加 15 秒（多半是后台被杀） |
| 检查会不会被当成噪音？ | 未回应率 | 长期高于三成 |
| 主动出现有没有用？ | 偏离类干预之后“回到了目标”的比例 | 大多是“还在原处”或“转移到别的娱乐” |
| 自报靠不靠得住？ | 自报“在做”但观察到偏离的比例 | 很高，说明不能只靠问 |
| 哪里最容易断？ | 偏离通常发生在第几分钟、偏到哪个 App | 用来调第一次检查的时间和偏离阈值 |

只有这个闭环站得住，再去加复杂的 Agent、自动化和设备控制才有意义。

## 3. 核心对象与需求的对应

| 需求里的概念 | 代码里的对象 | 要点 |
|---|---|---|
| 当前局面（工作记忆） | `Situation` | 模式、当前行动、待回答的检查、下次检查时间及理由、休息 / 静音 / 屏蔽状态、本轮偏离次数、待评估的干预 |
| 行动 | `Action` + `Expectation` | 做什么、为什么、计划多久、怎么验证（指定 App / 离开手机 / 不限）、本轮是否允许强干预 |
| 观察与反馈 | `Foreground`、`Observation`，加上 `CheckIn` 里的回答 | 客观状态（前台 App、各 App 时长、息屏时长）和用户自报分开存 |
| 偏差 | `Deviation` | 类型（符合计划 / 偏到娱乐 / 在做别的 / 没在用手机 / 无法观察）、各类时长、偏离起始分钟、一句话的“计划 vs 实际” |
| 一次交互 | `CheckIn` | 当时的局面 → 问题 → 回答（按钮或一句话）→ 判断 → 后续动作；独立成卡片，不进聊天流 |
| 干预 | `Intervention` + `ActResult` + `Aftermath` | 请求了什么、为什么；现实中是否发生；两分钟后人去了哪里 |

“系统不知道”本身也是数据：

- 没有权限时，偏差类型是“无法观察”，系统会明说“只能依靠你的回答”；
- 不回答的检查会被记为“未回应”，并按客观观察继续；
- 能力不可用时，干预会被降级，并写明理由。

## 4. 闭环是怎么跑的

**什么时候重新出现**（`Policy`）：

- 第一次检查放在计划时长的一半，最早 2 分钟、最晚 20 分钟；6 分钟以下的行动不安排中途检查。
- **偏离触发**：娱乐 App 连续在前台超过阈值（默认 2 分钟）时立刻出现，不等定时检查。“现实发生变化时把人拉回判断循环”主要靠这一条。同一段连续偏离只问一次。
- 回答“在做”后，下一次检查放在剩余时间的一半；回答“偏了，回去”后，3 分钟后复查。
- 到点一定会确认结果。休息会暂停时钟，休息结束时会叫你回来。
- 3 分钟没回应就再问一次，强度会升一级；10 分钟没回应就记为“未回应”，按客观观察继续。

**回答只需点一下**：在做 / 偏了，现在回去 / 完成了 / 还没完，再 5 分钟 / 太难，改小一点 / 休息 / 改做别的 / 没做成，先停下 / 这次别管我。

每次检查都有一个只针对它的选项子集。也可以写一句话：开了 AI 判断层时，这句话会被理解成上面的选项之一；没开时，这句话会被记进这次检查。

**干预强度怎么选**：

1. 先按本轮偏离次数定一个想用的强度：通知 → 弹出检查页 → 送回桌面 → 本轮屏蔽娱乐 App（之后再打开就立刻送回桌面）。
2. 如果上一次干预之后“回到了目标”，就保持同样强度，不升级。
3. 再用两个上限削减：用户的同意（这一轮没勾选“允许强干预”，最多只到“弹出检查页”），以及当前真正可用的能力。
4. 每个决定都附带一段理由，例如：“本轮第 3 次偏离，离开娱乐 App；「送回桌面」当前不可用，降为「弹出检查页」”。

**请求执行和现实执行是分开的**：每次干预都会生成一条请求事件，平台执行后必须回报真实结果。

| 干预 | 怎么确认真的发生了 |
|---|---|
| 通知 | 通知总开关和“检查”渠道都开着，才算 VERIFIED（细节里注明“无法确认是否被看到”） |
| 弹出检查页 | 2 秒内检查页真的进入前台（Activity 自己登记），否则记为 NO_EFFECT，并注明“可能缺少悬浮窗权限或被厂商拦截” |
| 送回桌面 | 无障碍服务没开就是 UNAVAILABLE；执行后 1.5 秒再看前台，目标 App 还在就是 NO_EFFECT |

确认只看结果，不归因：送回桌面后娱乐 App 确实离开了前台，就记为“已确认生效”，即使用户恰好是自己切走的。

有目标 App 的干预，两分钟后还会再评估一次行为效果：回到了目标、还在原处、转移到别的娱乐（行为转移）、离开了手机、去做了别的。

## 5. 关键取舍

**状态：只追加的事件日志，而不是数据库表。**

- 所有状态变化都是一行 JSON，写入后立刻 fsync。`Situation` 完全由重放得到，进程被杀、手机重启、升级之后都能原样恢复。这一点在单元测试和 Robolectric 测试里都验证过：重放结果和内存里的状态一模一样。
- 写到一半断电留下的残行，读取时会跳过，下次追加前也会补上换行。
- 未知事件类型会被跳过，所以老版本读新日志不会崩。
- 代价：数据量大以后统计会变慢。到那时可以加 SQLite 作为可重建的索引，日志仍然是唯一的真相来源。

**规则和大模型的分工。**

- 何时检查、问什么、多大力度，全部由本地规则决定。确定、可测、免费、离线，而且每个决定都有理由。“前台娱乐 App 连续 2 分钟 + 正在学习”这种判断不需要大模型。
- 大模型只在规则处理不了的地方出场：用户写了一句话而不是点按钮。它的输入是当前局面、客观观察和最近几轮记录，输出是结构化 JSON。输出只能落在这次检查给出的选项里，不能自己升级干预强度，解析失败或越界就当作没有回答。
- 以后再逐步交给它：重新规划、拆小任务、每日复盘，以及思维域（见第 6 节）。

**观察来源：以 UsageStats 为准，无障碍只做触发器。**

- UsageStats 在所有 Android 8+ 设备上都可用，授权一次就长期有效，而且能回看任意时间段，进程被杀后也能补上中间发生的事。缺点是有几百毫秒到几秒的延迟。
- 无障碍事件是即时的，但敏感：Android 13+ 侧载安装还需要先“允许受限制的设置”。所以只用它做两件事：前台切换时立刻 tick 一次，以及执行“送回桌面”。它不读取任何窗口内容。

**界面：不用 AndroidX / Compose，只用 Android 框架。**

- 这个开发环境访问不了 Google Maven。只用框架 API，才能在这里完整编译、打包、签名，并用 Robolectric 跑过真实的 Android 组件。APK 只有约 870 KB。
- 代价：界面朴素。闭环跑稳以后，可以只替换 `app` 里的界面层，`core` 不用动。

**其他：**

- `targetSdk` 是 34，避免 Android 15 强制全面屏让纯代码界面被状态栏遮挡。
- 常驻通知用倒计时显示“现在：X（6/10 分钟）· 为什么 · 下次检查”。这本身就是最弱、最持续的一种干预：把意图留在眼前，不让它退出工作记忆。

## 6. 已知风险与后续方向

**还没在真机上跑过。** 现在的验证是：

- core 的 17 个单元测试，覆盖闭环、升级、静音、休息、改小、未回应、重放、日志兼容、AI 输出约束、统计；
- 6 个 Robolectric 集成测试，在 Android 14 框架上运行真实的 Application、Activity、Service、通知、UsageStats、AppOps、无障碍服务。覆盖：完整的一轮、没有权限时的表现、能力不可用时的降级、通知里“说一句”的回复、弹出检查页没真正出现时记为没生效、送回桌面后娱乐 App 仍在前台时记为没生效。

Robolectric 模拟不了厂商系统的行为。真机上需要留意这些：

- **国产系统的后台清理**（MIUI / HyperOS / ColorOS / 鸿蒙等）：需要允许自启动和后台运行，并关闭电池优化。设置页里有入口，兜底闹钟能缓解被杀的问题，但不能完全消除。
- **部分 ROM 上 UsageStats 事件有延迟**：偏离发现会相应变晚，回顾页里“偏离开始到检查出现的间隔”会暴露这个问题。
- **从后台弹出检查页**：Android 10+ 需要悬浮窗权限；Android 14 的全屏通知权限可能被收回。这两种情况都会被记为 NO_EFFECT，同时仍然会发通知。
- **跨设备转移看不到**：干预后“离开了手机”，可能是真的去做事了，也可能是换到了电脑上。这要等电脑域接进来。

**之后按这个顺序扩展。** 每一步都复用同一套 Observation / Intervention / 验证接口：

1. **用数据调规则**（真机用一两周后）：阈值、第一次检查的时间、各级干预在不同 App 和时段的实际效果，把“上次有效就不升级”扩展成基于历史的选择。再加桌面小组件和快捷设置磁贴，把声明行动的成本降到两秒。
2. **设备级执行器**：通过 Shizuku 或 ADB 执行 `pm suspend` 或 `am force-stop`。它作为新的 `Level.DEVICE` 实现接入，可用性和执行结果照样如实回报。Operit AI 也可以作为一种执行器或判断器，通过 Intent 接入。
3. **电脑域**：浏览器扩展或本地 Agent 把前台窗口和标签页报给手机（或报给一个共享的日志），`Platform` 从单一来源变成多来源合并。到那时，“离开了手机”就能分辨出是不是转移到了电脑。
4. **思维域**：同一个闭环，换一种预期。“接下来要弄清 X”是行动，用户的笔记或回答是观察，偏差是“原地打转 / 重复已有信息 / 卡在某一步”。`CheckIn` 会增加“当前问题、已知信息、推理到哪、卡在哪”这类字段，由 AI 判断层维护，并主动提出下一个问题。
5. **和 Super Productivity 插件打通**：SP 负责一天的计划，回路负责“现在这十分钟”。之后可以给回路加一个 Intent 入口，从 SP 任务一键开始一轮。
