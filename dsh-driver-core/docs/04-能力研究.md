## 0. 结论先行

**性价比前三**（理由见 §4）：

1. **说完轮次触发 + 冷却/去重/随机窗口**。在"Gemini 刚说完、该你说了"那一刻发力，不再死等 60 秒。纯规则，不花模型调用。
2. **回应三级分层 + 防重复提问**。把"醒了 / 回了 / 有依据地想了"分开记，并拦住和最近几问太像的卡。纯规则，今天就能写测试。
3. **跨会话思考议程**。没接上的断点和缺的依据存成待办，下次开场主动从它们里挑题。只需一个小文件存储和规则选题，模型可选。

**最小方案**：只改 `bandwidth.js`、`driver.js`、`telemetry.js`，新增 `agenda.js`、`similar.js` 两个文件，预计约 300 行加测试，不碰提示词结构和 HTTP 协议。见 §5。

## 1. 现状基线：驾驶员现在会什么、缺什么

已有（都在 `plugin/lib/core/`，有测试）：

- 规则水位判定（`bandwidth.js`）：四个状态，按回复耗时、敷衍词、依据词和沉默判断。
- 两级升级、断点冻结与接回、休息拉回（`driver.js`）。
- 五段推进日志（`telemetry.js`）。
- 三层提示词，模型失败退回模板（`prompt.js`、`context.js`）。
- 六骰子降维（`dice.js`）。

从模拟时间线（`bin/simulate.mjs`）和代码里能直接看到的不足：

| # | 不足 | 位置 |
|---|---|---|
| a | 沉默只有一个固定阈值（60 秒）；定时插问固定 180 秒，可预测，也就容易被习惯性忽略 | `DEFAULT_DRIVER.silenceMs` / `pushEveryMs` |
| b | 没有"Gemini 刚说完"这个时刻：`LiveInference` 只报"开始说话"，不报"说完" | `android/kotlin/DriverReflex.kt` |
| c | 模板会重复（模拟里 4 条推进模板轮转），模型那边也没有"别重复上一问"的约束 | `driver.js #template`、`prompt.js` |
| d | `ADVANCED` 把"点了 A/B"和"说出依据"混在一起，看不出到底有没有真思考 | `driver.js #advanced` |
| e | 每次锁定都从零开始：没接上的断点、缺的依据，下次不会再被提起 | 无 |
| f | 表层"在做哪道题"要手动填，驾驶员不知道屏幕上是什么 | `start({topic, task})` |
| g | 所有出题都走同一个 DSH 会话的模型，不分难易 | `brain.js` |

## 3. 五项能力设计

每项都按：当前已有 → 参考代码 → 可复用部分 → 技术障碍 → 调用成本 → 预期收益 → 验证方式。

### 3.1 主动唤醒调度：随机时间窗口、上下文触发、冷却、去重

**当前已有**
- 固定 60 秒沉默触发（`tick` 里 `silenceMs`），第一次给"念给 Live"卡，再沉默给骰子卡。
- 固定 180 秒插问（`pushEveryMs`）。
- 不应答 30 秒升级。
- 没有去重：同一原因可以连着触发。

**参考代码**
- Open-LLM-VTuber-Web 的 IDLE 边界计时（L47-64）。
- Mika 的 `claimDue` 账本 + `lastConditionMet` 只在变化时动作 + `missedIntervals` 只补一次。

**设计（可复用部分）**
- **说完轮次触发（核心）。** `LiveInference` 增加 `AssistantStoppedSpeaking` 边沿（播放持续 ≥ 1.5 秒后消失）。插件收到 `audio {assistantSpeaking:false}` 后进入"轮到你"窗口：
  - 8–15 秒（随机）内没有新的对话迹象 → 触发一次轻提醒；
  - 窗口内你一开口（Gemini 又说话了）就作废。
  - 这和 VTuber"回到 IDLE 才计时、任何状态变化清零"是同一个模式，只是信号来自系统音频状态。
- **随机窗口。** 定时插问从固定 180 秒改成在 `[120, 240]` 秒里抽，用注入的随机数源，测试时可固定种子。
- **冷却与去重**（借 Mika 账本）：
  - 每次唤醒记一条 `{reason, dueAt, state}`；
  - 同一 reason 在冷却期（如 90 秒）内只派发一次；
  - 进程重启时还在 `claimed` 的那条不重发；
  - 同一种沉默一直持续时，只在"从说话变成沉默"那一刻派发一次（`lastConditionMet` 模式）。之后的升级交给已有的不应答链路，不再叠加新卡。

**技术障碍**
- 说完边沿依赖 `getActivePlaybackConfigurations()` 能稳定看到 Gemini 的播放。这一点**还没真机证据**（docs/02 §6 第 3 项）。拿不到时只能退回现在的 60 秒全局沉默。
- Gemini Live 有时会连说几段，中间有短停顿。阈值（1.5 秒）要靠真机数据调。

**调用成本**：零模型调用。轻提醒用现有的 `say_to_live` 模板。

**预期收益**：最高。现在的 60 秒在 Live 场景太晚了：你沉默 60 秒时，思考早就断了。"Gemini 说完 10 秒你还没接话"才是你最需要被推一下的时刻。

**验证方式**
- 单测（今天就能写）：喂一串 `audio true/false` 事件和注入时钟，断言窗口内开口会作废、冷却期内不重复、随机窗口落在区间内。
- 真机（以后）：录 3 次 15 分钟会话的音频状态日志，看"说完"边沿和你实际沉默的对齐程度。

### 3.2 思考议程管理：从未解决问题和历史断点里主动选题

**当前已有**
- 会话内有断点冻结与接回。
- 开场题只看手动填的 `task`。
- `history.json` 只存骰子统计、切屏分钟、回复耗时。
- **跨会话的未解决问题完全没有。**

**参考代码**
- Mika `MemoryExtractor`（原话校验、一次性说法过滤）、`MemoryIndex`（BM25 切词）、`TriggerDefinition.reminderText`（到点直接给原文、不启动模型）。

**设计**
- 新增 `agenda.json`，每条一个待办：

  ```js
  { id, text, anchor, source, quote, createdAt, lastSeenAt, touches, status }
  // text:   "第3题·黑点数量：缺'递增'的依据"
  // source: 'unresumed' | 'missing' | 'conclusion_doubt'
  // quote:  你的原话；只在 conclusion_doubt 里用
  // status: 'open' | 'done' | 'dropped'
  ```

- **入账**（纯规则，不调模型）：
  - 会话结束时，被中断但从没 `RESUMED` 的断点 → `unresumed`；
  - 有 `missing` 但最后没 `ADVANCED` 的卡 → `missing`；
  - 结论里含"不确定/好像/可能/再看" → `conclusion_doubt`，必须带原话（Mika 的 quote 校验思路：原话不在你的回复里就不入账）。
- **选题**（纯规则）：开场时，用 BM25 拿 `topic + task` 匹配 open 议程。
  - 有匹配 → 开场卡变成 A/B："上次停在【第3题·黑点数量】没接上。A 从这接着做 / B 先做新的"。
  - 没匹配但议程非空 → 隐秘层多一行"未解决：…"给模型参考。
  - 选中并答出依据 → 标 `done`；连续 3 次被跳过 → 标 `dropped`，不再纠缠。
- **以后再做**（需要模型）：会话后单独一次轻模型调用，从你的回复里提取"新暴露的死穴"，写进 `profile.habits` 的候选区，经你确认才生效。这是 Mika procedure 记忆的 pending 状态。

**技术障碍**
- 文本相似匹配对改写过的题目不准（"第三题" vs "第3题"）。先做数字归一，再靠 BM25 的两字切词。
- 议程会膨胀：设上限 30 条，超出淘汰最旧的。

**调用成本**：入账和选题零调用；以后的死穴提取每次会话 1 次轻模型调用。

**预期收益**：中高。直接解决"缺少长期记忆、每次从零开始"。开场第一问从"你卡在哪"变成"上次没接上的那个"，更像一个记得你的教练。

**验证方式**
- 单测：跑两次会话，第一次在断点处切屏后紧急结束，第二次开场断言是议程 A/B 卡，答对后状态变 `done`。
- 反例测试：结论里有"可能"但原话校验失败时不入账。

### 3.3 回应质量管理：区分唤醒、回应、有依据的思考（含防重复提问）

**当前已有**
- `replyFeatures` 有敷衍/放弃/依据/命中关键词/A-B 判断。
- `ADVANCED` 有 `why` 字段，但汇总只数一个总数，`advanceRate = advanced / generated`。
- 没有重复检测。

**参考代码**
- Mika `MemoryIndex` 的切词（用来算两张卡的相似度）。
- VTuber `handle_interrupt` 只记"真正听到的那部分"的口径。
- closepaw `onUserResponseSent(callId)` 只认对上号的回应（现有驾驶员已经这样做）。

**设计**
- **三级**，在 `Telemetry.summary()` 里分开数：

  | 级 | 定义 | 来自 |
  |---|---|---|
  | 醒（awake） | 卡亮出后 N 秒内出现任何对话迹象（点卡、打字、Gemini 开口） | `surface displayed` 之后的第一个信号 |
  | 回（responded） | 回复了这张卡且不是敷衍：A/B、念两个词、`say_to_live` 推断 | 现在 `ADVANCED` 的 `atomic_choice` / `words_given` / `spoke_to_live` |
  | 想（grounded） | 说出了依据或命中期望关键词 | 现在 `ADVANCED` 的 `basis_given` / `substantive` / `conclusion_given` |

  会话结束时报告的主指标改成 **"有依据的思考次数"**，而不是推进率。点 A/B 是为了把你从断线拉回来，不应该被当成思考。
- **防重复提问**：
  - 新增 `similar.js`：两字切词后算 Jaccard 相似度。
  - `#register` 前和最近 5 张卡比；相似度 ≥ 0.6 就换一个模板或骰子重出，模板用完就换意图（例如从"要依据"换成"排除哪个"）。
  - 给模型的提示词表层加一行"最近问过：…（别重复）"。
  - 被打断时没真正显示过的卡（没有 `DISPLAYED`）不计入"问过"（VTuber 口径）。
- **依据判定的灰区交给轻模型**（见 §3.5）：
  - 规则判不准的回复（不快不慢、没依据词、≥ 6 字）才问轻模型"这句有没有给出具体依据？只回 JSON `{grounded:bool}`"；
  - 解析失败记为"未判定"，**不当成没依据**（Mika `ConditionOutcome` 口径）。

**技术障碍**
- 字面相似度抓不到"意思一样、说法不同"的重复。这是第一版的已知局限；要抓同义重复得上嵌入向量，本轮不做。
- "醒"的 N 秒取多少需要数据，先取 15 秒。

**调用成本**：分级和去重零调用；灰区判定每次 1 次轻模型调用，预计每会话 2–4 次。

**预期收益**：高。直接回答"敷衍、重复提问"两个痛点；也让以后所有改进有一个不会自欺的指标。

**验证方式**
- 单测：同一会话里连续生成的卡两两相似度 < 0.6。
- 用模拟时间线回放，断言三级计数和人工标注一致。
- 加一个反例："A"不能被计入"想"。

### 3.4 Gemini Live 外部引导：悬浮卡通过屏幕共享影响对话

**当前已有**：`say_to_live` 卡让你**念**一句话给 Gemini，Gemini 一开口就推断你已经念了。没有利用屏幕共享。

**参考代码**
- ScreenSeek（一帧截取、框选裁剪、单次视觉调用）。
- Orbit `onHandleAssist`（默认助手拿屏幕）。
- closepaw `OverlayLocationPolicy`（悬浮层与前台判断）。

**设计思路（未验证的假设）**
- Gemini Live 打开"共享屏幕"后能看到整个屏幕。如果驾驶员的悬浮卡在屏幕上，卡上的字理论上也会被它看到。
- 于是可以有一种**"看卡"卡**：卡上写一段写给 Gemini 的话，例如"致 Gemini：他停在第3题·黑点数量，请只用一个 A/B 问题问他"。你只需要说两个字"看卡"，就把引导交给了 Gemini。开口成本比念一整句还低。
- **必须有失败回退**：说"看卡"后 10 秒内 Gemini 没开口，或你按了"没用"，就退回现在的 `say_to_live` 整句卡，再不行就退回 A/B。三级回退都已有，只是多加了最前面一级。

**技术障碍（全部未验证，任何一条不成立这项就做不了）**
1. Gemini Live 的屏幕共享**是否会把其他应用的悬浮窗一起传过去**。Android 14 起部分系统支持"只共享单个应用"，那样悬浮卡就不在画面里。
2. Gemini Live 是否只在你说话时才看屏幕。目前没有证据表明它会主动对画面变化开口，所以"看卡"两个字仍然是必须的。
3. 屏幕共享开着时，驾驶员的 level 1/2 全屏卡会盖住学习内容，Gemini 看到的是卡而不是题。全屏卡出现时要提示"先回到题目"。
4. Orbit 的默认助手方案和 Gemini 抢同一个系统角色（默认数字助理只能有一个），**不采用**。
5. ScreenSeek 式截屏需要单独的录屏授权（每次弹系统确认）。和 Gemini 同时录屏会不会互相影响**未知**。

**调用成本**
- "看卡"本身零调用。
- 若用 ScreenSeek 式框选"钉住这题"补表层（不足 f）：每次钉题 1 次视觉模型调用，只在你主动框选时发生。

**预期收益**：不确定。成立的话开口成本最低；不成立就什么也没得到。所以排在前三之外，先做验证。

**验证方式（手动协议，5 分钟）**
1. 开 Gemini Live 并共享屏幕。
2. 在任意应用上放一张测试悬浮卡，写"暗号：蓝鲸七"。
3. 对 Gemini 说"屏幕上的暗号是什么"。
4. 能答出 → 障碍 1 通过；再测"看卡"能否让它按卡上要求提一个 A/B 问题。
5. 记录系统版本和共享模式（整屏/单应用）。

### 3.5 成本路由：规则优先，轻模型判简单的，强模型出难题

**当前已有**
- 规则层已经很重：水位判定、拉回卡、沉默卡、骰子卡、结论卡都是模板。
- 只有开场、推进、刹车、接回会去问 DSH 会话的模型，没有轻重之分，超时 8 秒退模板。

**参考代码**
- Mika 的 `MemoryExtractor`（任务结束后单独一次轻量调用、不带工具，结果全部由代码复核，模型出错时什么也不做）。
- Mika `ClientHeaders.kt` 注释里列出的多种辅助调用（轻量、起标题、核查、意图判断），说明它也是主模型和轻模型分开调。
- `MemoryContext` 全量注入以利缓存。

**设计：三层，按动作固定分派，不让模型决定走哪层**

| 层 | 用在 | 现状 |
|---|---|---|
| 0 规则 / 模板 | 拉回、沉默、骰子、结论、议程选题、去重、三级计数 | 已有大部分 |
| 1 轻模型（单轮、无工具、只回 JSON） | 灰区依据判定（§3.3）；把模板句子换个说法（防机械感）；会话后死穴提取（§3.2） | 新增 |
| 2 强模型（DSH 出题会话，带三层上下文） | 开场、刹车、接回后的追问、结论复核 | 已有 |

- 轻模型从哪来：独立 APP 方案里可由 APP 直接调用一个便宜的 OpenAI 兼容接口（自带 key）。这条路**还没决定**，属于下一轮。插件这边只定义接口 `judge(text) → {grounded} | null`，拿不到就当"未判定"。
- 强模型省钱：隐秘层记忆少时全量注入、顺序固定（Mika `Auto` 模式），让前缀更容易命中缓存。DeepSeek 有前缀缓存，交接包里 fish-memory 的注释也证实了这一点。

**技术障碍**
- 轻模型的判断和规则冲突时听谁：规则判出敷衍/放弃时规则优先；只有规则说"不确定"才问轻模型。
- 改写模板可能改坏 A/B 选项，所以只改 `text`，不动 `options`。

**调用成本**（按现有提示词实测约 2,500 字符、粗估 1.5k–2k token 计）
- 一次 15 分钟会话预计强模型 6–10 次：输入约 1.5–2 万 token，输出约 1 千 token。
- 轻模型 2–6 次，每次几百 token。
- 规则层零成本。
- 价格随模型变，这里不写金额。

**预期收益**：中。主要是让"非机械化"有便宜的实现（轻模型改写），而不是省钱：规则层本来就承担了大部分。

**验证方式**
- 单测用假轻模型：确认只有灰区回复才调用；解析失败不改变判定。
- 统计每会话三层的调用次数并写进推进日志。

### 3.6 （支撑项）用 promptfoo 评测主动提问和追问

不是能力本身，但上面每一项都需要它来证明"变好了"。

- **提供方**：写一个 `eval/driver-provider.mjs`。它的 `callApi(prompt, context)` 从 `context.vars` 读一份上下文样例（水位、上一问、最近回复、死穴），调用现有 `synthesize()` + `driverPrompt()` 发给模型，再用 `parseCard()` 解析。返回原始输出和解析结果。
- **确定性断言**（JS，零成本，先跑）：
  - 能解析；
  - 字数 ≤ 40；
  - THROTTLED/ESCAPED 时只能是 ab/read_two_words；
  - ab 有两个选项；
  - 与 `vars.lastQuestions` 的相似度 < 0.6（复用 §3.3 的 `similar.js`）。
- **模型评分**（llm-rubric，按次付费，后跑）：
  - "这一问是否用到了给定的死穴或规律？"
  - "是否 3 秒内能答？"
  - "是否追问了依据而不是重复要求同一件事？"
- **多轮**（simulatedUser）：给模拟用户一个人设"他总是回'嗯'和'选D'，只有被问到具体词才说依据"，跑 6 轮，看驾驶员能不能在 6 轮内逼出一次依据。要注意：模拟用户本身也是模型，结果只能做相对比较，不能当真人效果。
- **样例集**：从推进日志 JSONL 里抽真实上下文，去掉敏感内容后做成 20–40 条。现在还没有真实日志，第一版只能手写。

## 4. 按性价比排序

| 排名 | 能力 | 成本 | 收益 | 能否今天验证 | 主要风险 |
|---|---|---|---|---|---|
| 1 | 说完轮次触发 + 冷却/去重/随机窗口（§3.1） | 零模型调用；插件约 120 行；Kotlin 加一个边沿 | 最高：卡在真正断线的那一刻 | 插件逻辑可以；音频边沿要真机 | 拿不到播放状态时退回 60 秒，不会更差 |
| 2 | 回应三级 + 防重复（§3.3，不含轻模型灰区判定） | 零调用；约 100 行 | 高：治"敷衍、重复"，并建立不自欺的指标 | 完全可以 | 字面相似度抓不到同义重复 |
| 3 | 跨会话思考议程（§3.2，不含模型提取） | 零调用；约 100 行 + 一个 JSON 文件 | 中高：治"没有长期记忆" | 完全可以 | 题目改写后匹配不上 |

- ScreenSeek 式钉题（要录屏授权，和 Live 并存未知）；
- promptfoo 评测（等前两项落地后跑，用来证明效果）。

## 5. 最小方案（基于现有驾驶员，未实现）

只改纯逻辑层，不碰 HTTP 协议的已有字段，不碰提示词的三层结构。

| 文件 | 改动 |
|---|---|
| `lib/core/similar.js`（新） | `terms(text)`：汉字两两切词 + 数字归一（思路同 Mika `Tokenize`，重写）；`jaccard(a, b)` |
| `lib/core/driver.js` | ① `audio()` 接受 `assistantSpeaking:false`，记 `turnEndedAt`，开一个 8–15 秒随机的"轮到你"窗口；`tick()` 里窗口到期且没有新迹象 → 派发一次 `say_to_live`，原因记 `turn_gap`。② 唤醒账本 `s.wakes`：`{reason, at}`，同一 reason 90 秒冷却；沉默只在"说话 → 沉默"变化时派发一次。③ `pushEveryMs` 改为 `[pushMinMs, pushMaxMs]`，用注入的 `rng`。④ `#register` 前调 `similar.jaccard` 和最近 5 张已显示的卡比，≥ 0.6 就重出（最多 2 次，仍重复就换意图）。⑤ 会话结束时把未接回的断点、未补上的 `missing` 写入议程。⑥ `start()` 时先查议程，命中就用议程 A/B 卡作开场 |
