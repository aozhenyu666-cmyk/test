# 伴生：产品说明

版本：交给 Claude 的开发交接版 v1.0 · 2026-10-22

配套文件：[执行方案与 GitHub 复用清单](02-execution-plan.md)。两份文件共同描述本次任务，可直接交给开发 AI。

## 1. 要做成什么

**做一个常驻桌面的中文 AI 伙伴：它能跟上我与 ChatGPT / Gemini 的讨论，在我卡住、想反驳、需要材料或暂时接不上话时，自然地接住这段交流，让我更容易继续思考和表达。**

项目名为「伴生」。当前服务于个人自用，允许接入能力较强的云端模型和付费语音 API。质量目标是聪明、自然、及时、有稳定的桌面存在感。

用户能从一段实际体验中感到：“它知道我们刚才在说什么，有自己的反应，我可以顺着它说，也可以直接纠正它。”产品成功看这种体验，以及用户是否更容易回到有内容的讨论。

## 2. 使用背景与三个角色

用户已经在用 ChatGPT、Gemini 等主力 AI，尤其希望保留原产品的交流能力与使用习惯。困难主要发生在：不知道下一句怎么说、回复太长而失去兴趣、思路跳转后忘记原来的问题，以及卡住后很难重新进入讨论。

| 角色 | 负责的事 |
|---|---|
| 用户 | 提出想法、感受和判断，可以含糊、停顿、反悔、跳话题；无需每次组织完整问题 |
| 主力 AI：ChatGPT / Gemini | 主要的分析、推演、知识回答和内容生成，继续在用户原本使用的入口中工作 |
| 伴生 | 理解当前讨论、记住关键点、作出自然反应、提供有价值的切入点，并在适当时机把话题接回主力 AI |

Claude、DeepSeek、TPC 等在本次交接中是开发协作者。它们是否也作为伴生运行时的模型，由实际 API 能力决定；这两种角色需要分清。

## 3. 一次完整使用应当怎样发生

1. 用户打开桌面的伴生，开始一场讨论，选定当前的主力 AI 会话。当前主题可以从对话中逐渐形成，不要求先填一份任务表。
2. 用户照常与 Gemini 或 ChatGPT 交流。伴生持续接收这场讨论中可获取的用户表达、主力 AI 回复及必要的语音状态。
3. 伴生一边听或看，一边更新对讨论的理解。有价值的想法可以提前准备，是否说出来另行决定。
4. 当出现具体的矛盾、有趣的点、值得追问的缺口，或者用户明确表示卡住时，伴生作出短而贴切的反应。它可以有倾向、给一个可修改的建议，也可以只表达好奇。
5. 用户可以接着说、反驳它、转回主力 AI、忽略它，或让它安静。伴生顺着实际反应调整，不要求用户完成固定交互步骤。
6. 结束时保留本场主题、已确认的结论和未解决点，方便下次接续。笔记归档可以随后进行。

三方交流是完整验收的必要条件。仅能与伴生一对一聊天的演示，可作为开发过程中的局部成果。

## 4. 必须具备的产品能力

| 编号 | 能力 | 做到什么程度 |
|---|---|---|
| F1 | 理解当前讨论 | 能结合本场较早的关键表达解释眼前的新回复；保持用户、主力 AI、伴生的内容来源，识别用户的最新修正 |
| F2 | 主动而有内容 | 主动介入必须关联当前材料或相关记忆；能先提出一个具体看法，降低用户从零提问的负担 |
| F3 | 自然的中文声音 | 支持流式输出、用户打断、停止旧内容，声音清楚、节奏可听；用户开口后能及时把话权交回去 |
| F4 | 桌面存在感 | 有常驻的轻量角色或视觉形象，表现听、想、说、安静等状态；不遮挡主要操作，窗口切换后仍可找到 |
| F5 | 三行路标 | 展示“当前在聊什么 / 已确认什么 / 还有什么没解开”；支持收起和修正，内容跟随讨论更新 |
| F6 | 连续的会话记忆 | 保存本场的目标、关键依据、约束、结论和改口；能够导出、恢复本场状态，记住明确的交互偏好 |
| F7 | 共同控制节奏 | 用户随时可叫停、暂停主动发言、恢复陪伴；主力 AI 正在说话时能协调话权，避免三个声音叠在一起 |
| F8 | 可诊断、可替换 | 能知道一次介入依据了哪段内容、为何播放或取消；模型与语音服务可通过配置或适配层更换 |

三方交流还需识别用户这句话是对谁说的。首版可以沿用原应用的语音按钮、当前会话选择或一个明确的唤起动作，避免一句话同时触发两个 AI 长篇回答；之后再优化免按键的对象识别。

F1 和 F6 要求的是有效的上下文管理。可以使用增量摘要与按需检索，无需每次重发全部历史；摘要必须保留来源和用户修正，不能只剩下笼统主题。

主力 AI 网页、原生客户端、Live 语音可能开放不同的内容。产品必须清楚区分实际读到的、转写得到的和尚不可见的部分；无法读取其内部历史或隐藏状态时，不应声称已经同步。

## 5. “活人感”具体意味着什么

伴生的表现需要包含对内容的直接反应、好奇、轻微玩笑、不同意见、短回应，以及适当的安静。用户抱怨时，它可以先回应那件事本身；用户已经进入思考时，它可以只保持在场。

**允许它有主见并主动把事情往前带。** 当有充分上下文时，可以直接提出下一步、指出某个矛盾，或给一个不完整但可修改的想法，让用户有东西可接。建议仍是建议，用户确认后才进入“已决定”的记录。

不强制每句末尾问一个问题，也不强制每次给选项。不把 180 字、固定三句话、固定十秒沉默或固定介入比例设为总规则。主动接话通常先说一个短句；内容有价值、用户接住后再展开。

所谓快速反应，应尽量带着当下内容。动作、音效和“嗯”可以表达正在听，但不能不断用这些占位，掩盖后面迟迟没有有效回应。

“两个声音抬杠”保留为以后可比较的交互实验。首版先让一个伙伴表现出稳定、灵活、能听懂的个性。角色外形和说话风格可以调整，不预设必须模仿某个平台的网友或采用某种二次元人设。

### 供理解方向的例子

下面是设计示例，不是触发后逐字播放的台词库。

| 当时发生了什么 | 伴生可能怎样参与 |
|---|---|
| 主力 AI 又加入一套复杂系统，而用户刚说怕做不出来 | “诶，它怎么又加了一套后台系统。你刚才才说怕弄复杂。” |
| 主力 AI 回答很长，其中有一个值得继续追的点 | “我倒想听它把第三段那个例子讲具体一点。前面那些先放着。” |
| 用户说不知道从哪里开始 | “我先押接话这件事。先听一小段，你觉得假，我们就改那一段。” |
| 用户突然觉得伴生也会太吵 | “对，我刚才也在往里塞东西。你先和它说，我听着。”随后实际减少介入 |
| 用户在查与当前问题相关的网页 | 保留原问题；有可读材料时把新内容连回来，暂时没有有用联系就安静 |
| 用户停顿后继续自言自语 | 保持听取、必要时作轻回应；不因计时器到点插入一段建议 |

## 6. 桌面体验与声音的要求

“高级感”落实在协调的体验：启动和连接状态清楚；动作与真实听说状态一致；声音不中断、不重复、不忽快忽慢；角色和三行路标占用有限空间；用户能迅速收起、静音或恢复。

Coopanion 是桌面存在感的参考。自然的人声、中文韵律、打断和话权需要单独验证，不能用精美角色或拟声效果代替这些能力。

双模型、全双工、自定义声线、复杂动画都是可选实现手段。若一个现有模型配合预生成、流式语音和正确的取消机制已经满足体验，可以直接采用。

## 7. 本轮范围与分期

**首个完整版本交付：一个桌面底座、一种可用的中文语音链路、至少一个真实主力 AI 会话入口、当前会话记忆、主动参与、三行路标和随时停止。** 默认优先验证 Gemini 的实际使用入口，再扩展 ChatGPT。

第一条三方链路可先贯通浏览器文字会话；与此同时，早期必须验证主力 AI 的原生语音共存问题，包括可获取的字幕或音频、麦克风使用、说话者区分和伴生插话。语音共存通过后，才算覆盖用户希望的“与 Gemini 语音交流时伴生在旁边”的场景。

先保留的质量底线：有上下文的智能、真实声音、三方协作、自然反应和可停止。规模可以缩小，不能把这些全部换成脚本演示。

之后按实际缺口扩展：跨天笔记检索、第二个主力 AI 适配器、更多声线、多个角色、手机端、自动执行操作。Notion 等笔记工具放在归档或检索环节，不承担实时对话转接。

## 8. 怎样判断满足了需求

技术上，需要真实数据流、语音可打断、记忆可修正、过时内容可取消，且断线后不会重复旧话。

体验上，用同一段三方交流比较两种表现：一种偏总结与安排下一步；一种允许反应、好奇、轻回应和安静。由用户指出哪些具体瞬间想接话，哪些瞬间觉得烦、假或被催促。保留原话和当时上下文用于改进。

最终应能回答：它是否抓住了我真正关心的那个点；是否让我更容易说出自己的想法；是否帮助我继续与主力 AI 讨论；是否知道什么时候退开。

不把聊天时长、发言次数或模型自评的“自然度”单独当作产品成功。用户主动结束一场已经完成的讨论，也属于正常结果。

## 9. 交接时仍需确认的事实

目标操作系统、实际使用的 Gemini / ChatGPT 入口、可用 API 与声线尚未由用户明确指定。Claude 应优先从已有项目和实际使用环境确认；确实无法推断的必要信息再集中询问。开发用的云端 Linux 环境不能自动代表用户的桌面系统。

前期 GitHub 调研完成了文档、部分源码和 Issue 核查，尚未完成项目运行、中文音质或延迟实测。配套执行方案中的底座优先级是开发建议，由实际验证结果决定采用哪一个。
