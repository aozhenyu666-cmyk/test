# 伴生：交给 Claude 的执行方案与 GitHub 复用清单

版本：v1.0 · 2026-10-22

先阅读 [产品说明](01-product-brief.md)。本文件规定工作安排、复用方向和交付标准；具体语言、目录和服务组合由 Claude 根据选定项目确定。

## 1. 接手后的总任务

基于现有开源桌面伙伴和语音组件，交付产品说明中的第一套真实三方体验。先读取现有代码、找到扩展位置，再进行必要修改。已有能力优先配置和复用，新增代码主要围绕主力 AI 会话接入、伴生的会话理解与介入策略。

开发顺序：**跑通一个现有桌面伙伴 → 接入真实主力 AI 内容 → 形成会话理解和主动反应 → 调整自然语音与话权 → 用真实场景验收。** 主力 AI 原生语音能否共存，应在最开始做可行性检查。

接手后持续推进到可运行结果。只在实际需要目标平台、账户配置或用户体验判断时询问；常规实现选择由 Claude 根据证据作出。交付中明确哪些已经运行，哪些仍是回放或模拟。

## 2. 默认选型与替换顺序

| 部分 | 默认安排 | 何时换或补 |
|---|---|---|
| 桌面底座 | 先核验 **N.E.K.O.**：其中文语音、主动话题、记忆与角色功能接近需求 | 若目标系统运行、真实会话接入或可维护性存在实质障碍，转验 **AIRI**；最终选一个 |
| 桌面体验 | 用 **Coopanion** 对照常驻角色、动作、气泡和交互细节 | 作为体验参考即可；代码复用按实际许可处理 |
| 语音链路 | 优先沿用所选底座已经可用的链路 | 确有缺口再选 **LiveKit Agents** 或 **Pipecat** 中的一套；前者优先看表达性示例，后者优先看流式管线和交付控制 |
| 主动参与 | 借鉴 **Thoughtful Agents** 的“生成候选 → 评价 → 选择是否说” | 先加入少量候选和明确的取消条件；需要时再引入更多研究模块 |
| 主力 AI 上下文 | 先接一个实际会话，优先验证用户使用的 Gemini 入口 | 浏览器读取参考 **browsa** 和 **Council Bridge**；原生客户端另验辅助功能或字幕/音频路径 |
| 中文轮次 | 先使用底座已有的 VAD、轮次与打断机制 | 误判明显时比较 **Smart Turn + Silero VAD**；轻回应时机进一步参考 **MaAI** |
| 记忆 | 复用底座现有存储，补齐本场关键状态和来源 | 跨天检索出现明确缺口后，再评估 **mem0** 等 |
| 调试 | 先保留会话事件、介入原因、模型耗时和真实播放记录 | 现有日志不足时加 **Langfuse**；行为对照可用 **promptfoo** |

N.E.K.O. 是第一勘察对象，并非已经验证最优。Claude 可以根据一次实际运行和扩展点检查改选 AIRI，交付中写明理由即可。若两者均有实质障碍，再查看 Open-LLM-VTuber 等备选，无需先安装所有候选。

## 4. 实施阶段与每阶段产物

阶段按结果推进，不用先承诺未经验证的工期。遇到某个外部入口受阻时，可继续完成独立模块；真实入口仍是最终验收项。

### 阶段 A：跑通现有底座，确认真实入口

**要做的事：**

- 读取实际工作目录、项目约束和用户现有成果，确认目标桌面系统。选择一个上游版本并记录提交号、启动方法和本次修改位置。
- 先验 N.E.K.O. 的桌面形态、中文输入/输出、真实打断；必要时换 AIRI。列清哪些能力来自底座，哪些需要补。
- 找到模型调用、语音播放、记忆更新、主动消息和桌面展示的扩展入口。可用现成设置或插件完成的部分先用现成入口。
- 对用户的主力 AI 入口做一次实际采集：能否获得自己的输入、主力 AI 完整回复、流式完成状态及当前会话标识。
- 同时试一次原生语音共存：主力 AI 是否能继续正常收音和播放；伴生能读到什么；如何避免误把主力 AI 音频当作用户发言。先验证输入输出通道与话权，再承诺全程自然插话。

**交付：**可启动的上游基线、简短的选型记录、真实入口的能力表、缺口与后续改动位置。浏览器文字和原生语音分别标记通过、局部通过或待验证。

**继续条件：**至少跑通桌面与一条真实中文语音链路，明确一条可实现的主力 AI 上下文路径。缺少凭据或设备时，直接记录缺项并继续可完成的代码工作，不把模拟结果标为通过。

### 阶段 B：让它确实理解同一场讨论

**要做的事：**

- 优先接入一个真实会话。先做最少的页面/字幕/音频适配，保留人工导入或回放作为调试工具。
- 为输入保留“哪个会话、谁说的、什么时候、来自哪里、内容是否完整”。识别当前轮次的增量与最终内容，避免把流式片段和重新滚动读到的旧消息反复当成新话。
- 在底座已有记忆上增加当前主题、关键依据、用户约束、确认结论、未解决点和最近改口。已确认结论必须能回到相应的用户表达。
- 做好三行路标，先保证内容准确和可修正，再调整样式。用户没有确认的建议留在待考虑内容中。

**交付：**用户、主力 AI、伴生三个角色的实际事件流；能跨数轮记住约束的会话状态；会随讨论变化的三行路标。

**验收例子：**用户先说“怕复杂”，主力 AI 后来加后台系统，伴生能关联起来；用户改口“这次允许复杂，先要效果”，旧约束随后不再继续支配它的发言。

### 阶段 C：加入主动思考和自然参与

**要做的事：**

- 在主力 AI 新回复、用户新表达或话题变化时更新理解，提前准备少量有内容的候选。避免按每个字符、音频块重复请求大模型。
- 每条候选带上相关的会话状态版本、依据和适用条件。播放前确认它仍然相关、没有重复、当前可以介入。
- 借鉴 Thoughtful Agents 的候选与筛选流程，并使用 LiveKit 表达性示例调整接话动作。允许直接反应、好奇、轻微挑战、简短提议，也允许没有值得说的内容。
- 用户改口、自己接上了话、主力 AI 已补齐遗漏或用户叫停时，撤销对应候选；撤销范围包括待播声音。
- 加入可调的主动程度与重复抑制。默认强度通过实际体验定，不固定十秒插话，也不把切窗口单独作为走神证据。

**交付：**至少一段真实三方交流中，由材料变化触发的有效介入；至少一段“准备了但因用户继续说而取消”的记录。

**验收例子：**它能指出真正相关的一点，用户可自然接话或纠正；它不会每次都重述问题、布置任务或要求二选一。

### 阶段 D：协调声音、反应速度和桌面表现

**要做的事：**

- 先优化已有流式链路。确有声音或控制缺口时，才接入一套替代语音框架。若底座支持强文本模型，优先沿用；若仅能使用特定实时模型，记录限制再决定补充方式。
- 用户开始说话时停止伴生播放，并清理旧音频队列；后端取消能力不足时，也要让客户端停止并丢弃过期结果。误打断后能恢复后续正常交流。
- 主力 AI 发声时，伴生通常先保持无声反馈或等待。需要用户主动切话时，提供低负担的暂停/唤起方式。自动检测不可靠就明确使用手动话权方案，后续再升级。
- 明确用户当前在对主力 AI 还是伴生说话，先复用原应用的语音按钮或简单的唤起动作。用户回给主力 AI 的内容可供伴生理解，但不应每次自动触发伴生另起一轮回答。
- 对“嗯、对、我在听”一类短回应做开关对照。避免它们触发主力 AI 新一轮回答，也避免用户正说关键内容时被盖住。
- 动作与真实听说状态同步；角色、气泡、三行路标都可以迅速收起，静音和恢复入口清楚。

**交付：**一套可重复试用的中文声音和桌面交互；用户打断、主力 AI 发声、伴生发声之间的切换行为；实际延迟记录。

**速度怎样记录：**分别记用户说完、转写可用、模型首字、声音首块可用、实际开始播放和实际停止播放。统计典型值与慢的一端，写明设备、网络、提供商和样本数。不能把首 token 或合成环节的宣传数字写成完整体验延迟。

半秒内作出有内容回应是可探索方向，不是本文件声称已可达到的结果。根据首轮测量定位瓶颈，再判断预生成、模型路由或声音替换的收益。

### 阶段 E：真实试用、修正与交接

**要做的事：**

- 使用同一组真实三方材料比较“偏总结/安排”与“自然反应/好奇/轻回应”两种策略；尽量保持模型、声音和上下文一致。
- 用下面的场景表检查行为，记录具体好片段和坏片段。优先修正误插话、误记忆、旧内容继续播放和明显套话。
- 用户在实际会话中体验一段，再依据反馈调整主动程度与声音。用户未试用时标记“体验待确认”，代码和客观验证照常交付。
- 形成简短的运行、配置和继续开发说明，使下一位开发者可以接手。

**交付：**可运行修改、启动说明、依赖版本、配置模板、场景结果、已知缺口及下一步。对真实链路和模拟链路分别描述。

## 5. 必须覆盖的试用场景

| 场景 | 期待结果 |
|---|---|
| 用户卡住，说“我不知道该抓哪一个” | 能给具体切入点或可修改看法，减少从零提问的负担 |
| 主力 AI 回答很长 | 抓住一个有价值的点；是否开口取决于当前节奏，避免再堆一篇总结 |
| 用户安静阅读、思考或停顿后继续说 | 能等待，实际插话不打断正在形成的表达 |
| 用户切去查与主题有关的资料 | 保留原问题；有可获取内容时建立联系，不机械催回原窗口 |
| 用户反驳或改口 | 及时更新理解，撤销不适用的候选与路标内容 |
| 用户明确说“停”“先安静” | 声音和主动发言都按要求停止；状态清楚可恢复 |
| 主力 AI 正在发声，或麦克风听到回声 | 不形成自动互相回应的循环；不把所有声音都归为用户 |
| 中途断线、刷新页面或重连 | 不重复旧消息、旧工具结果和过期声音；会话归属正确 |
| 蓝牙设备断开，或在空闲时突然开口 | 输入输出能恢复或清楚报错，不出现界面显示正常而实际失去收音 |
| 结束后再次打开本场讨论 | 能恢复主题和未解决点，建议与用户决定仍有区别 |

可直接参考已有故障入口：[Coopanion 蓝牙/麦克风问题](https://github.com/Pal-AI-Lab/Coopanion/issues/203)、[Pipecat 重连后重复结果](https://github.com/pipecat-ai/pipecat/issues/6301)、[Pipecat 系统指令未传到 Gemini](https://github.com/pipecat-ai/pipecat/issues/6285)、[LiveKit 误打断状态](https://github.com/livekit/agents/issues/7063)、[N.E.K.O. 运行中关闭截图仍触发兜底](https://github.com/Project-N-E-K-O/N.E.K.O/issues/3419)。这些是检查线索，接手时核查当前版本和修复，不据此认定所选版本一定有同样问题。

## 6. 给实现保留的自由与必须保持的约定

目录、语言、数据库、事件传输和部署方法沿用选定底座。无需为了“快嘴慢脑”建立两套独立模型系统，也无需为了会话记忆先引入图数据库。

各模块只需保持可替换的概念边界：**输入事件 → 当前会话理解 → 候选参与内容 → 是否交付 → 声音和桌面表现**。这可以存在于同一个程序中，不要求拆成多个服务。

至少保留六项一致约定：会话身份、说话者来源、当前交谈对象、状态修订、取消信号、真实播放状态。后续换模型、声音或主力 AI 入口时，围绕这些约定接入。

付费云端模型可作为正常方案，按实际质量、响应和费用选择。账户产品订阅不自动等于可调用 API；所需配置通过本地配置或环境变量提供。屏幕和声音采集范围由当前会话及实际开关决定，暂停后所有后续阶段都要遵守最新状态。

## 7. Claude 首次应交付什么

首次开发交付应包含：**选定并实际启动的底座、一个真实中文语音回合、主力 AI 上下文接入的证据，以及下一处明确改动。** 条件足够时继续贯通阶段 B、C，不停在路线图上。

若受设备、账户或目标入口限制，列出已经完成的独立工作、可重现的阻塞证据，以及用户只需补充的最小信息。不要用假消息播放的录屏代替真实三方链路的完成声明。

## 8. 后续交给 TPC 或其他开发者

本轮先由 Claude 贯通第一条可运行链路。每次交付同时更新一页交接记录，写明：采用的上游版本、启动方式、当前模块入口、已通过场景、真实与模拟部分、待解决问题。

之后可以把独立事项交给 TPC，例如第二个主力 AI 适配器、另一条中文声音对照或桌面表现优化。以 Claude 已经跑通的约定为依据，按模块接续；当前不预设 TPC 的技术能力，也不要求双方各自重建一套底座。

## 9. 来源与证据范围

本方案基于 2026-10-22 完成的伴生开源研究：58 个项目说明、30 份源码/设计/许可文件，以及 17 条深入复核的 Issue。表中链接提供直接复查入口。

前期完成的是资料和静态代码核查，没有项目运行与声音基准。安装时以实际选定提交的说明、许可、依赖和模型条款为准，记录差异后继续实施。原有完整报告用于需要时的定向补查，本方案已经包含首轮开发所需的目标、优先级与验收标准。
