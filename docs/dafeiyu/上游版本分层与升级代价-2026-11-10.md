# 上游版本分层与升级代价（实测）

> 2026-11-10。回答一个问题：**把底层换到上游最新的 `ccch1mneyyy/dsh-Go` v1.0.14，代价是多少。**
>
> 本文所有数字都是当天实测算出来的，不是估计。末尾写了怎么复现。看不懂某条数字就回去跑一遍，不要凭印象改。

## 0. 结论先说

我们不是「落后 10 个版本」，我们是 **v1.0.4 的一个 fork**。上游从 v1.0.4 到 v1.0.14 走了 1207 个提交、改了 2671 个文件，跟我们自己的改动撞了 **44 个文件**。

所以「换成 v1.0.14」不是一件可以一刀否掉的事，它是四件代价差一个量级的事。分档看第 3 节。

## 1. 四层套娃，每一层都有出处

| 层 | 是什么 | 出处 |
|---|---|---|
| ① 官方内核 | `@deepseek-ai/dsh` **0.2.1-rc.4** | `runtime/build-runtime.sh` 的 `DSH_VERSION` 默认值 |
| ② 上游壳 | `ccch1mneyyy/dsh-Go` | 我们的树就长在它的 **v1.0.4** 上（第 2 节有证明） |
| ③ 我们的魔改 | 6 个内置插件 + 手机原生六项 + 墙/姐妹/预判/随机器 | `app/assets/engine/plugins/`、`app/android/.../phone/`、`loop/` |
| ④ 构建基线 | `fish-build-N` | 出包在 `aozhenyu666-cmyk/test` 的 release |

**别把这三个版本号焊成一套**：内核是 `0.2.1-rc.4`，壳是 `1.0.4`，构建基线是 `fish-build-42`。它们分别属于不同的层，互相不同步是正常的。

## 2. 我们确实在 v1.0.4 上（证明）

用 GitHub 树 API 拿 v1.0.4 的完整文件清单，跟我们本地逐文件比对：

| 核什么 | 实测 |
|---|---|
| 我们覆盖 v1.0.4 的 `app/lib`+`app/android` 文件 | **1177 / 1177，100%** |
| 我们自己的新增文件 | 133 个（android +117、lib +16） |
| 我们相对 v1.0.4 的差异 | 180 个（133 新 + 47 改） |
| 我们锁的引擎 | `dsh-0.2.1-rc.4`，**与 v1.0.4 锁的同一个** |
| 我们的 10 个补丁 | 与 v1.0.4 的 10 个**逐名对应** |
| 我们自己的引擎补丁 | **0 个** |
| 上游 `app/assets/engine/plugins` | **0 个**（v1.0.4 / v1.0.10 / v1.0.14 全为 0） |
| 上游 `BuiltinPluginGuest.kt` | **不存在**（两个版本都没有） |

两条要紧的推论：

1. **引擎层和补丁层我们一行没自己写**，全部继承自 v1.0.4。所以这两层可以整体换掉，没有要抢救的自研资产。
2. **内置插件机制、39 个插件 JS、六项原生能力，上游一次都没碰过。** 换壳不会覆盖它们，只会覆盖上游自己那部分。

`app/pubspec.yaml` 里的 `1.0.4+1` 不是随手写的，文件清单独立证实了它。

## 3. 四档改动，代价不是一个量级

| 档 | 改什么 | 实测代价 | 可逆 | 拿到什么 |
|---|---|---|---|---|
| **T0** 只升补丁 | `runtime/patches/` 10 → 55 | 自有修改 0，冲突 0；45 个新增里 32 个纯加法，13 个要先换 1 个补丁 | ✅ 可回退 | 45 个上游 bug 修复，其中 1 个（投影缓存跨进程回写）行为真的变了 |
| **T1** 升引擎 | → `0.2.2-rc.1`，补丁 → 121 | Dart RPC 层 37 处版本耦合、302 个引擎包全换版本；**插件侧已查清，风险低** | ❌ 不可逆 | 新引擎 + 121 补丁 |
| **T2** merge 壳 | `app/lib`+`app/android` 跟到 v1.0.14 | 2671 个上游改动，**44 个冲突文件** | ⚠️ 勉强 | 多任务手机操控、ML Kit OCR、扫码配对、Live2D、视频 |
| **T3** 侧载 APK | 装官方 arm64 包 | 插件和配置全丢 | ❌ | — |

### T0 是最划算的一档

v1.0.14 的 `runtime/patches/pins.json` 里，**55 个补丁登记了 `0.2.1-rc.4`**（我们现在跑的引擎），另外 66 个只挂在 `0.2.2-rc.1` 下（另有 3 个还登记了 `0.2.1-rc.2`）。我们的 10 个补丁**全部**在这 55 个里面，所以引擎一个字节都不用动。

**45 个可以新增，但不是「纯加法」，实测分成两段：**

- **32 个是纯加法**：`before` sha256 精确等于我们当前打完后缀的产物，接上去就行。
- **13 个必须先换一个补丁**：`zzz-title-cache-refresh.diff` 上游版在 rc.4 上的产物是 `f980fc8d8a`，我们是 `6b0e64cd9b`。这 13 个（`zzzzzz-session-deletion`、`zzzzzzz-input-recovery`、`zzzzzzz-jsonl-root-check-retry`、`zzzzzzz-query-open-retry`、`zzzzzzzz-model-defaults`、`zzzzzzzz-schedule-authorization`、`zzzzzzzzz-developer-header-lookup`、`zzzzzzzzz-materialize-temp`、`zzzzzzzzz-prompt-admission`、`zzzzzzzzz-session-event-admission`、`zzzzzzzzz-session-id-membership`、`zzzzzzzzz-tool-history-lookup`、`zzzzzzzzz-workspace-domain-close`）在链上都排在这个补丁之后，不换就卡住。换成上游版后 **45/45 全部解锁**（已模拟验证）。

**换成上游版之后，10 个老补丁里 9 个在 rc.4 上产物字节完全相同**（`fs-create-exclusive`、`plugin-manager-active-run-guard`、`route-guard`、`zz-direct-runtime`、`zzz-config-editor-path`、`install-log-redaction`、`zzzz-plugin-config-readability`、`zzzzz-plugin-config-bundles`、`plugin-manager-cancel-tree-confirmation`）——上游只是往 diff 里加了两代引擎的条件分支和注释，rc.4 那条分支一行没改。**唯一真正变行为的就是 `zzz-title-cache-refresh`**：上游版在 storage-domain 多改 4 个 hunk、storage-json 多改 1 个 hunk，方向是「刷新冷投影记录时要跨进程回写」。

所以 T0 的真实形态是**整目录替换 `runtime/patches/`（10 → 55）**，代价是「4 个文件的投影缓存/存储逻辑跟着上游改」，可回退（换回来即可），不是零改动。

`pins.json` 的 `before`/`after` sha256 校验是很好的安全网：补丁跟版本对不上，构建直接失败，不会静默坏。**注意它校验的是补丁链的中间状态**——同一文件被多个补丁叠着改时，第二个补丁的 `before` 等于第一个的 `after`（例如 `dsh-plugin-manager` 上 6 个补丁首尾相接）。所以不能只挑自己想要的补丁，链断了就构建挂。

### T1 不可逆，注意三点

- v1.0.11 公告原文：新引擎写入后，**定时任务不保证还能被旧版引擎读回**，不建议退回旧版。
- 升级后 Linux 环境**只保留 `/root`**，`/usr/local`、`/opt` 里的东西要重装。
- 插件兼容性**已经查过了，风险低**（下面两小节是实测，不是推测）。真正的未知不在插件，在壳（Dart RPC 层）——302 个引擎包全部换版本，静态手段筛不出重点，必须实跑。

### T1 插件侧风险：已量化，结论是低

**cordis 4.0.5 → 4.1.0 改了什么**（比 `lib/types/*.d.ts`）：改动集中在 Fiber 内部和 `internal/*` 钩子，不是插件用的公开面。

| 改动 | 内容 | 我们用不用 |
|---|---|---|
| `fiber.d.ts` | `_config` → `rawConfig`/`effectiveConfig`；`store` → `committed`/`provisions`；`_resolveConfig` → `resolveConfig()`；`update()` 返回 `void` → `Awaitable<void>` | 0 命中 |
| `events.d.ts` | `internal/config` 与 `internal/update` 签名全变；新增 `internal/commit`；`once()` 接受 `symbol` | 0 命中 |
| `reflect.d.ts` | `Impl.fiber` → `Impl.ctx` + `uid`/`dependents`/`release`；`notify()` 返回 `Fiber[]` → `void` | 0 命中 |
| `context.d.ts` | 只差一处 `baseUrl?: string` → `string \| undefined` | 无影响 |
| `cordis-effect-dispose-completion.diff` | dispose 循环修健壮性：原来一个 cleanup 抛错就中断、后续全不跑；修后逐个 try/catch、LIFO 全跑完再抛第一个错 | 只对我们有利（23 处 `ctx.effect` 的路由注销不会因为一个失败而漏掉） |

**宿主服务的公开面**（下载两版 npm 包比对 `.d.ts`）。部署的 4 个插件实际只调了 7 个服务成员，全部两版都有：

`webServer.register`、`tools.register`、`systemPrompt.context`、`agents.list`、`agents.roots`、`llm.listModels`、`llm.stream`

8 个 `inject` 声明的服务名（`agents`/`llm`/`sessionTitle`/`sessions`/`systemPrompt`/`timer`/`tools`/`webServer`/`workspaceRegistry`）在两版里都注册着。`ctx.interval(callback, delay)` 签名没变（timer 1.1.7→1.2.0 只改了 `throttle`/`debounce` 的返回类型，我们没用）。

**唯一一次「消失的成员」命中是假警报**：`titleInput` 在投影缓存里读会话标题，只出现在 `dsh-speak-up/lib/host.js`，而这个插件**已退役不部署**（`BuiltinPluginGuest.kt:77`）。在跑的 4 个插件没有引用。

风险下限：插件在 rc.1 上大概率能直接加载并注册路由。风险上限没排除：`dsh-tools` 的公开成员面从 109 个涨到 118 个、少了 13 个（`run`/`finish`/`presentAs`/`maxParallel`/`requireRuntime` 等），我们**一个都没调**，但这说明工具层内部重构过，工具调用的运行时行为要实跑才知道。

### T3 仍然禁止

侧载官方 APK 会覆盖 `/opt/dsh-app/plugins`，墙、姐妹、预判、随机器和六项原生配置全在里面。这条不松口。

## 6. 两处顺手该收的隐患（都没动）

1. **CI 把版本歧义固化进每次构建**：`.github/workflows/build-dafeiyu-apk.yml:202` 硬编码 `--build-name 1.0.4`。改它会牵连 `app/test/update/version_test.dart` 对 `1.0.0+xxx` 的断言。
2. **应用内更新实际失效**：`app/lib/update/update_config.dart:23` 默认 `updateRepo = 'ccch1mneyyy/dsh-go'`，CI 用 `--dart-define=DSH_UPDATE_REPO=aozhenyu666-cmyk/dsh-Go` 覆盖成我们的 fork，而那个 fork **零 release**。所以不会被推官方包（安全），但也拿不到更新，`fish-build-N` 只能手动换包。

## 7. 贯穿所有档的硬约束

不管选哪档，**真机验收 35 条 + 第四轮 18 条仍然全空**。升级只会让待验项更多——上游每一版自己都写「这一版没有在真机上验证过」。

在真机一条证据都没有的前提下动引擎或动手机操控核心，风险不在于改错，而在于**改错了没人能发现**。

## 8. 怎么复现这些数字

```powershell
# 上游某版本完整文件清单（含 blob sha，可用来做内容比对）
Invoke-RestMethod "https://api.github.com/repos/ccch1mneyyy/dsh-Go/git/trees/v1.0.14?recursive=1" -Headers @{'User-Agent'='x'}

# 上游两个版本之间的补丁与引擎版本分布
Invoke-WebRequest 'https://raw.githubusercontent.com/ccch1mneyyy/dsh-Go/v1.0.14/runtime/patches/pins.json' -UseBasicParsing

# 本地某个文件相对 v1.0.4 是否被改过：算 git blob sha 跟上游 sha 比
git -C <repo> hash-object -- <相对路径>

# 冲突面 = (上游 v1.0.4→v1.0.14 改过的文件) ∩ (我们相对 v1.0.4 改过的文件)
```

### 补丁链与插件兼容性怎么复核

`pins.json` 的结构是 `patches[补丁名][引擎版本][文件路径] = { before, after }`。判断某个补丁能不能单拿，就是看它的 `before` 是否等于当前状态的 sha256：

```powershell
# 1. 算出我们打完后缀之后的 per-file 状态（读我们自己的 runtime/patches/pins.json）
# 2. 从上游 55 个 rc.4 补丁里逐个试：before 对上当前状态才准加，加了之后状态更新为 after
# 3. 反复迭代到不动点，剩下加不动的就是被别的补丁卡住的
# （PS 5.1 的 ConvertFrom-Json 处理 package-lock/pins 这类大 JSON 会报重复键，用 node 读）

# cordis 两版 API 面：npm 上是公开包，直接下 tarball 比 lib/types/*.d.ts
https://registry.npmjs.org/@deepseek-ai/cordis/4.0.5
https://registry.npmjs.org/@deepseek-ai/cordis/4.1.0
# → dist.tarball，解包后 diff package/lib/types/ 下的 .d.ts

# 宿主服务面：8 个包都公开，两版各下一份比 .d.ts
https://registry.npmjs.org/@deepseek-ai/dsh-host-webserver/-/dsh-host-webserver-0.2.1-rc.4.tgz
https://registry.npmjs.org/@deepseek-ai/dsh-host-webserver/-/dsh-host-webserver-0.2.2-rc.1.tgz
# 涉及 dsh-host-webserver / dsh-tools / dsh-session / dsh-agent / dsh-llm /
#      dsh-system-prompt / dsh-session-title / dsh-workspace / cordis-plugin-timer
```

比 `.d.ts` 时按 `^\s{1,8}(?:readonly\s+)?(名字)\s*\??\s*[:(<]` 抽成员名，两版取差集。这个抽法有噪声（会把类型别名的字段也算进去），所以**只把差集当线索，逐个用 grep 回去确认我们有没有真调**。

注意两个坑：
- `git rev-list --max-parents=0 HEAD` 会返回**两个** root（`2b57946d`、`8fc97768`，后者是被 merge 进来的孤儿树），拿它当导入基线算 diff 会算错。判断基线要用第 2 节的文件清单法，不要用 git 历史。
- `aozhenyu666-cmyk/test` **不是 fork**（`fork:false, parent:null`），不能用 GitHub 的 compare 跟上游做树对比；`compare` API 还会在 300 个文件处截断。
