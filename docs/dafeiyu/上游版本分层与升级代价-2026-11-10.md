# 上游版本分层与升级代价（实测）

> 2026-11-10。回答一个问题：**把底层换到上游最新的 `ccch1mneyyy/dsh-Go` v1.0.14，代价是多少。**
>
> 本文所有数字都是当天实测算出来的，不是估计。末尾写了怎么复现。看不懂某条数字就回去跑一遍，不要凭印象改。

## 0. 结论先说

我们不是「落后 10 个版本」，我们是 **v1.0.4 的一个 fork**。上游从 v1.0.4 到 v1.0.14 走了 1207 个提交、改了 2671 个文件，跟我们自己的改动撞了 **44 个文件**。

所以「换成 v1.0.14」不是一件可以一刀否掉的事，它是四件代价差一个量级的事。分档看第 3 节。

## 1. 四层套娃，每一层都有出处

| 层 | 是什么 | 出处 |
|---|---|---|
| ① 官方内核 | `@deepseek-ai/dsh` **0.2.1-rc.4** | `runtime/build-runtime.sh` 的 `DSH_VERSION` 默认值 |
| ② 上游壳 | `ccch1mneyyy/dsh-Go` | 我们的树就长在它的 **v1.0.4** 上（第 2 节有证明） |
| ③ 我们的魔改 | 6 个内置插件 + 手机原生六项 + 墙/姐妹/预判/随机器 | `app/assets/engine/plugins/`、`app/android/.../phone/`、`loop/` |
| ④ 构建基线 | `fish-build-N` | 出包在 `aozhenyu666-cmyk/test` 的 release |

**别把这三个版本号焊成一套**：内核是 `0.2.1-rc.4`，壳是 `1.0.4`，构建基线是 `fish-build-42`。它们分别属于不同的层，互相不同步是正常的。

## 2. 我们确实在 v1.0.4 上（证明）

用 GitHub 树 API 拿 v1.0.4 的完整文件清单，跟我们本地逐文件比对：

| 核什么 | 实测 |
|---|---|
| 我们覆盖 v1.0.4 的 `app/lib`+`app/android` 文件 | **1177 / 1177，100%** |
| 我们自己的新增文件 | 133 个（android +117、lib +16） |
| 我们相对 v1.0.4 的差异 | 180 个（133 新 + 47 改） |
| 我们锁的引擎 | `dsh-0.2.1-rc.4`，**与 v1.0.4 锁的同一个** |
| 我们的 10 个补丁 | 与 v1.0.4 的 10 个**逐名对应** |
| 我们自己的引擎补丁 | **0 个** |
| 上游 `app/assets/engine/plugins` | **0 个**（v1.0.4 / v1.0.10 / v1.0.14 全为 0） |
| 上游 `BuiltinPluginGuest.kt` | **不存在**（两个版本都没有） |

两条要紧的推论：

1. **引擎层和补丁层我们一行没自己写**，全部继承自 v1.0.4。所以这两层可以整体换掉，没有要抢救的自研资产。
2. **内置插件机制、39 个插件 JS、六项原生能力，上游一次都没碰过。** 换壳不会覆盖它们，只会覆盖上游自己那部分。

`app/pubspec.yaml` 里的 `1.0.4+1` 不是随手写的，文件清单独立证实了它。

## 3. 四档改动，代价不是一个量级

| 档 | 改什么 | 实测代价 | 可逆 | 拿到什么 |
|---|---|---|---|---|
| **T0** 只升补丁 | `runtime/patches/` 10 → 55 | 自有修改 0，冲突 0 | ✅ 可回退 | 45 个上游 bug 修复 |
| **T1** 升引擎 | → `0.2.2-rc.1`，补丁 → 121 | Dart RPC 层 37 处版本耦合、插件 API 要实测 | ❌ 不可逆 | 新引擎 + 121 补丁 |
| **T2** merge 壳 | `app/lib`+`app/android` 跟到 v1.0.14 | 2671 个上游改动，**44 个冲突文件** | ⚠️ 勉强 | 多任务手机操控、ML Kit OCR、扫码配对、Live2D、视频 |
| **T3** 侧载 APK | 装官方 arm64 包 | 插件和配置全丢 | ❌ | — |

### T0 是最划算的一档

v1.0.14 的 `runtime/patches/pins.json` 里，**55 个补丁登记了 `0.2.1-rc.4`**（我们现在跑的引擎），另外 121 个挂在 `0.2.2-rc.1` 下。也就是说上游替我们在这条引擎线上继续维护了 45 个修复，可以白拿，引擎一个字节都不用动。

`pins.json` 的 `before`/`after` sha256 校验是很好的安全网：补丁跟版本对不上，构建直接失败，不会静默坏。这比「合错了但能启动」安全得多。

### T1 不可逆，注意三点

- v1.0.11 公告原文：新引擎写入后，**定时任务不保证还能被旧版引擎读回**，不建议退回旧版。
- 升级后 Linux 环境**只保留 `/root`**，`/usr/local`、`/opt` 里的东西要重装。
- 我们插件里有 43 处 `ctx.get/inject/effect/on`；v1.0.14 恰好有个 `cordis-effect-dispose-completion.diff` 动的是 `ctx.effect` 的语义。**这条不实测不能假设兼容。**

### T3 仍然禁止

侧载官方 APK 会覆盖 `/opt/dsh-app/plugins`，墙、姐妹、预判、随机器和六项原生配置全在里面。这条不松口。

## 4. T2 的 44 个冲突文件

没有一个是我们新增的文件——**我们的新增文件跟上游新增文件零路径撞车**。冲突全落在双方都改过的存量文件上，分布很不随机：

| 区域 | 冲突数 | 是哪些 |
|---|---|---|
| `android/.../phone/` | 7 | `PhoneA11yService`、`A11yKeeper`、`A11yProbe`、`PhoneControl`、`PhoneCore`、`PhonePrompts`、`PhoneToolCatalog` |
| `android/.../runtime/` | 6 | `DshProcess`、`DshService`、`RuntimeController`、`SafeMode`、`L2sMigration`、`ManagedSkillInstaller` |
| l10n | 8 | `app_*.arb`、`phone_*.arb`、`gen/app_localizations*` |
| `lib/` 其余 | 16 | `home_shell`、`chat_list`、`chat_state`、`web_home`、`pet_stage`、`pet_overlay_bridge`、`phone_channel`、`app_rules_page`、`phone_control_screen`、`ui_skill`、`update_config`、`app.dart`、`diagnostics_*` |
| Gradle / Manifest | 4 | `build.gradle.kts` ×2、`settings.gradle.kts`、`AndroidManifest.xml` |

其余 3 个在 `res/values*/phone_a11y_strings.xml` 和两个 `test/` 下。

### 热点文件的实测改动量（上游 v1.0.4 → v1.0.14）

| 文件 | 行数 | 上游变动行 |
|---|---|---|
| `phone/PhoneCore.kt` | 662 → **1333** | 973 |
| `phone/PhoneControl.kt` | 645 → **1114** | 681 |
| `runtime/RuntimeController.kt` | 861 → 1145 | 536 |
| `state/chat_state.dart` | 1875 → 2134 | 407 |
| `ui/shell/home_shell.dart` | 435 → 586 | 275 |

**这才是真正的代价，而且很讽刺**：上游 v1.0.11~v1.0.14 的重仓投入（多任务手机操控、按截图坐标操作、ML Kit OCR、后台屏实时预览）全部砸在我们也重仓的同一批文件里，`PhoneCore.kt` 直接翻倍。这类冲突不能靠自动合，只能「取上游新文件 → 把我们那几处钩子重新接回去」。

**caveat**：44 是**文件级**冲突数，不是「44 处手工改」。行级只量了上面 5 个，其余 39 个没量。

实测：`mlkit|live2d|伙伴小屋|maxConcurrent|后台任务上限|扫码配对|video_player|小技巧` 在 `app/lib` 下 **0 命中**。

| 版本 | 实质内容 |
|---|---|
| v1.0.10 | 定时任务新建/修改要单独确认 |
| v1.0.11 | **换运行时到 0.2.2-rc.1**；定时任务手动新建免二次确认；网页版改用官方抽屉 |

## 6. 两处顺手该收的隐患（都没动）

1. **CI 把版本歧义固化进每次构建**：`.github/workflows/build-dafeiyu-apk.yml:202` 硬编码 `--build-name 1.0.4`。改它会牵连 `app/test/update/version_test.dart` 对 `1.0.0+xxx` 的断言。
2. **应用内更新实际失效**：`app/lib/update/update_config.dart:23` 默认 `updateRepo = 'ccch1mneyyy/dsh-go'`，CI 用 `--dart-define=DSH_UPDATE_REPO=aozhenyu666-cmyk/dsh-Go` 覆盖成我们的 fork，而那个 fork **零 release**。所以不会被推官方包（安全），但也拿不到更新，`fish-build-N` 只能手动换包。

## 7. 贯穿所有档的硬约束

不管选哪档，**真机验收 35 条 + 第四轮 18 条仍然全空**。升级只会让待验项更多——上游每一版自己都写「这一版没有在真机上验证过」。

在真机一条证据都没有的前提下动引擎或动手机操控核心，风险不在于改错，而在于**改错了没人能发现**。

## 8. 怎么复现这些数字

```powershell
# 上游某版本完整文件清单（含 blob sha，可用来做内容比对）
Invoke-RestMethod "https://api.github.com/repos/ccch1mneyyy/dsh-Go/git/trees/v1.0.14?recursive=1" -Headers @{'User-Agent'='x'}

# 上游两个版本之间的补丁与引擎版本分布
Invoke-WebRequest 'https://raw.githubusercontent.com/ccch1mneyyy/dsh-Go/v1.0.14/runtime/patches/pins.json' -UseBasicParsing

# 本地某个文件相对 v1.0.4 是否被改过：算 git blob sha 跟上游 sha 比
git -C <repo> hash-object -- <相对路径>

# 冲突面 = (上游 v1.0.4→v1.0.14 改过的文件) ∩ (我们相对 v1.0.4 改过的文件)
```

注意两个坑：
- `git rev-list --max-parents=0 HEAD` 会返回**两个** root（`2b57946d`、`8fc97768`，后者是被 merge 进来的孤儿树），拿它当导入基线算 diff 会算错。判断基线要用第 2 节的文件清单法，不要用 git 历史。
- `aozhenyu666-cmyk/test` **不是 fork**（`fork:false, parent:null`），不能用 GitHub 的 compare 跟上游做树对比；`compare` API 还会在 300 个文件处截断。
