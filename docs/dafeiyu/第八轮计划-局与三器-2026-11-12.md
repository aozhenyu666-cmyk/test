## 0. 一句话

**AI 不管他想什么，只管节奏。** 节奏由三样东西组成：

- **调度器**：任何事都要先开成一「局」，每局资源有限，到点收局。
- **触发器**：局里高频给出具体动作，脑子空了也有下一步。
- **验收器**：收局时查产出物，判得比现在更准、更难糊弄。

两条鱼和墙都围着「局」转：小鱼偶尔开局，大鱼在局里陪他想、在局外自己想，墙执行预算并做最后裁决。

## 1. 原则

### 1.1 过量原则（取乎其上，仅得其中）

对**系统**：

- 所有强度类参数的默认值取「偏高」那一档：触发频率、验收严格度、每天局数。用户只能往下调，往下调有门槛（见 T2）。往上调随时可以，没有门槛。
- 晨间计划的任务量按用户报的 1.3 倍排，多出来的部分标成「加局」，做不完不扣分，做完了加分。

- 每个工单分「最小交付」和「超额项」。最小交付缺一条，工单算未完成；超额项至少做一半，没做的逐条写原因。

- 第七轮 §1 的十二条工作纪律全部继续有效，本轮不再重复。

## 2. 总架构

```
                 ┌──────────── 设定（作息模板、固定工作时间、资源上限） ────────────┐
                 │                                                                  │
晨间计划 ──→ 调度器：局队列 ──→ 开局 ──→ 局内：触发器高频出指令 ──→ 收局 ──→ 验收器
                 ↑                │                 │                            │
          无局超时自动开局     小鱼偶尔开局     大鱼陪想 / Gemini Live          墙裁决
                 │                                                                  │
                 └────────────── 记忆库（局、触发、产出、判定、两鱼的看法） ←────────┘
                                          ↑
                                   大鱼暗思考（局外）
```

**「局」** 是唯一的核心对象：

| 字段 | 含义 | 例 |
|---|---|---|
| `what` | 一句话 | 定下情绪池要不要做 |
| `kind` | 局型 | 思考 / 执行 / 外出 / 休息 / 设计 |
| `dept` | 四大部归属 | 谋划思考 |
| `budget` | 有限资源（不止时间） | 25 分钟；最多展开 2 个方案 |
| `deliverable` | 收局必须交的东西及形态 | 一句结论，**手写拍照** |
| `cadence` | 触发间隔 | 每 4 分钟 |
| `onTimeout` | 到点怎么办，写死 | 强制收局；无产出记「空局」 |
| `opener` | 谁开的局 | 晨间计划 / 用户 / 小鱼 / 无局超时 |

## 3. D 组：数据库与记忆

### D1 局的数据库

把局、触发、产出、判定落成一套表，**所有三器的状态都从这里读写**，不再散在多个 json 文件里。

建议放在已有的 `fish-memory.sqlite` 里，通过 `dsh-go-memory` 的迁移机制加表（照它已有的迁移写法）。如果现状核对发现这样做不合适，在回报里写原因再另建库。

建议的表（字段为最低要求，可加不可减）：

| 表 | 一行是什么 | 关键字段 |
|---|---|---|
| `bouts` | 一局 | id, what, kind, dept, budget_json, deliverable_json, cadence_s, opener, planned_at, opened_at, closed_at, close_reason, status |
| `triggers` | 一次触发 | id, bout_id, at, type（回想/精简/预判/提问/动作/检查）, modality（说/写/拍/做）, text, channel, answered_at, answer_ref, skipped_reason |
| `deliverables` | 一份产出物 | id, bout_id, at, form（文本/照片/文件/语音）, ref, extracted_text, size |
| `verdicts` | 一次判定 | id, bout_id, layer（代码/判官/墙）, result, scores_json, quotes_json, model, at |
| `throttles` | 一次降频 | id, bout_id, at, from_s, to_s, reason, approved |
| `day_settings` | 一天的作息快照 | date, template_id, work_blocks_json, limits_json |

规则：

1. 所有写入走一个模块（建议 `lib/bouts.js`），其他模块不直接写 SQL。
2. 所有 SQL 固定文本 + 参数绑定（`topics.js` 已有的规矩）。
3. 时间一律存毫秒时间戳；日期键一律北京时间 `YYYY-MM-DD`（依赖第七轮 P0-2）。
4. 账本 `ledger.jsonl` 继续写，作为审计流水；数据库是查询用的状态。两者冲突时以账本为准，并提供从账本重建数据库的脚本。

**最小交付**

- [ ] 迁移脚本 + 回滚说明
- [ ] `lib/bouts.js` 的增删查改 + 测试 ≥ 30 条
- [ ] 从账本重建数据库的脚本 + 测试（重建结果与在线写入结果逐行一致）
- [ ] 旧数据（第七轮的时间块、四段提交）迁入的测试

**超额项**

- [ ] 周报脚本改为从数据库出数：每天局数、空局率、触发应答率、降频次数、各局型验收通过率
- [ ] 数据库体积和查询耗时的基准脚本（模拟一年的数据量）
- [ ] 导出到笔记库 `大肥鱼/局/日期.md`，Obsidian 里可以直接看每一局

### D2 两条鱼的记忆分层

现在两条鱼共用一份记忆，这是她们越来越像的原因之一：看到的东西一样，说出来的自然也一样。

分三层：

| 层 | 内容 | 谁能读 | 谁能写 |
|---|---|---|---|
| **共享事实** | 他是谁、发生过什么、局的记录 | 两条鱼 | 代码（从账本和局表抽取） |
| **各自的看法** | 她对某件事的判断、对他的理解、她的立场史 | 主要是自己；对方只能读摘要 | 各自 |
| **大鱼的问题队列** | 暗思考产出的待追问问题（F4） | 大鱼 | 大鱼暗思考 |

借鉴：

- `dsh-soul`：节点类型（约束 / 决策 / 产物 / 进度），以及「取代」「矛盾」两种边。她改变看法时，旧看法不删，连一条「被取代」，可以回看她是怎么改的。
- `memory-system`：久没被提起的看法逐级压短，被提起时恢复原文。
- `dsh-xingxi`：检索先给索引，再按需取原文。

**最小交付**

- [ ] 「各自的看法」的表和读写接口，测试 ≥ 20 条（含对方只能读摘要、取代关系、衰减）
- [ ] 两条鱼的注入内容各自不同：同一时刻两边的注入文本，共享层之外的重合率要低于阈值（测试断言）
- [ ] 看法的衰减与恢复

**超额项**

- [ ] 面板上「她们怎么看你」：两边对同一件事的看法并排显示，看得出分歧
- [ ] 分歧检测：同一对象上两边看法相反时，记一条，作为大鱼下次的讨论素材

### D3 记忆的调用方式

大鱼要「调用过去的记忆，然后开始分析讨论」，前提是调得出来、调得准、不撑爆上下文。

- 常驻注入只放索引（今天几局、哪几件没收尾、她最近改过的 3 个看法），不放正文。
- 正文按需取：`recall(关键词 | 对象 | 日期)`，返回带编号的片段，每次 ≤ 1500 字符。
- **引用要带编号**：大鱼在分析里提到过去的事，必须带上片段编号，代码校验编号存在。编号不存在的引用会被剥掉，并记一条「虚构引用」。

**最小交付**

- [ ] `recall` 工具 + 测试 ≥ 15 条
- [ ] 引用编号校验 + 测试（假编号会被剥掉并记账）
- [ ] 注入只放索引，过第七轮 P0-3 的预算

**超额项**

- [ ] 「虚构引用率」进周报
- [ ] 召回质量的离线评测：从账本里取 50 个真实问题，人工标注应该召回什么，跑召回率

## 4. W 组：墙从背景板变成控制塔

现在墙只在面板角落里占一块审计。本轮让它成为**打开面板时的第一屏**：此刻在哪一局、还剩多少、下一次触发什么时候、什么在等验收。

墙的每一句话仍由代码模板生成，**不经过模型**（第七轮 A3 的原则不变）。

## 5. F 组：两条鱼

### F1 小鱼：少催，偶尔调度

**现状问题**：天天催，催的内容和知识库无关。

**改成**：

1. 催进度这件事从小鱼身上拿掉。进度由触发器负责，按局的节奏走，不由小鱼开口。
2. 小鱼的新职责是**偶尔从知识库里挑一件事来开局**。例如：笔记库里有一篇三天没动的笔记，或者有一个停放了的挂载卡，或者有一个他提过但没开过局的想法。她用自己的口吻提出来，附一个开局提议（五项都填好），他可以接、改、拒。
3. 频率有硬上限：每天 ≤ 2 次，工作时间段内不打断进行中的局，只在无局时出现。
4. 她提的局被接受、并且验收通过，记一次「调度命中」。命中率进 `brain.js` 的学习，决定她下次从哪类素材里挑。

**最小交付**

- [ ] 小鱼的发球类型里移除催进度类，测试断言
- [ ] 「从知识库挑一件事」的选题函数 + 测试 ≥ 12 条（素材来源、去重、近 7 天提过的不再提）
- [ ] 开局提议的格式校验（五项缺一不发）
- [ ] 频率上限与「不打断进行中的局」的测试

**超额项**

- [ ] 调度命中率进周报
- [ ] 他拒绝时可以说一句原因，原因进她对他的看法（D2）

### F2 大鱼：照着 Claude 的样子重塑

**现状问题**：和小鱼说话几乎没区别。

**目标形象**（行为层面的描述，写进她的人格卡）：

| 特征 | 具体表现 |
|---|---|
| 先想清楚再说 | 回复前先形成自己的判断（见 F3 的先判后答） |
| 直接 | 先说结论，再说理由；不铺垫，不客套 |
| 有依据 | 提到过去的事带记忆编号；没有记录就说「我没有这方面的记录」 |
| 承认不确定 | 区分「我确定」「我倾向于」「我不知道」，并说出什么信息会改变她的判断 |
| 会不同意 | 他说错了直接指出错在哪；他坚持但没给新理由时，她维持原判并说明为什么 |
| 只问关键问题 | 一次最多一个问题，问的是答案一变、结论就会变的那个 |
| 会改主意 | 有新证据时明确说「我之前判断 X，现在看是 Y，因为……」 |
| 不讨好 | 不说「你说得对」「好问题」「你真棒」作为开头；不重复他的话来显得在听 |

她和小鱼的分工也重新写清：小鱼是朋友，管情绪和陪伴，偶尔调度；大鱼是谋士，管分析、讨论、验收前的把关，以及局外的暗思考。

**最小交付**

- [ ] 大鱼人格卡重写，按上表逐项落成可执行的说话规则
- [ ] 一份 30 条的对话评测集：每条是一个情境 + 他说的话 + 对她回复的检查项（例：不能以「你说得对」开头；必须带至少一个记忆编号；问题数 ≤ 1）。检查项由代码判定
- [ ] 两条鱼的风格区分测试：同一情境下两边各回复 10 次，用简单特征（平均句长、问句比例、记忆引用数、语气词频率）做区分，断言可区分

**超额项**

- [ ] 评测集扩到 100 条，接进 CI，每次改人格卡都跑一遍，通过率下降就失败
- [ ] 她每周写一段「我这周对你的判断变了哪些」，带编号，进笔记库

### F3 反顺从：代码层的约束

「不要高度顺从」不能只靠提示词劝。以下机制全部在代码里：

1. **先判后答**：大鱼回复前先输出一段不给他看的结构化判断：`{ 我的看法, 把握程度, 什么会让我改变看法 }`。正式回复生成后，代码比对两者：回复里的立场和这段判断相反，且他这一轮没有提供新信息（用第七轮 A1 的证据规则判），就重写一次。
2. **开头黑名单**：「你说得对」「确实」「好问题」「没错」等开头命中就重写。
3. **同意率监测**：沿用第七轮 A1 的 `agreementRate`。超过阈值时注入一行提醒。
4. **立场账本**：沿用第七轮 A1，硬立场在到期前她没有修改的工具。
5. **追问有质量线**：她的问题必须引用当前局的某个字段，或某条记忆编号。空泛的「你觉得呢」「还有吗」会被拦下重写。

**最小交付**

- [ ] 先判后答的生成与比对 + 测试 ≥ 15 条
- [ ] 开头黑名单 + 测试
- [ ] 追问质量线 + 测试
- [ ] `fake-user.test.mjs` 加三个剧本：他坚持一个明显错误的判断 6 轮；他用情绪施压要她认同；他给出真正的新证据。前两个剧本她必须维持判断，第三个必须改

**超额项**

- [ ] 「先判后答」的判断记录进 D2 的看法层，长期看她的判断准不准
- [ ] 每周统计她被重写的次数和原因，进周报

### F4 大鱼的暗思考

收编第七轮 B2。第七轮 B2 的硬边界全部保留（不依赖用户消息、不读屏幕文字、不直接发消息、没有变化就不产出）。

本轮补的是**产物的去向**：

| 产物 | 去向 |
|---|---|
| 关联：两件事之间的联系 | D2 的看法层 |
| 缺口：某件事缺了什么信息 | 大鱼的问题队列，下次合适的时候追问 |
| 局的复盘：这一局为什么空了 / 为什么过了 | D2；连续 3 次同类空局时，生成一条调整建议给 W3 的设定页（只是建议，用户确认才生效） |
| 明天的局建议 | 晨间计划的候选 |

频率：工作时间段外每 2 小时一次，工作时间段内只在收局后跑一次。每天上限沿用第七轮。

**最小交付**

- [ ] 四类产物的生成、校验（每条必须能解析到证据编号）和去向接线，测试 ≥ 20 条
- [ ] 问题队列：大鱼每次开口前取队首，判断当下是否合适问；合适就问，问过出队
- [ ] 源码扫描测试：暗思考没有任何消息出口

**超额项**

- [ ] 问题队列在面板上可见，他可以自己点一条来答
- [ ] 暗思考的花费（token 数）进周报

## 6. S 组：调度器

### S1 作息模板与固定工作时间

用户会固定每天的工作时间。调度器的第一步是把一天切成几种时段：

| 时段 | 规则 |
|---|---|
| 工作时段 | 必须在局里；无局上限 5 分钟 |
| 非工作时段（清醒） | 允许无局；无局上限 30 分钟，到点由小鱼提议或自动开休息局 |
| 吃饭 | 只允许休息局 |
| 深夜 | 沿用深夜锁 |

模板来自 W3 设定页；每天早上按模板生成当天的 `day_settings` 快照，当天不变（改动明天生效，改紧除外）。

**最小交付**

- [ ] 模板 → 当日快照的生成 + 测试 ≥ 12 条（工作日/休息日、跨零点、模板缺失时用默认）
- [ ] 各时段的无局上限测试

**超额项**

- [ ] 节假日自动识别（只做法定节假日表，不联网）
- [ ] 例外日：生病、出差一键切换，只保留深夜锁，记账

### S2 局的生命周期

```
planned ──开局──→ open ──到点/交付──→ closing ──验收──→ passed / partial / failed / empty
   │                │
   └──作废──→ void   └──用户提前收局（必须交产出）──→ closing
```

1. **开局**：晨间计划排好的局到点自动开；用户可以手动开；小鱼可以提议开；无局超时自动开。
2. **预算**：时间到了强制进 closing，不商量。非时间资源（方案数、展开数）由触发器在局内检查。
3. **延长**：每局最多延长 1 次，最多原预算的 50%，延长必须说一句理由。每天延长总次数有上限（默认 3）。
4. **空局**：到点没有任何产出，记 `empty`。空局本身也是数据，进大鱼的复盘。
5. **加局**：晨间计划里 1.3 倍的多出部分。

**最小交付**

- [ ] 状态机 + 测试 ≥ 30 条（每条边、延长规则、空局、并发时只能有一个 open 局）
- [ ] 晨间计划生成局队列（收编第七轮 A2 的排程函数）
- [ ] 和第七轮 `machine.js` 的全天状态表对接：「在局里」成为一个主状态或叠加层，写清优先级

**超额项**

- [ ] 局的预估校准：同类局的实际用时和预算对比，下次排程时给建议
- [ ] 局队列在当天内的重排（沿用第七轮 A2 的重排额度规则）

### S3 无局状态

**这是「即使我什么都不做，它也有很强的控制力」的落点。**

无局是一种被计时的状态。到上限时，按以下顺序自动开局：

1. 晨间计划里下一个待开的局
2. 小鱼的知识库调度提议（如果今天额度还在）
3. 大鱼问题队列里最重要的一条，开成一个 10 分钟的思考局
4. 一个 10 分钟的「整理局」：产出物是一句「我现在该做什么」

他可以换成别的局，但**不能选择不开局**（工作时段内）。

**最小交付**

- [ ] 无局计时与自动开局顺序 + 测试 ≥ 12 条
- [ ] 工作时段与非工作时段的不同规则

**超额项**

- [ ] 无局时长分布进周报：一天里哪些时段最容易无局

## 7. T 组：触发器

### T1 指令库

触发器每次给出的是**一个具体动作**，不是一句关心。指令分六类：

| 类型 | 例 | 用于 |
|---|---|---|
| 回想 | 「不看笔记，目标是什么？」 | 思考局开局、长时间无应答后 |
| 精简 | 「一句话，推到哪了？」 | 思考局中段 |
| 预判 | 「下一步你猜会怎样？写下来。」 | 动手之前 |
| 提问 | 「卡住你的是哪一个问题？」 | 连续两次没有进展 |
| 动作 | 「拿笔，写下三条已知条件，拍照交上来。」 | 任何局 |
| 检查 | 「还剩 8 分钟。现在能交什么？」 | 预算剩 1/3 时 |

规则：

1. 指令的**类型和顺序**由代码按局型和当前进度选；指令的**措辞**可以由模型按情境改写，但改写后必须仍然是一个可执行的动作（代码校验：包含动词、包含局内的某个对象、不超过 40 字）。
2. 同一局内同一句指令不重复出现。
3. 思考局的标准序列（收编第七轮 C1、C2）：回想 → 精简 → 预判 → 提问，循环；挂载卡（目标 / 已知 / 中间结论）是思考局的固定附件。
4. 指令库是数据，存在笔记库 `大肥鱼/触发/指令库.md`，用户可以自己加。

**最小交付**

- [ ] 指令选择函数 + 测试 ≥ 25 条
- [ ] 改写后的校验 + 测试
- [ ] 指令库文件的格式、读取、去重
- [ ] 每种局型的默认指令序列

**超额项**

- [ ] 指令效果学习：哪类指令之后他应答最快、产出最好，用 `brain.js` 已有的 Thompson 抽样调整选择概率
- [ ] 用户自定义的指令单独统计效果

### T2 频率与降频

**它高频，我也要能降频。** 但降频不能等于关掉。

| 局型 | 默认间隔 | 最多降到 |
|---|---|---|
| 思考 | 4 分钟 | 8 分钟 |
| 执行 | 10 分钟 | 20 分钟 |
| 设计 | 5 分钟 | 10 分钟 |
| 外出 | 15 分钟 | 30 分钟 |
| 休息 | 不触发 | — |

规则：

1. 降频随时可以说，但必须说一句理由，记进 `throttles` 表。
2. 每局最多降一次；每天降频总次数有上限（默认 4）。
3. 降到下限以下需要在 W3 设定页改，走冷却期。
4. 升频随时可以，没有任何门槛。
5. 连续 3 次触发没应答，不是继续加频，而是换通道（T3）。
6. 他说「用笔写下」这类模态要求时，后续同一局的指令默认采用这个模态。

**最小交付**

- [ ] 频率计算 + 降频规则 + 测试 ≥ 15 条
- [ ] 降频理由进账本，周报里列出最常见的降频理由

**超额项**

- [ ] 应答速度驱动的自适应：他每次都在 30 秒内应答且产出质量高，间隔自动放宽一档（这是唯一不需要他开口的降频）

### T3 通道

| 通道 | 适合 | 备注 |
|---|---|---|
| 通知 | 执行局、外出局 | 最轻 |
| 浮层 | 思考局、设计局 | 复用已有浮层 |
| 语音 | 外出局、骑车时 | 依赖第七轮 B5 |
| Gemini Live | 需要连续追问的思考局 | 鱼负责开局和收局，Gemini 负责局内的高频语音追问 |

**Gemini Live 的接法**：开局时把局的五项和指令序列生成一段背景交给 Gemini（沿用已有的 `gemini_live` 简报机制），说明「每 N 分钟问一次，按这个顺序」。收局时读回复盘（已有机制），复盘内容作为产出物进验收。

**最小交付**

- [ ] 通道选择规则 + 测试
- [ ] 连续未应答时的通道升级
- [ ] Gemini Live 简报里加入局的五项和指令序列

**超额项**

- [ ] 骑车模式：检测到在移动（可用已有的手机现状信号判断，只用加速度或步数，不用定位）时自动切语音

### T4 线下模态：笔写、拍照

他会告诉 AI「用笔写下」。这条路需要：

1. 触发指令里带模态 `write`。
2. 他拍照交上来（相机或图库，**依赖第七轮 P0-1 修好连麦舱误锁**）。
3. 识图模型把照片里的字提取成文本，存进 `deliverables.extracted_text`。
4. 提取结果再进验收器。

**最小交付**

- [ ] 拍照提交入口（面板 + 浮层）
- [ ] 识图提取 + 失败时如实提示「看不清，重拍」
- [ ] 照片时间戳校验：拍摄时间必须在本局开局之后（代码判定）

**超额项**

- [ ] 手写内容自动归入挂载卡对应栏位（目标 / 已知 / 中间结论），用户确认
- [ ] 手写照片按日期归档进笔记库

## 8. V 组：验收器

### V1 三层验收

现在的墙只看物理证据（文件大小、截图时间、使用时长），难糊弄但判不了质量。用户要更强的分析判断力，所以加一层判官。三层各管各的：

| 层 | 判什么 | 能不能被说服 |
|---|---|---|
| **代码层** | 交了没有、格式对不对、时间对不对、字数够不够 | 不能，纯规则 |
| **判官层** | 质量：有没有回答局的 what，推理有没有断，结论有没有依据 | 不能：判官看不到聊天记录，只看产出物、局的五项和评分标准 |
| **墙** | 最后裁决：按一张表把前两层合成结果 | 不能，纯规则 |

墙的合成表例：代码层不过 → 不过；代码层过、判官 ≥ 70 → 过；判官 40–70 → 一半；< 40 → 不过。阈值进 W3 设定。

### V2 判官

1. 独立会话，可单独配模型，默认用比聊天模型更强的那个。
2. 输入只有：局的五项、产出物（文本或提取后的文本）、这类局型的评分标准。**不给聊天记录，不给两条鱼的看法。**
3. 输出严格 JSON：每一条评分项给分，并**引用产出物里的原文**作为依据。引用不是产出物的子串，这一项作废按 0 分。
4. 评分标准是数据，按局型写在笔记库 `大肥鱼/墙/评分标准.md`，用户可以改（改松走冷却期）。

### V3 校准

判官会判错。每周让用户从本周判定里随机抽 5 条，标「判对了 / 判严了 / 判松了」。

- 判官和用户的一致率进周报。
- 一致率连续两周低于 70%，生成一条评分标准调整建议（只是建议）。

**最小交付**

- [ ] 三层验收的接线 + 墙的合成表 + 测试 ≥ 20 条
- [ ] 判官的输入隔离测试：判官会话里不出现任何聊天内容（源码扫描 + 运行时断言）
- [ ] 判官输出的 JSON 校验和引用校验 + 测试 ≥ 15 条
- [ ] 每种局型一份默认评分标准
- [ ] 校准抽样与一致率统计

**超额项**

- [ ] 判官评测集：20 份人工标好分数的产出物，每次改判官提示词或换模型都跑一遍
- [ ] 申诉（第七轮 A3）进入判官重判时，换一个模型判，两次结果都显示

## 9. X 组：自己写插件和工作流的能力

分三级，越往下权限越小、门槛越高。

| 级 | 她能做什么 | 形态 | 怎么生效 |
|---|---|---|---|
| 1 | 写新的局模板、指令包、评分标准草案 | 数据（笔记库里的 md） | 局模板和指令包直接可用；评分标准草案要用户确认 |

**工作流描述只认这些原语**：开局、触发、等待应答、读记忆、写笔记、提交验收、通知。没有锁、额度、信用分、规则、立场结算相关的原语（第六轮的 `wall-forbidden` 清单继续有效）。

- [ ] 工作流原语的解释器 + 测试 ≥ 20 条（含每个禁用能力被拒）
- [ ] 插件提议文档的模板（必须写清：解决什么问题、账本证据、需要的权限、可数的成功指标）

**超额项**

- [ ] 她写的局模板被使用后的效果统计（同类局的通过率对比）
- [ ] 每月一次「她自己写了什么、哪些有用」的汇总进笔记库

## 10. 执行顺序

```
前置       第七轮 P0-1 / P0-2 / P0-3（已在做）
第 1 批    D1 局的数据库  →  S2 局的生命周期  →  S1 作息模板  →  S3 无局状态
第 2 批    T1 指令库  →  T2 频率与降频  →  T3 通道  →  T4 笔写拍照
第 3 批    V1/V2 三层验收与判官  →  W1 控制塔  →  W2 局详情  →  W3 设定页  →  V3 校准
第 4 批    D2 记忆分层  →  D3 记忆调用  →  F2 大鱼人格  →  F3 反顺从  →  F4 暗思考
第 5 批    F1 小鱼调度  →  X 自建能力
```

理由：

- 局是一切的底座，先建表和状态机。
- 触发器和验收器是用户每天都会碰到的，排在两条鱼之前。
- 墙的界面要等三器的数据都有了才有东西可显示。
- 大鱼的改造依赖记忆分层，记忆分层依赖局的数据。
- 自建能力最后：要等她能用的原语都稳定了再开放。

**每一批结束出一个包，用户在真机上用至少 3 天，再开下一批。** 第 1、2 批合起来就是上一轮对话里说的「先只做思考局这一种，用一周」。

## 12. 需要用户决定的事

1. **固定工作时间是几点到几点？** 工作日和休息日各一个。S1 的默认模板要用。
2. **无局上限**：工作时段 5 分钟、非工作时段 30 分钟，合适吗？
3. **思考局默认 4 分钟一触发**，下限 8 分钟。这是按过量原则定的偏高值，用一周后再调。
4. **判官用哪个模型？** 判得准的模型更贵。建议判官用最强的那个，因为它每天只判十几次。
5. **晨间计划 1.3 倍**：多出来的叫「加局」，做不完不扣分。这个倍数可以改。
6. **大鱼的形象参照 Claude**：本文按行为特征写（直接、有依据、承认不确定、会不同意、只问关键问题、不讨好）。如果你想要的是别的方面（比如语气、句式），告诉我具体是哪些。
