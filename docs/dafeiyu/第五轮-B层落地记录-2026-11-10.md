### 三条硬约束的落法（§14.3）

1. **常驻层无 `probability` 字段，随机器只接收 `eligible[]`**
   `vibe.js` 的 `READONLY_BLOCKS` 与 `ARMS` 是两张不相交的冻结表，有测试守着
   （`常驻只读层根本不在 ARMS 里`）。约束层不是"约定不随机"，是**代码里根本没有那条路径**。

2. **`verdict` / `verdictSource` 禁止模型写入**
   `submit_prediction` 的参数 schema 里只有 `claim / dueInHours / evidenceRefs / metrics`。
   `verdict` 只有 `predict.js` 的 `settle()` 能写，`verdictSource` 硬编码 `WALL_TELEMETRY`。
   集成测试里硬塞 `verdict: 'hit'` 进去，账本里仍是 `null`。

3. **每轮落注入快照；`@ D` 只用 system 角色且只搬最短一行；墙不收自由文本**
   快照落 `ledger.jsonl` 的 `state: 'vibe'` 行（`{seed, turn, picks, betaVersion, at}`）。
   `depth` 这个 arm 做到了"只搬最短一行"。`@ D` 本身做不到，见下「问题 5」。

## 二、两个真 bug（顺手修了，因为它们正好挡在路上）

### 1. 五张脸色从来没进过 prompt

`index.js:664` 原来写 `writeJson(stateFile('temper.json'), { edge, at })`——把
`face / label / rule / surprise` 全丢了。于是：

- `temperLine()` 被 import 了，但**一次都没被调用**；
- 就算调用也拼不出内容（`rule` 是空的，`temperLine` 直接返回 `''`）。

也就是说 `temper.js` 的五档脸色（哄/逗/冷/怼/训）从第四轮上线至今**对模型完全无效果**，
只有 `face` id 被 `chooseFace` 拿去做记账。已改成整份存，并由 `temper` 这个 arm 注入。

> 影响面：这是行为变更。之前脸色不影响说话，现在会。真机上如果觉得"变凶/变嗲得太突然"，
> 先看这颗：这是**修回设计意图**，不是新加的性格。

### 2. `Number(null) === 0` 把"量不到"判成"量到 0"

`predict.js` 的 `num()` 原来直接 `Number(v)` 再判 `isFinite`。
`tasks_ratio` 在"今天没定任务"时返回 `null` → `Number(null)` = `0` → `0 < 0.5` 成立
→ 预判被判 **hit**（或者反过来判 miss）。

这是会**冤枉人**的错误：他没定事，不是"一件没做"。已在 `num()` 里显式挡掉
`null / undefined / ''`。测试 `到期后 /plan 会把它撞一遍` 就是抓这个的。

## 三、发现但**没处理**的问题（留待白天）

> 用户明确：这轮只记录，不动手。以下每条都写了「为什么没动」和「动了会怎样」。

### 问题 1 · 总纲 §14.2 的示例指标在我们代码里根本不存在

总纲写的是 `ui_path_bytes_delta / total_bytes_delta`、`core_module_focus_minutes`、
`source: "墙/规则.md#metrics"`。这三样**一个都没有**：

- `lib/wall.js` 没有 `metrics` 配置表，`DEFAULT_WALL` 只有
  `enabled/meals/eveningOpen/relaxSegmentMin`，`wallConfig()` 也只 clamp 这几项；
- `lib/wall_auditor.js` 实际在量的只有四类：文件字节增量（`GROWTH_MIN_BYTES=300`）、
  新截图张数、某 App 今日分钟数、当日任务完成情况。

**本轮处理**：把 `proxy_metrics` 收敛成代码真能量到的五个（`file_growth`、
`screenshot_count`、`app_minutes`、`fun_minutes`、`tasks_ratio`），编不出来的指标名
直接拒收。这比总纲原意**更严**，不是更松。

**白天要决定的**：要不要在 `wall.js` 里真造一张 `metrics` 表。造了才能支持
"UI 路径字节占比"这类细分指标，但也就意味着要写新的文件扫描逻辑——
§14.2 那句 `source: "墙/规则.md#metrics"`（让用户自己在 Markdown 里配指标）
在现有架构下等于要写一个 Markdown→指标表达式的解析器，工作量不小。

### 问题 2 · 总纲自相矛盾：铁律既"绝不随机"又进了随机器

- §14.1 的 `ARMS` 里有 `ironSplit`，且它在 `GROUPS.G_MIND` 里（会被抽样）；
- §14.3 第 1 条说「常驻层无 `probability` 字段」，§15 说「判断核心属常驻只读层，不进 `GROUPS`」；
- §11 的表格把「铁律」明确划进**约束层，绝不随机**。

**本轮处理**：取「不违反硬约束」的那一支——**铁律全量照常注入，`ironSplit` 只决定
这一轮额外强调哪一条**。渲染出来是「下面这些照旧全部算数，只是这一轮额外看紧这一条：X」，
有测试断言这句话必须存在。任何一条铁律都不会因为抽样而不见。

**白天要决定的**：如果原意真是"每轮只讲一条铁律"，那就和 §11/§14.3 直接冲突，
得先裁决，再改 `readonly` 的边界——那个改动会动到类型级只读，风险高。

### 问题 3 · `@ D`（注入深度）在当前架构下做不了

`index.js` 唯一的注入口是 `agent.ctx.systemPrompt.context({ name, order, text })`，
`order: 850`。`order` 只在**系统提示内部**排序，没有"插到最后一条用户消息上方"这种能力
（SillyTavern 的 `@ D` / Depth 0 才有）。所以 §13.5 的「只搬最短一行到最后」只能做到
"把最短那行放进系统提示的靠后位置"，做不到真正的 prompt 底部。

**本轮处理**：`depth` arm 选 `stateLines` 里最短的一行，以「时刻记住这一句：X」的形式注入。
不假装做到了 `@ D`。

**白天要决定的**：是否要为它改宿主侧的 prompt 组装接口。那是 DSH 引擎层的活，不是插件的。

### 问题 4 · 组合抽样的信用分配已经按 §13.1 处理，但样本会攒得很慢

按 §13.1 做成了**逐 arm 记账**（`updateArm`，只给被抽中的记）。但要注意一个真实约束：

arm 的账**只在"他当时正在娱乐 App 里"那一球才有结果**（`brain.js` 的 `observe` 只在
`phone.fun && phone.app` 时置 `pending`）。也就是说：

- 一天真正能记账的回合可能只有几次；
- 7 个 arm，每组 2–3 个，单个 arm 大约 1/2 ~ 1/3 的命中率，还要再乘上"他在娱乐 App"的比例。

结论：**账本要好几个星期才攒得出稳定信号**。这跟 `deriveBeliefs` 要求每格 ≥4 次是同一类问题，
只不过 arm 这边目前**还没有**往 prompt 里写判断（我没加），所以暂时不会出现
"假装了解他"的副作用。

**白天要决定的**：要不要把 arm 的结果也纳入 `deriveBeliefs`（现在没有）。
纳入就要定一个"多少次才说"的阈值，阈值定低了会胡说。

### 问题 5 · arm 记账依赖内存里的 `lastVibePicks`，进程重启就丢

`index.js` 里 `let lastVibePicks = []`，在 `chatPersonaText` 里被赋值，在 `sense()` 里被消费。
引擎重启（或 APP 被系统杀掉）之后，上一轮抽了哪几个 arm 就不知道了，那一球的账会漏记一次。

**为什么没修**：要修就得把 `lastVibePicks` 存进 `brain.json`（或 `vibe.json`），
多一处落盘、多一个可能不一致的状态。漏记一次不影响正确性（只会让样本更少），
所以按"最小改动"先放着。

**白天要决定的**：如果发现真机上漏记频繁（比如频繁被系统杀），再补。

### 问题 6 · `submit_verdict` 仍然是完整的旁路（这是老问题，本轮没碰）

`followup.js` 的 `checkVerdict` 只校验格式（kind 六选一、satisfied 布尔、
非空 summary/nextStep），`index.js` 的 `applyVerdict` 拿到 `satisfied: true` 就
清义务、关锁、开 20 分钟放风、解锁娱乐。

但**现在多了一条对照**：`submit_prediction` 这条路把 `verdict` 锁死在遥测手里了。
两条路的落差会越来越明显——押一条预判要真凭据，裁一次过关只要一句话。

**没动的原因**：收窄 `submit_verdict` 是用户决策项，第四轮已经问过，用户当时选的是
「只做预判闭环 + 五步第一步挑刺」，没选收窄裁决。按用户决定执行，不擅自加。

**白天要决定的**：要不要让 `submit_verdict(kind=review/evening)` 也要求挂 `evidence_refs`。
技术上现成（`predict.js` 的验真逻辑可以复用），但会明显降低"过得去"的容易度。

### 问题 7 · vibe 的 20 秒复用窗口是拍的，不是算的

`chatPersonaText` 每轮可能被调用不止一次（`text: () => chatPersonaText(role)` 是惰性函数，
prompt 组装或重试时会被调多次）。为了"同一轮里两句人设不打架"，加了个
`VIBE_HOLD_MS = 20_000` 的缓存窗口：20 秒内同角色的重复调用复用同一批素材。

**为什么是 20 秒**：拍的一个"够覆盖一次组装+重试、又短于两次真实对话"的数。
没有度量依据。

**白天要决定的**：真机上看 `ledger.jsonl` 里 `state: 'vibe'` 的密度。
如果一轮里落了 3 次快照，说明 20 秒太长或太短；如果两次真实对话被合并了，说明太长。

### 问题 8 · `samples`（例句池）和 `keywordCard` 的素材池是我写的，需要你过一遍

`vibe.js` 里的 `SAMPLES`（5 张脸 × 2 条例句）和 `IRON_RULES`（6 条）是**硬编码中文**，
按"从她已有的人设卡里蒸馏、不引入新约束"的原则写的，但语气对不对只有你能判。

**没动的理由**：这是内容活，不是工程活，而且改起来零风险（纯字符串常量）。
