# 第三轮接口约定（Claude Code ↔ DeepSeek）

这份文件是**插件 Node 层与手机原生层之间**的契约。改这里之前先看对方有没有按旧版本写好了代码：
`/plan` 的返回字段、事件名、裁决落账形状，两边必须同时改。

分三层看：

- **墙**（Node）：按全天状态机算出"这一刻什么状态、娱乐锁不锁、放行谁"。手机只执行，不判断。
- **控制感知**（Kotlin）：亮屏、前台 App、锁屏页上报、拦下就开始计时。手机自己也在本地计时，引擎死了照锁。
- **对话追问**（两姐妹）：只能用 `submit_verdict` 影响墙，没有别的把手。

## 1. `POST /dsh-go-companion/v1/plan`

手机每次切 App / 定时器到点都问一次。带手机现状，拿回"这一球说不说 + 现在什么状态 + 该锁什么"。

### 请求（手机 → 插件）

```json
{
  "sessionId": "session-xxx",
  "timeZone": "Asia/Shanghai",
  "roll": 100,
  "phone": {
    "app": "com.game",
    "label": "王者",
    "fun": true,
    "minutes": 23,
    "screenOn": true,
    "local": "15:00",
    "today": [{ "app": "com.game", "minutes": 40 }]
  }
}
```

`local` 是手机当地时间 `HH:MM`，节奏和状态机优先用它（挂时区换算容易差一小时）。`phone` 整块可以没有。

**`timeZone`（R7 P0-2 起基本不用发）**：手机固定发 `Asia/Shanghai`，插件默认 `lockTimeZone: true` 时也**一概忽略**请求体里的这个字段，一律按 `Asia/Shanghai` 算「今天」「零点」「安静时段」。
只有插件 config 显式把 `lockTimeZone` 设成 `false`，请求体的 `timeZone` 才会被采纳——
手机端把时区改成纽约、或者模拟器默认 UTC 都不会再把她的时间基准带偏。
手机侧自己的时间计算统一走 `loop/core/BeijingClock.kt`（固定 `Asia/Shanghai`，不读设备时区）。

### 返回（插件 → 手机）

老字段一个都没动，**新加的三块**加粗。

| 字段 | 说明 |
| --- | --- |
| `speak` / `reason` / `nextCheckAt` | 这一球说不说、为什么、下次什么时候问 |
| `speaker` | `companion`（鱼丸）/ `strategist`（鲸澜） |
| `force` | `{level, name, why, app, release}`，力度与是否放行 |
| `rules` | `{v, at, rules:[{kind, until, why}], block:{包名: until}}`，本地执法快照 |
| **`state`** | **全天状态机：见第 2 节** |
| **`followup`** | **`{active, reason, currentQuestion, since, until}`** |
| **`obligations`** | **`[{kind, text, reask, createdAt, ageMs}]`** |
| `refuse` / `gear` / `session` / `geminiSchedule` / `wall` / `trust` / `tide` / `block` / `shield` / `silence` | 沿用第二轮 |

`rules.rules[].kind` 现在有这些：`default`（白天默认锁）、`night`（深夜）、`review`（晚间对账）、`morning`（晨间立项）、
`task`（冲刺 / 她们立的任务）、`refuse`（拒绝模式）、`followup`（追问锁）、`block`（临时封禁名单在 `block` 里单独给）。

**`followup` 是新的 kind，需要 DeepSeek 在 `Enforcement.kt` 的 `LockPriority` 里加一项**，位置按第 2 节的优先级表。
在加上之前手机可以先把未知 kind 当 `default` 处理，不会崩。

`rules` 是"引擎活着时的实时快照"，`state` 是"这一刻的全天判断"。**两者冲突时手机以 `state.layers[0]` 为准**——
`rules` 只为了让老版本客户端不至于完全瞎掉。

### `session`：连麦舱（R7 P0-1 起带 `graceMs`）

```json
"session": { "app": "com.google.android.apps.bard", "allow": ["com.google.android.apps.bard"],
             "until": 1794153600000, "graceMs": 45000, "topic": "…", "mode": "interrogate" }
```

- `graceMs`（新）：舱内**其余第三方 App** 的宽限，毫秒，默认 `45000`，可用插件 config `sessionGraceMs` 改。
- 手机侧不再"白名单以外一律 4 级锁"，改三级：**放行** / **宽限**（只提示，不弹锁屏页）/ **锁**。
  判定顺序：急事底线、她自己、输入法·系统弹层 → 插件 `allow` + 用户放行名单 → 当前默认桌面（`resolveActivity`
  运行时解析，写死名单只兜底）→ 娱乐目标（`block` ∪ 拦截目标，**立刻锁**）→ 系统应用（图库、文件选择器、相机、GMS）
  → 其余第三方 App 先宽限 `graceMs`，连续停留超时才锁。回到白名单 App 即清零。
- 老版本忽略 `graceMs`，行为不变。

## 2. `state`：全天状态机（C2）

```json
{
  "state": "followup",
  "priority": 80,
  "until": 1794153600000,
  "funLocked": true,
  "allow": [],
  "backTo": "standby",
  "followup": { "active": true, "reason": "standby", "currentQuestion": "这二十分钟在干嘛", "since": 0, "until": 0 },
  "agenda": "追问锁：把当前问题问完，给出裁决（submit_verdict）。",
  "layers": [
    { "kind": "followup", "priority": 80, "funLocked": true, "until": 1794153600000, "why": "追问锁：把这一个问题说清楚。", "reason": "standby" }
  ],
  "nextChangeAt": 1794153700000
}
```

- `state`：主状态，**同一刻只有一个**。取值：
  `night` 深夜锁 / `evening` 晚间对账 / `morning` 晨间立项 / `review` 验收 / `followup` 其他原因的追问锁 /
  `sprint` 冲刺 / `brain` 共脑（Gemini 舱）/ `meal` 吃饭 / `break` 放风 / `standby` 待命（默认严格）。
- `priority`：越大越优先。**多锁并存时放行范围取最严，界面只显示最高那一项**。
- `funLocked`：这一刻娱乐锁不锁。`allow`：只放行哪些包名（共脑时是 Gemini；其余为空 = 全按 `funLocked` 走）。
- `backTo`：追问锁结束后回到哪个主状态（`state` 不是 `followup` 时等于 `state`）。
- `layers`：所有同时生效的层，从高到低排好。**裁判只看 `layers[0]`**。
- `nextChangeAt`：下一次换状态的时刻。手机按这个安排下一次问 `/plan`，不用一直轮询。

优先级（`LAYER_PRIORITY`）：

```
night(100) > evening(90) > followup(80) > sprint(70) = brain(70) > meal(60) = break(60) > standby(50)
```

> 手机端 `LockPriority` 建议的最终顺序：`night > evening > followup > task(sprint) = brain > default(standby)`。
> `meal` / `break` **不下发锁**（`funLocked:false`，`layers` 里没有这两层）。

### 2.1 两个计时，手机照做就行

- **晨间立项：7:00 之后第一次亮屏才开。** 深夜锁锁到 7:00，晨间窗口从 7:00 开始，两者不重叠。7:00 前亮屏不算起床，不会提前开门；当天只开一次。
- **待命 10 分钟计时器：** 主状态是 `standby`、且连着 10 分钟没换出待命，插件自己开一把 `reason:'standby'` 的追问锁。
  换出待命指进入吃饭 / 放风 / 冲刺 / 共脑 / 晨间 / 对账；**聊天不算动**。
  开锁那一刻 `nextCheckAt` 会落在那儿，手机按它回来问 `/plan` 即可，不用自己再定时。已经欠着一笔 `standby` 义务时不再追问，只记账。
  他明确要安静（`muted`/`quiet`/`disabled`）或者已经三球没接要退避 3 小时（`no-take`）时，计时器不抢这个 `nextCheckAt`。

## 3. `POST /v1/event`：手机报来的事

| `type` | 携带 | 插件做什么 | 返回 |
| --- | --- | --- | --- |
| `overlay-closed` | `chatted` / `muted` / `busy` / `app` | 记一笔（不算回过话、不开安静期） | `{ok:true}` |
| `defied` | `app` / `label` / `source` | 开拒绝模式 + 开追问锁（原因 `defiance`），顺带问掉挂着的违抗义务 | `{ok, refuse:{until}, force:{level:4,app,why}}` |
| `tamper` | `what` / `app` | 拒绝 60 分钟 + 记 -100 分 | 同 `defied` |
| `breakglass` | `minutes` / `steps` / `note` | 破窗一段（每天 1 次），期间放行 | `{ok, breakUntil, penalty}` |
| `notif` | `app` / `label` / `title` / `group` | 攒进防波堤，任务结束一次性简报 | `{ok:true}` |
| **`start`** | `task` / `minutes` / `long` | 进冲刺：娱乐锁、通知收进防波堤 | **`{ok, sprint:{until,minutes,task}}`** |
| **`request-review`** | — | 他不是等到的，自己点"申请验收" | **`{ok, followup:{...}}`** |
| **`screen-on`** | — | 只记账。门开不开由 `/plan` 的作息判定 | **`{ok:true}`** |
| **`gemini-end`** | `minutes` / `by` | 连麦结束：满 3 分钟 → 追问锁（`gemini`）；不足回待命 | **`{ok, counted, followup}`** |
| **`followup-timeout`** | — | 锁到点没裁决：结束拦截、扣分、挂义务 | **`{ok, expired, followup, obligations}`** |
| **`wechat-hit`** | `page` / `dwellMs` | 微信误入视频号：只记账，**不升级成违抗** | **`{ok:true}`** |
| **`blocked-open`** | `app` | 他打开被拦的 App：挂着的义务按动作再问一次 | **`{ok, ask, followup}`** |

加粗的是第三轮新增。旧事件行为没变。

### `POST /dsh-go-companion/v1/gemini/due`

D4 的到点取货口。`/plan` 里的 `geminiSchedule` 只告诉手机「下一场排在什么时候」，
到点后手机调这个 POST，插件返回这一场的 launch（取完就置成已发，重复调用不会再给同一场）。

```json
{ "v": 1, "launch": { "brief": "给 Gemini 的背景简报", "topic": "本次要聊的焦点", "minutes": 20, "mode": "thinking" } }
```

没到点或已经取过 → `launch: null`。手机拿到 `null` 就什么都不做。

`geminiSchedule` 形状（`/plan` 顶层）：

```json
{ "at": 1794153600000, "topic": "为什么这周进度卡住", "minutes": 20 }
```

`at` 是插件按 `timeZone` 算好的**绝对时间**，手机直接 arm 闹钟，不要自己按本地时间推。
（`schedule_gemini_live` 工具接受 `HH:MM`，过去的时间顺延到明天，换算在插件里做完。）

这张表有两处会写它，手机不用区分：`schedule_gemini_live` 预约的（`by: "schedule"`），
和 R4-6「走神强拉」当场写的（`by: "drift"`，`at` 就是此刻 + 半秒，`mode` 固定 `interrogate`）。
两种情况手机都照同一条路：arm 闹钟 → 到点 `POST /gemini/due` → 拿 launch 拉起 Gemini。

`blocked-open` 是**"只由他的动作触发再问"**那一条的实现：不定时弹，他打开哪个被拦的 App 就趁这一次问。
一条义务只问一次（问过记 `askedAt`），不会每次开 App 都堵他。

## 4. `submit_verdict`：唯一的裁决入口（C3）

```json
{
  "kind": "morning | review | defiance | standby | gemini | evening",
  "satisfied": true,
  "summary": "为什么算过关（满意时必填）",
  "nextStep": "下一步做什么（满意时必填）",
  "tasks": [{ "task": "改简历", "evidence": "简历.pdf" }],
  "longTerm": false
}
```

- 格式**只校验结构，不判断内容**。满意不满意是姐妹的决定。
- 格式不合格 → 按不满意处理，原因回给姐妹；账本记 `state:'verdict-invalid'`（`code` 说明哪一项不合格），
  **不写 `state:'verdict'`**，免得污染 D3 的笔记同步。
- 满意 → 关锁 + 按 `kind` 收尾：`morning` 的任务进当日文件并放风；`review` 放风 + 清算任务；`evening` 对账出明天额度。
- 不满意 → 锁**不消失**（`until` 不动），只记账；到点按超时处理。这就是"回复敷衍时窗口不消失"。

### 账本里一条裁决的形状（DeepSeek 的 D3 按这个扫）

```json
{ "state": "verdict", "at": 1794153600000, "by": "strategist",
  "kind": "morning", "satisfied": true,
  "summary": "定下两件事", "nextStep": "按计划走",
  "tasks": [{ "task": "改简历", "evidence": "简历.pdf" }],
  "longTerm": false }
```

字段名用 `nextStep`（驼峰），读的时候 `next_step` 也认。`tasks` 只在晨间立项有。

## 5. `followup` / `obligations`：锁住了什么

`config.followup = { reason, question, since, until, closedAt?, closedBy? }`

- 同一时刻**只有一把**。同原因重复开不续命（30 分钟上限绕不过去）；换原因才重新计时。
- 上限 `followupCapMin`（默认 30 分钟），超时扣分 `followupPenalty`（默认 5 分）。

超时挂什么义务（`OBLIGATION_TABLE`）：

| 原因 | 义务 | 再问时机 |
| --- | --- | --- |
| `morning` | 当天不能放风，直到补完立项 | 下次打开被拦的 App |
| `review` | 这一轮不放风 | 不再问 |
| `evening` | 今晚不开申请窗口 | 不再问 |
| `defiance` / `standby` / `gemini` | 只记账扣分 | 下次违抗时再问 |

## 7. 第四/五轮新增（第五轮回填）

### 7.1 `POST /dsh-go-companion/v1/sisters`（第四轮，只读）

`{v, ok, sisters:{cards:[{role,name,persona,memory:[],recent:[]}], audit:{...}}}`。
只读：不改规则、不改额度、不落盘。

### 7.2 `POST /dsh-go-companion/v1/deposit`（第五轮）

每日四部门提交。四段按固定顺序：`intel` 信息收集、`thinking` 谋划思考、`behavior` 行为管理、`coord` 统筹规划。
每段两栏：`report`（汇报内容，≥200 字）+ `thought`（我的想法，≥80 字），字数按**去掉空白和标点**后计。

请求：

| 字段 | 说明 |
| --- | --- |
| `action` | `status`（默认，只读）/ `submit`（交一段）/ `slot`（A4：记一条日间短记录） |
| `department` | `submit` / `slot` 必填，四个 key 之一 |
| `report` / `thought` | `submit` 必填，两段原文（`report` 对行为管理部无效，见下） |
| `text` / `taskId` | A4：`slot` 用，一条记录（≤200 字）与关联任务（选填） |
| `timeZone` | 选填，算「今天」用 |

返回（三种 action 同形）：

```json
{ "v": 1, "ok": true,
  "deposit": {
    "day": "2026-11-09", "done": 1, "total": 4,
    "missing": ["谋划思考", "行为管理", "统筹规划"], "missingText": "今天还缺 3 段：…",
    "items": [{ "key": "intel", "label": "信息收集", "hint": "…", "done": true,
                "at": 1762..., "reportChars": 214, "thoughtChars": 96,
                "minReport": 200, "minThought": 80,
                "duty": "今天读了 / 查了 / 问了什么，来源是什么", "evidence": "笔记库新增文件、gemini_log",
                "autoReport": false, "slots": 2 }],
    "departments": [{ "key": "intel", "label": "信息收集", "hint": "…" }]
  } }
```

退回收：`{...同上, ok:false, error:{code, message}}`，`code` 是：

| code | 什么时候 |
| --- | --- |
| `bad-department` | 没有这个 key |
| `too-thin` | 字数不到 / 套话 / 想法是汇报的复读 |
| `bad-slot` | A4：`slot` 的 `text` 空着、超过 200 字，或那个部今天已记满 20 条 |
| `unsupported` | A4：晚间对照没过——汇报里提到的事，今天的记录槽和证据来源里都找不到对应 |

被退回的不落盘。状态按天复归，不累计（记录槽和四段一起清）。

**A4 两条新规矩**：

1. **行为管理部的 `report` 整个不看**（不是覆盖，是不读）。插件按墙的遥测自动生成那一段，
   用户只写 `thought`。界面侧把汇报栏设成只读，提交时不送 `report`。
2. **`submit` 会先做晚间对照**（`unsupported`）。对照的池子是「当天该部的记录槽 + 证据来源」：
   信息收集/谋划思考看今天动过的笔记，统筹规划看当天的时间表与重排记录，行为管理不对照（证据是遥测）。
   两处都空即判无据。

### 7.3 `/status` 新增 `deposit` 块（第五轮）

`statusBody().deposit = {...statusOf(今天), missingText}`，形状同 7.2 的 `deposit`（无 `departments`）。

### 7.4 `wall` 块新增三个字段（第五轮）

`POST /v1/wall`（action=status）的 `wall` 里多三样：

| 字段 | 说明 |
| --- | --- |
| `depositDone` | 今天已交几段 |
| `depositTotal` | 一共几段（4） |
| `depositMissing` | 还缺哪几段，`、` 分隔；交齐是空串 |

`/plan` 返回的 `wall` 块与浮层面板的 `wall` 只加了 `depositMissing`（那两处不需要计数）。

**`relaxRemaining` 的取值变了，语义没变**：它仍然是「现在还能放几天假」，但第五轮起
**四段没交齐时是 0**（以前是纯周额度）。同一份判断也写在 `requestRelax()` 里——
窗口开着、额度也有，没交齐照样返回 `code: 'deposit'` 拒掉。所以看到 0 时要读 `depositMissing` 才知道为什么。

### 7.5 `GET /wall/thread` 与 `POST /wall/appeal`（第七轮 A3）

A3 把「墙说过的话」和「申诉」做成两条只读/受控的接口。**两条都不调用模型、不联网**：
判定码由 `lib/wall_auditor.js` 产出，话由 `lib/wall_voice.js` 按码配模板，中间没有生成环节。
`test/wall-voice.test.mjs` 有一条源码扫描守着这件事（`wall_voice.js` 里不许出现
`askModel|callModel|invokeModel|llm|chatCompletion|openai|gemini|fetch(|http(s)://`）。

#### `GET /wall/thread?timeZone=Asia/Shanghai`

读最近 14 天、最多 60 条的审查记录，按时间**倒序**（最新的在最上面，界面不用自己翻）。

```json
{
  "v": 1, "ok": true,
  "thread": {
    "bubbles": [
      { "kind": "verdict", "at": 1794000000000, "who": "墙", "text": "未通过。要求：文件增长 ≥ 300 字节。实测：+112 字节。差 188。", "pass": false },
      { "kind": "submit",  "at": 1793999990000, "who": "他", "text": "写文档", "pass": null },
      { "kind": "rule",    "at": 1793990000000, "who": "他", "text": "规则变更。他：门禁 120 → 90。立即生效。", "pass": null }
    ],
    "kinds": ["submit", "verdict", "rule"],
    "appealLeft": 2,
    "appealMax": 2
  }
}
```

气泡**只有三种**（`kinds` 就是这个白名单，插件不认第四种）：`submit` / `verdict` / `rule`。
`pass` 只在 `verdict` 上有意义，另外两种是 `null`。`who` 只有「他 / 姐妹代交的名字 / 墙」。

**这一条不生成任何新句子**：`kind=submit` 的 `text` 是账本里记的事名，`kind=rule` 的
`text` 是 `change_rules` 当初记下的改动，`kind=verdict` 的 `text` 是判定当时写下的原话。
所以「墙说过什么」永远是当时那句话，重读一万次都一样。

#### `POST /wall/appeal`

一条具体判定 + 一份**新的**物理证据。每天 2 次（`APPEAL_MAX_PER_DAY`）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `at` | number | 要申诉的那条判定的时间戳（= `thread.bubbles[].at`，也是账本里那条的 `at`） |
| `evidence` | string | 新的物理证据：文件路径、`截图`、或 `某 App N 分钟` |
| `task` | string | 可选，这件事叫什么；不给就用那条记录里的 `kind` |
| `baseline` | object | 可选，`{path, size}`：文件大小基线 |
| `timeZone` | string | 可选，`Asia/Shanghai` |

成功：

```json
{ "v": 1, "ok": true,
  "appeal": { "code": "file:pass", "pass": true, "text": "通过。要求：文件增长 ≥ 300 字节。实测：+112 字节。", "left": 1, "appealLeft": 1 } }
```

`code` 是重算出来的判定码（下表），`text` 是 `verdictVoice(code, vars)` 生成的那句话，
`left` 是这次用掉之后今天还剩几次。

失败（`ok: false`，`error.code` 是四种申诉码之一，`error.message` 是 `appealVoice` 的固定话）：

| `error.code` | 什么时候 |
| --- | --- |
| `appeal:no-quota` | 今天 2 次已经用完 |
| `appeal:not-verdict` | `at` 找不到对应的判定（只认 `state` 是 `verdict` / `wall-audit` 的记录） |
| `appeal:no-new-evidence` | `evidence` 是空的，或这条判定下已经交过同一份 |

**申诉不改判定，只重算一次**：判还是由 `auditTask` 按同一套规则算，证据是不变的输入时结论必然不变。
每次申诉落一条 `{state:'appeal', at, target, evidence, code, pass}` 到账本，
额度按**这条记录的条数**算（不按判定数算——被判一百次也只有今天那两次）。

#### 判定码表（`lib/wall_voice.js` 一个码配一句）

| 码 | 什么时候 |
| --- | --- |
| `file:pass` / `file:short` / `file:grew0` | 文件增长够了 / 不够 / 一点没长 |
| `file:no-file` / `file:stale` | 路径不存在 / 存在但立项后没动过 |
| `screenshot:pass` / `screenshot:none` | 立项后有新截图 / 一张都没有 |
| `app:pass` / `app:short` / `app:not-found` / `app:zero` | 某 App 用够了 / 不够 / 使用记录里没有 / 0 分钟 |
| `none:unverifiable` | 交的完成物是墙查不了的类型 |

`wall_auditor.js` 的 `auditTask` 在每个分支多返回 `code` 和 `vars`（`path/min/grew/diff`、
`n`、`label/need/got/diff`、`evidence`），`verdict/pass/data/missing` 的语义一个字没变。
**`AUDIT_CODES` 加新码而 `VOICE_TEMPLATES` 没配，`verdictVoice` 直接抛**——
兜底会让「新分支没配话」悄悄溜到用户面前；`test/wall-voice.test.mjs` 遍历那张表来钉这一条。

### 7.6 `GET /mount` 与 `POST /mount`（第七轮 C1）

工作记忆挂载卡。**卡里的每一句都必须是他自己的话**：她只能通过 `mount_propose` 带账本行号提议，
他点头（`accept`）才落卡。这条规矩落在 `lib/mount.js` 的三个入口上（`isUserText` 判来源、
`src` 必填、`withStep` 的 `from` 越界直接拒），不靠提示词。

#### 卡的形状

```json
{ "id": "1794409810837-a4f", "topicId": "",
  "openedAt": 1794409810837,
  "goal":   { "text": "把增量同步做出来", "by": "user", "at": 1794409810837 },
  "givens": [ { "text": "服务端已经有版本号了", "by": "user", "at": 1794409900000, "src": "128" } ],
  "steps":  [ { "text": "所以是订阅没解绑", "by": "user", "at": 1794409950000, "from": [0] } ],
  "status": "open", "parkedWhy": "" }
```

`status` 只有三种：`open` / `parked` / `closed`（别的值一律当 `closed`）。
`givens` ≤5（`MAX_GIVENS`）、`steps` ≤5（`MAX_STEPS`），两者的 `text` 都截到 120 字（`TEXT_MAX`）。
`steps[].from` 是 `givens` 的下标（0 起），**必须非空**——结论说不出由哪几条已知推出来，就不算结论。

#### `GET /mount?timeZone=Asia/Shanghai`

只读视图，浮层小卡打开时先读一次：

```json
{ "v": 1, "ok": true,
  "mount": {
    "status": "open",
    "goal": "把增量同步做出来",
    "givens": [ { "text": "服务端已经有版本号了", "at": 1794409900000, "src": "128" } ],
    "steps":  [ { "text": "所以是订阅没解绑", "at": 1794409950000, "from": [0] } ],
    "maxGivens": 5, "maxSteps": 5,
    "parkedWhy": "",
    "scaffold": { "user": 0, "her": 1, "ratio": 0, "cap": 3, "hit": 1 },
    "id": "1794409810837-a4f",
    "ask": false,
    "pending": null,
    "cards": [ { "id": "1794409810837-a4f", "status": "open", "goal": "把增量同步做出来", "parkedWhy": "" } ]
  } }
```

- `givens` / `steps` 给的是**条目本身**，不是条数（条数由界面取 `.length`）。只给个数，
  界面就得自己再猜内容——而「把三栏摆给他看」正是这张卡的全部意义。
- `goal` 在停着 / 关掉的卡上也带着。不然浮层小卡在停着的卡上只能显示一句「停着的卡」。
- `id` **必须回**：`resume` 要按它指认是哪一张。
- `ask` 是断链检测亮没亮（30 分钟窗口内有效）。
- `pending` 是等她被点头的那一条提议 `{text, slot, src}`，没有就是 `null`。
- `cards` 是全部卡的一眼清单（最多 `MOUNT_KEEP=12` 张，最新的在最后）。
- `scaffold` 是脚手架撤除比例：`user` = 他自己挂的次数、`her` = 她提议才挂的次数、`hit` = 两者之和，
  `cap` = 她今天还能提议几次。四档写死不调：`ratio` ≥2 → `0`、≥1 → `1`、≥0.5 → `2`，否则 `3`
  （`ratio` = `user/her`；`her` 为 0 而 `user` 不为 0 时是 `Infinity`，JSON 里会变成 `null`，此时 `cap` 是 `0`）。
- 没有卡时 `status` 是 `none`，`goal` 是 `''`，两个数组是 `[]`——**不冒充一张空卡**。

#### `POST /mount`

`action` 决定做什么，其余字段按动作给。**十个动作**：

| `action` | 字段 | 做了什么 |
| --- | --- | --- |
| `status`（默认） | — | 同 GET |
| `open` | `goal` | 开一张新卡。已经有一张 `open` 时拒（`card-open`） |
| `seen` | `text` | 断链检测的**显式入口**：把他这一句原话交给 `driftOf` |
| `given` | `text`、`src?` | 追加一条已知。满 5 条拒（`givens-full`） |
| `step` | `text`、`from` | 追加一条中间结论。`from` 必须引用已有已知（`step-needs-given`） |
| `accept` | `from?` | 把 `pending` 那条落卡，账本记 `by:'her'` |
| `drop-proposal` | — | 不要那条提议（不落卡） |
| `park` | `where` | 停起来。**必须说一句停在哪**（`park-needs-why`） |
| `resume` | `id` | 恢复一张停着的卡。已有一张 `open` 时拒（`card-open`） |
| `close` | — | 关掉（只读留存，不再进每轮注入） |

`seen` 的回包多一个 `drift` 块：`{ drift, hit, need, ask, streak }`。
`drift` 是重合等级、`hit` 是这一轮对上的关键词数、`need` 是阈值、`ask` 是亮没亮卡、
`streak` 是连续漂了几轮（`DRIFT_STREAK=2` 才亮）。

失败一律是 `{ v:1, ok:false, error:{ code, message } }`，`mount` 视图照给（界面不用再读一次）：

| `error.code` | 什么时候 |
| --- | --- |
| `goal-empty` | `open` 没给目标 |
| `card-open` | 已经有一张 `open` 的卡，又来开/恢复 |
| `no-card` | 现在没有卡，却要加东西 / 恢复一张不存在的 id |
| `givens-full` / `steps-full` | 已经 5 条 |
| `step-needs-given` | 结论没引用已知，或引用了不存在的下标 |
| `not-user-text` | 要挂的那句不是他的原话（`isUserText` 判）。面板手写那条路 `sources` 是空的、一律放行，所以这个码实际只在 `mount_propose` 上触得到 |
| `park-needs-why` | 停放没说停在哪 |
| `propose-needs-source` | 提议没带账本行号 |
| `card-not-open` / `card-not-parked` / `card-closed` | 动作和卡的状态不搭 |
| `bad-proposal` / `bad-slot` | 提议的形状或槽位名不对 |
| `no-proposal` | 没有待确认的提议却点了头 |
| `bad-action` | `action` 不在上面十个里 |

#### 三条规矩

1. **卡上只放他的原话。** `not-user-text` 不是「字数超了」，是「这压根不是他说过的话」。
   超长原话仍是原话（落卡时截到 120 字）。
2. **同时只有一张 `open` 卡。** 开新卡前旧卡必须 `parked`（带一句停在哪）或 `closed`。
3. **`seen` 没有自动接线。** 插件拿不到用户的聊天消息（`chatPersonaText(role)` 的入参只有角色），
   所以断链检测纯函数写好了，但**要由拿得到消息的那一层来调 `POST /mount action=seen`**。
   在这一层接上之前，界面上的 `ask` 永远是 `false`。

#### 注入与支线

- 卡开着时进状态层，`priority` **65**（状态层最高，规格要求）。一行 ≤300 字符（`INJECT_MAX`），
  格式 `[挂载] 目标：… ｜ 已知：①…②… ｜ 推到：… ｜ 上次动：14:20`。
  装不下时**先丢已知**（从最后一条丢），目标和结论一定留下。关掉 / 没卡时返回空串，不占预算。
  代价：卡开着会把状态层里 `deposit`(40) / `knowledge`(35) 挤掉。
- `MEMORY_LEAK_TRACK` 是 `config.tracks` 的**兜底第一条支线**（`lib/mount.js` 里写死四个业务槽位，
  `tracks.js` 一个字没改）。规则：`config.tracks` 是非空数组就以配置为准；空数组 / 缺失就用
  `[MEMORY_LEAK_TRACK]`。**要关掉这条支线必须写 `enabled:false`**——默认配置本来就是 `tracks: []`，
  没法用「空」区分「没配」和「全关」。

### 7.7 `GET /drill-op` 与 `POST /drill-op`（第七轮 C2）

四个基本操作（回想 / 精简 / 预判 / 提问）的**判据层**。合格线全在 `lib/drills.js` 的纯函数里，
**不问模型**——判断题交给模型，模型就会开始安慰人。

#### `GET /dsh-go-companion/v1/drill-op?timeZone=Asia/Shanghai`

只读：出什么题、额度、近 14 天通过率。**读一次不记账、不消耗额度。**

```json
{
  "v": 1, "ok": true,
  "op": {
    "order": ["recall", "brief", "predict", "ask"],
    "next": "recall",
    "meta": { "name": "回想", "ask": "不看任何东西，说出上次推到哪。",
              "pass": "与卡上结论的关键词召回率 ≥ 0.3，且作答时挂载卡是遮住的",
              "source": "已停放的卡、昨天的四部记录", "demo": "停在「订阅没解绑」那条…" },
    "quota": { "used": 0, "max": 6, "left": 6 },
    "stats": { "recall": { "asked": 0, "passed": 0, "rate": 0 }, "brief": { … },
               "predict": { … }, "ask": { … } }
  }
}
```

- `next` 是**今天第一个还没过的操作**（固定顺序 `recall→brief→predict→ask`）；
  额度用完或四个都过了是 `null`。
- `stats` 里没练过的操作 `asked` 是 **0**、`rate` 是 **0**——**没练过 ≠ 满分**。
- `rate` 是近 14 天（今天算第 1 天）。

#### `POST /dsh-go-companion/v1/drill-op`

```json
{ "op": "recall", "answer": "停在订阅没解绑", "blind": true, "timeZone": "Asia/Shanghai" }
```

- `op` **可以不给**：不给就按链路该出的那个判（`result.op.next`）。调用方少一步，
  链路也少一处能绕开的地方。给了不认识的值回 `bad-op`，**不挑一个替它判**。
- `blind`：回想专用，手机侧遮住挂载卡后上报 `true`。**不遮就不算**（`not-blind`）——
  看着抄谁都答得上。

返回在 `GET` 的整份基础上多一个 `judge`：

```json
{ "judge": { "op": "recall", "ok": true, "code": "pass",
             "text": "想起来了：卡上结论覆盖 0.62。" } }
```

`demo`（示范）**只在没过且这个操作今天已经没过 ≥1 次时才出现**：
第一次没过只说他差在哪条线，第二次才给示范。第一次就给等于替他答，他会照着抄。

#### 错误码

| 码 | 意思 |
|---|---|
| `empty` | 这一题是空的 |
| `no-source` | 精简：没有原文可比（他最近没有超过 100 字的话） |
| `too-long` | 精简：压完超过 30 字 |
| `no-goal-word` | 精简：和卡上的目标没有一个共同关键词 |
| `off-topic` | 精简：和原文重合率低于 0.2（另起一件说） |
| `no-compress` | 精简：和原文重合率高于 0.9（照抄不是压缩） |
| `no-assertion` | 预判：没有一个可核对的断言 |
| `not-one-question` | 提问：问句不是恰好 1 个 |
| `yes-no` | 提问：是是非题（问完只剩两个答案） |
| `no-card-word` | 提问：和卡上的已知 / 结论没有一个共同关键词 |
| `no-card` | 卡上还没有可用的内容 |
| `not-blind` | 回想：作答时挂载卡没遮住 |
| `too-little` | 回想：卡上结论覆盖不到 0.3 |
| `bad-op` | `op` 不是四个之一 |
| `no-quota` | 今天的 6 题用完了（HTTP 200，`ok:false`） |

#### 账本与链路

- 每次判完记一行 `{ state:'drill-op', op, ok, code }`——**只有这三个字段，不存答案原文**。
  额度和链路都读账本，不记账下一题会一直卡在同一个操作。
- **不记这一笔会怎样**：`/plan` 每球都在问同一个操作，用户答了没人判，6 题额度当天耗尽，第二天重来。

#### 题目怎么出（挂在已有触发点上，不新建闹钟）

`/plan` 的出题槽位里，`drill`（九种思维题）与 `drillOp` **共用一个槽位、不叠着出**：
欠着的思维题（上一题没回 / 答糊弄了）优先补，没欠着才让「该练的那个操作」顶掉随机思维题。
额度用完、或者四个操作今天都过了，就不出。

#### 聊天里回球也算数

答案从聊天回来时（`session/event` 的 `user/message`），插件**按 `pending.drillOp` 走代码判**，
不走模型判球（`judgeReply`）。所以聊天里答对答错，和面板里答，判的是同一套 judge。
`setPending` 带过来的 `drillOp` 来自 `/plan` 回包的 `extra.drillOp`。

回给判球链路的 `verdict` 只用既有判词（过了 `engaged`、没过 `brief`），**不自造新词**：
自造词会污染六判词白名单，而这条路上的 `verdict` 还要进大脑记账。

#### 面板

`POST /sisters` 回包新增 `drillOps`（与 `op.stats` 同一张表，同一个窗口）。
`sisters_page` 在「〔墙〕今日审计」之后多一张「〔四个基本操作〕近 14 天」卡：
逐行 `通过 x/y（z%）`，没练过的行写「还没练过」而不是 `0%`。
这张卡**不能点**——没有答题页面，题在聊天里出、聊天里答。

### 8.1 新工具 `submit_prediction`（两个角色都有）

押一条到期会被证伪的预判。**这是唯一一处 `verdict` 不由模型写的地方。**

| 参数 | 说明 |
| --- | --- |
| `claim` | 一句能被证伪的话（≥6 字） |
| `dueInHours` | 几小时后判，1–168，默认 20 |
| `evidenceRefs` | 1–5 条，到时候拿什么撞它。**空数组直接拒收，不落盘** |
| `metrics` | 1–3 条判据，**全部成立才算说中** |
| `metrics[].metric` | 只能是 `file_growth` / `screenshot_count` / `app_minutes` / `fun_minutes` / `tasks_ratio` |
| `metrics[].op` | `>` `>=` `<` `<=` |
| `metrics[].threshold` | 数 |
| `metrics[].path` | `file_growth` 必填，文件路径（可相对笔记库） |
| `metrics[].app` | `app_minutes` 必填，App 名字 |

**参数里没有 `verdict`，也没有 `verdictSource`**——不是不让你填，是这条路不存在。
`verdict` 只由 `lib/predict.js` 的 `settle()` 按墙的遥测算出来，`verdictSource` 恒为
`WALL_TELEMETRY`。模型硬塞多余字段会被 schema 与 `checkClaim` 双重丢掉。

退回时 `ok:false`，`text` 里逐条列出问题，**不落盘**。

### 8.2 新状态文件 `companion/predict.json`

```json
{ "v": 1, "day": "2026-11-10", "seq": 1,
  "list": [{
    "id": "P-20261110-01",
    "claim": "明天会先折腾 UI 周边，把接口核心逻辑往后推",
    "createdAt": 1762..., "dueAt": 1762..., "day": "2026-11-10",
    "metrics": [{ "metric": "file_growth", "op": "<", "threshold": 300,
                  "path": "/…/大肥鱼/周报.md", "baseSize": 1000 }],
    "evidenceRefs": ["审计/2026-11-11.md"],
    "verdict": null,
    "verdictSource": "WALL_TELEMETRY",
    "settledAt": 0,
    "readings": null,
    "revision": null
  }] }
```

`verdict` 的取值只有三个：

| 值 | 含义 |
| --- | --- |
| `null` | 还没到期 |
| `hit` | 全部判据成立 |
| `miss` | 任一判据不成立 |
| `unknown` | 到期了但遥测里量不到（没定任务、App 没记录）。**没有证据不算说中，也不冤枉他** |

`file_growth` 的 `baseSize` 是**立项那一刻**的字节数，之后只量增量——和墙审文件的
口径完全一致（`wall_auditor.js` 的 `GROWTH_MIN_BYTES = 300`）。

### 8.3 新状态文件 `companion/vibe.json`

```json
{ "v": 1, "turn": 42,
  "last":   { "innerOS": 41, "temper": 40, "samples": 41 },
  "streak": { "innerOS": 2,  "temper": 1,  "samples": 1 } }
```

`turn` 是轮次（只增），`last[arm]` 是这个 arm 最后一次被抽中的轮次（Cooldown 用），
`streak[arm]` 是连着被抽中的次数（Sticky 用）。**`brain.json` 的 `arms` 才是 win/lose 账本**，
两者不要混。

### 8.4 `brain.json` 新增 `arms` 表

```json
{ "arms": { "innerOS": { "win": 3, "lose": 1 }, "samples": { "win": 0, "lose": 4 } } }
```

7 个 arm 各自独立记账（`innerOS` / `temper` / `samples` / `keywordCard` / `prediction` /
`ironSplit` / `depth`），**绝不按组合记账**。只给这一轮真被抽中的 arm 各记一次。
旧的 `faces` / `drills` / `hours` 三张表一字未改，`betaSample` 一行未改。

### 8.5 `ledger.jsonl` 新增两种行

| `state` | 什么时候写 | 关键字段 |
| --- | --- | --- |
| `predict-new` | 交上一条预判 | `by`（companion/strategist）、`id`、`claim` |
| `predict` | 结算了一批到期预判 | `settled: [{id, verdict}]` |
| `vibe` | 每轮注入素材 | `seed`、`turn`、`picks: [{group, arm, sampled, sticky}]`、`betaVersion`、`role`、`at` |

`vibe` 这一行是排查用的**注入快照**：真机上"人设前后不一致"时翻它，
能直接看到那一轮到底注入了哪几个 arm、采样值多少、当时账本是哪个版本——不用猜。

### 8.6 `temper.json` 的形状变了（是个 bug 修复）

以前只存 `{edge, at}`，把 `face / label / rule / surprise` 丢了，导致五档脸色的
**说话规则从没进过 prompt**。现在整份存：

```json
{ "edge": 0.42, "at": 1762..., "face": "cool", "label": "冷",
  "rule": "话少、平、不带情绪，像在等他自己意识到。一句就够。", "surprise": false }
```

读旧文件不会炸（缺字段时 `temperLine()` 返回空串）。

**这是本轮最大的行为变更**：五张脸从"无效"变成"有效"。真机上如果觉得情绪跳得太突然，
先查这里，再查 `vibe.json` 的 `streak`。

## 9. 第六轮 B 层：三个审查锚点（早 / 晚 / 周末）

早、晚、周末各一次审查，**全部由墙主持**，复用同一条链路（`submit_to_wall` 工具 + `/wall` 路由 +
`wall_auditor.js` 的纯函数判定），没有第二个审查入口。

### 9.1 新增一种 kind：`week`

`submit_to_wall` 的 `kind` 枚举新增 `week`（周度审查）。它和 `evening` 是两件事：

| kind | 审什么 | 什么时候能交 | 下不下发锁 |
| --- | --- | --- | --- |
| `evening` | 今天这一天 | 21:30–23:30 | 是（原有） |
| `week` | 这一周的客观数字 + 下周重心二选一 | 周日晚 20:00–23:30，当周一次 | **否** |

`week` 交过就把门关上（`rhythm.json` 的 `weekDone = true`），同一晚不会重复交。
它**不进** `followup.js` 的 `VERDICT_KINDS`，所以不能通过 `submit_verdict` 走裁决锁。

### 9.2 `rhythm.json` 新增三个字段

| 字段 | 含义 |
| --- | --- |
| `weekDay` | 本周周末审查挂在哪个当地日（`startOfDay` 的毫秒值） |
| `weekSince` | 门开的时刻 |
| `weekDone` | 当周是否已审过；`true` 后当周不再开 |

旧文件读进来是 `{}`，缺这三个字段不影响早晚两次与深夜锁。

### 9.3 `trackRhythm()` 的签名与返回值

新增入参 `weekday`（0=周日 … 6=周六，由 `tz.js` 的 `weekdayOf(now, tz)` 算，也可直接用 `tz.js` 的
`weekdayOf`）。新增返回 `weekReviewGate`（这一轮该不该做周度审查）与 `openWeek`（这一轮刚开门，
写一条 `gate-open`）。

**`morningGate` 仍然要求亮屏**，这是有意的：门开的那一刻是对账的起点，晚起的人一解锁就能开始；
去掉它会让门固定在 7:00 开、7:30 过期，11 点起床的人再也看不到立项。
"他没来也算审过"由 9.4 的缺席记录兜底，不靠强推这道门。

### 9.4 `ledger.jsonl` 的 `wall-audit` 行新增 `absent`

到点还没有结论时，墙按账本补一条缺席记录，**只记账、绝不 `applyVerdict`**
（不加锁、不罚、不扣额度）：

```json
{ "v": 1, "state": "wall-audit", "at": 1762..., "kind": "morning",
  "pass": false, "absent": true, "by": "wall",
  "missing": ["今天没有立项记录，标准没定，晚上就无从撞"] }
```

判定是纯函数 `rhythm.js` 的 `absentAnchors(min, weekday, seen)`：

| 锚点 | 到点 | 补记条件 |
| --- | --- | --- |
| `morning` | 当地 12:00 | 当天还没有任何 `wall-audit{morning}` |
| `evening` | 当地 23:30 | 当天还没有任何 `wall-audit{evening}` |
| `week` | 当地 23:30 且是周日 | 当周还没有任何 `wall-audit{week}` |

补记在 `/plan` 里做（紧跟预判结算之后），所以手机每次问都会经过它；同一天不会重复补。

### 9.5 `/status` 新增 `anchors`

```json
{ "anchors": {
    "morning": { "at": 1762..., "pass": true, "absent": false },
    "evening": null,
    "week": null } }
```

三个键**恒定存在**，`null` 表示"今天这一次还没有任何结论"。面板据此一眼看出哪一次漏了——
这是"静默失效"唯一的可查出点：缺席会有记录，记录不会消失。

### 9.6 一条踩过的坑：系统产出不能混进"最近改过的笔记"

`anchorSweep` 会把缺席写成 `大肥鱼/墙/审计/<今天>.md` 的一行（为了留痕给人看）。
但这些审计文件是**系统产出**，不是他写的笔记。`vaultRecentNotes()` 是球的话题素材源，
原来只排除 `每日/`、`记忆.md`、`长期规划.md`，没排除审计目录——
结果审计记录 mtime 最新，把真笔记挤出前三，球发出去的话题就变成了
"〔墙〕晨间立项：缺席——今天没有立项"。

现在 `vaultRecentNotes()` 也排除 `大肥鱼/墙/审计/`。规矩是：

- **写盘之前先问：谁会读这个文件？** 新增一类自动写入，必须检查它会不会挤进
  「最近改过的笔记」「最近的判断」「记忆」这类**由内容决定话题**的读取方。
- 留痕该写还是要写（`vaultAudit` 不动），要修的是**读的一侧**，不是写的一侧。
- 审计原文照旧给姐妹页用（`sisters.js` 的 `auditOf` 直接读 `<今天>.md`，不走 `vaultRecentNotes`），
  所以排除它不影响"墙的今日审计"显示。

## 10. 第六轮 A：支线底座（通用槽位 + 一页配置）

一条「支线」= 一个练习方向。**底座只认四个固定槽位，具体是哪个方向一个字都不进代码**，
方向内容全在 `config.tracks` 这一页配置里。所以加第三条支线只改配置（引擎层 diff = 0），
把所有支线清空则底座全部返回空、主干链路不受影响。

### 10.1 槽位协议（改这个数组等于改协议）

| key | 中文名 | 含义 |
|---|---|---|
| `scene` | 触发场景 | 什么时候这条支线起作用 |
| `first` | 第一反应判断 | 他下意识给出的那个判断 |
| `missed` | 漏掉的条件或反例 | 这个方向最常被跳过的前提，或最典型的反例 |
| `blind` | 盲区标签 | 一句话给这个盲区命名 |

### 10.2 `config.tracks`（一页配置，数组）

```json
{ "tracks": [
    { "id": "t1", "name": "（方向名）", "enabled": true,
      "scene": "……", "first": "……", "missed": "……", "blind": "……" } ] }
```

- **四条槽位缺任何一条（或只有空白），整条丢掉**，不做"缺的用默认补上"。
- `enabled: false` 才算关掉；**写错类型（如 `"no"`）不当成关**。
- 同时生效上限 6 条，超出部分截断并在 `over` 里报出来，不静默。
- 单项内容超 200 字截断并加 `…`（防止一页配置把上下文挤爆）。

### 10.3 `POST /dsh-go-companion/v1/tracks`

不带 `tracks` → 只读状态；带 `tracks` 数组 → **整页替换**。

```json
{ "v": 1, "ok": true, "count": 2, "max": 6, "recent": ["t1"],
  "tracks": [ { "id": "t1", "name": "…", "blind": "…" } ],
  "dropped": [ { "id": "x", "reason": "slot-missing", "missing": ["盲区标签"] } ],
  "over": [], "slots": [ { "key": "scene", "label": "触发场景" } ] }
```

`dropped[].reason` 只有两种：`slot-missing`（带 `missing` 数组）和 `disabled`。

**一条都没合格却又确实给了非空数组**时返回 `ok:false` + `error.code = "no-valid-track"`
并带上 `dropped`，**不清空现有配置**——这十成是写错了。

### 10.4 `/status` 新增 `tracks`

与 `10.3` 的只读形态同构。`count = 0` 是正常状态（全部关掉），不是错误。

### 10.5 挑法与记账

- 与思维题同一套"最近用过的三条避开"（`recentTracks`，只认 `ledger.jsonl` 里
  `state === 'generated'` 且带 `track` 字段的条目，新→旧）。
- 挑中的支线 id 写进那一球的 `extra.track`，和 `extra.drill` 并列。
- 判定只吃三个 bool（`sceneHit` / `firstHit` / `missedHit`），**不听自述**：
  少给字段一律不算中，默认不放水。


## 11. 第六轮 C：暗思考（只整理、不开口）

后台独立的一层：**按固定节奏自己跑**，不依赖任何用户消息，整理当下的客观变化，
写进账本供三次审查取用。**它不产生任何要发出去的话**——没有浮层、没有通知、没有发球。

### 11.1 触发面（唯一的，别再加第二个）

挂在 `POST /v1/plan` 里（`lib/index.js` 的 `planRoute`），和 `anchorSweep` 同一条路。
原因是引擎里**手机闹钟问 `/plan` 是唯一的"后台"触发面**（`features_api.dart` 写明
`schedule_create` 只能模型创建、Host 无创建面）。**手机不问就不跑**，与审查锚点同一限制。

单次运行是纯函数，不调模型：判定层不许模型自己写结论（红线 §3.9/§3.10）。

### 11.2 节奏与上限（写死在 `lib/muse.js`）

| 常量 | 值 | 作用 |
|---|---|---|
| `MUSE_MIN_GAP_MS` | 45 分钟 | 两次之间最短间隔，防止空转 |
| `MUSE_MAX_PER_DAY` | 12 | 每天上限，超了当天不再跑 |

### 11.3 输入：只吃白名单字段（隐私线）

只从 `cleanPhone()` 的返回里取这几个：`app` / `minutes` / `fun` / `screenOn` /
`charging` / `local` / `switches` / `today[]`。

**屏幕上的字一个都不进来**：`text` / `title` / `ocr` / `content` / 通知内容这类字段
即使被塞进来也不会进快照（有单测守）。单个 App 时长上限 1440 分钟。

### 11.4 什么算"有变化"（五条，全是客观量）

`app` 换前台 / `screen` 亮熄变化 / `minutes` 任一 App 今日时长涨 ≥5 分钟 /
`switches` 15 分钟内切屏涨 ≥3 次 / `hour` 跨整点。差一档不算。

今天第一次跑（没有前一次）本身算一条，`why = ["first"]`——这是可查的起点。
**一条都不满足就不产出，也不写空账。**

`why` 的取值范围只有这六个：`first` / `app` / `screen` / `minutes` / `switches` / `hour`。

`museDue` 内部还有两个"这次不跑"的原因：`too-soon`（离上次不到 45 分钟）、
`daily-cap`（今天已满 12 次）。这两个**只用于内部判定，不写进账本**——
账本里只会出现真的跑过的那条。

### 11.5 账本记录

```json
{ "v": 1, "state": "muse", "at": 1794294699397,
  "why": ["app", "minutes"],
  "summary": "14:30 · 前台是 com.example.reader（已用 40 分钟）；亮屏",
  "next": "换了前台：…，审查时可以问这段时间拿到了什么。",
  "signal": { "at": 0, "local": "14:30", "app": "…", "minutes": 40,
              "fun": false, "screenOn": true, "charging": false,
              "switches": { "m15": 4, "h1": 12 }, "today": [ … ] } }
```

键就这六个：`state` / `at` / `why` / `summary` / `next` / `signal`。
**`muse` 不在 `summarize` 的计数白名单里**，所以它既不参与发球判定、
也不会被当成"最近聊过的话题"而误静音。

### 11.6 `/status` 新增 `muse`

```json
{ "muse": { "today": 3, "max": 12, "minGapMs": 2700000,
            "last": { "at": 0, "summary": "…", "next": "…", "why": ["app"] } } }
```

`last` 为 `null` = 今天还没跑过（正常，不是错误）。


## 12. 第六轮 D：姐妹自建工作流的护栏

她能自己提议、自己搭新工作流，但护栏在**能力层**（`lib/workflows.js`），不靠提示词劝。
路由**另起**：`/v1/workflows`，与现有两套乒乓和 `/drill` 彻底隔离。

### 12.1 一个工作流长什么样

```json
{ "id": "w…",
  "problem": "解决什么问题",
  "evidence": "账本证据（引哪条、哪个数）",
  "trigger": "什么时候触发",
  "ask": "对用户的要求",
  "metric": "可数的成功指标",
  "judge": "7 天后怎么判",
  "uses": ["vault_search"],
  "state": "proposed",
  "at": 1794294699397 }
```

六项**缺任何一项就整条否决**（`code = "field-missing"` + `missing` 数组），
不做"缺的用默认补上"。单项超 200 字截断加 `…`。

`state` 只有四态：`proposed`（等她提议完等他点）→ `trial`（他点了「试」）→
`running`（转正）→ `stopped`（停了）。

### 12.2 能力层闸门 `workflowGuard(capability, args)`

**默认关门**（不在白名单一律拒），三道判定按顺序：

| 命中 | `code` | 说明 |
|---|---|---|
| 墙/力度/信用分/权限/规则文件（`WALL_CAPABILITIES` 16 项） | `wall-forbidden` | 明着列出来，让"被拒"可测可查 |
| `args.path` 命中私密目录（`/data/data`、`Android/data`、`obb`、`.ssh`、`DCIM`、`private`） | `private-path` | 连路径都不许出现 |
| 不在 `WORKFLOW_ALLOW` 白名单 | `not-allowed` | 白名单只有 7 项：`companion_topic`、`sister_note`、`notes_vault`、`vault_search`、`vault_recent_notes`、`kb_write`、`gemini_log` |

`uses` 里**只要有一条被拒，整条提议否决**（`code = "capability-refused"` + `rejected` 数组）。

### 12.3 配额

| 限制 | 值 | 拒绝码 |
|---|---|---|
| 每周最多提议 | 1 条（按自然周，周一为界，数账本 `workflow-proposed`） | `week-quota` |
| 同时在跑（`trial` + `running`） | ≤3 条 | `running-quota` |
| 同一个 `problem` 不重复提（`stopped` 的不算） | — | `duplicate` |

「满了先停再加」：配额满了直接拒，不做排队或自动挤掉。

### 12.4 `POST /dsh-go-companion/v1/workflows`

不带 `action` → 只读（返回 `12.6` 的形态）。
所有写动作都返回 `{ v, ok, workflows, ... }`；失败返回 `ok:false` + `error.code`。

| `action` | 参数 | 做什么 |
|---|---|---|
| `propose` | 六项 + `uses`（或包在 `workflow` 里） | 校验 + 配额 + 闸门，过则落成 `proposed` |
| `trial` | `id` | 他点「试」：`proposed` → `trial`，记 `trialAt` |
| `stop` | `id` | 手动停（`stopReason = "user"`） |
| `effect` | `id` + `count`（必须 > 0） | 记一次可数效果 |

**被拒也留痕**：`propose` 被拒时账本写 `workflow-refused`（带 `code` / `missing` / `rejected`），
验收要查得到"墙的能力被拒"这件事真的发生过。

`effect` 的 `count <= 0` 一律拒（`code = "no-count"`）——**空转不算效果**。

**全部拒绝码**（`lib/workflows.js` + 路由层，共 16 个，实现与本节一致）：

| `code` | 什么时候 | 带什么 |
|---|---|---|
| `wall-forbidden` | 命中 `WALL_CAPABILITIES` | `capability` |
| `private-path` | `args.path` 命中私密目录 | `capability` |
| `not-allowed` | 不在 `WORKFLOW_ALLOW` 白名单 | `capability` |
| `no-capability` | 能力名是空的 | — |
| `capability-refused` | `uses` 里有一条没过闸门 | `rejected[]` |
| `field-missing` | 六项缺项 | `missing[]` |
| `manual-action` | `ask` 里要用户手动做 | — |
| `not-an-object` | 传进来的不是对象 | — |
| `week-quota` | 本周已提过 1 条 | `quota` |
| `running-quota` | 同时在跑已 3 条 | `quota` |
| `duplicate` | 同一个 `problem` 在跑 | `workflow` |
| `not-found` | `id` 找不到（`trial`/`stop`/`effect`） | — |
| `bad-state` | 状态不允许这个动作（如已 `trial` 再 `trial`） | `state` |
| `bad-action` | `action` 不认识 | `action` |
| `no-count` | `effect` 的 `count <= 0` | — |
| `save-failed` | 写配置失败（这条不算数） | — |

### 12.5 到期处理（挂在 `/plan` 上，不自建调度器）

在 `planRoute` 里跑 `workflowSweep`，和暗思考、审查锚点同一条路：

| 状态 | 到期条件 | 有可数效果 | 没有 |
|---|---|---|---|
| `trial` | `now - trialAt ≥ 7 天` | → `running`，账本 `workflow-promoted` | → `stopped`，`stopReason = "no-effect-7d"` |
| `running` | `now - promotedAt ≥ 30 天` | 续期（`promotedAt = now`），账本 `workflow-reviewed` | → `stopped`，`stopReason = "no-effect-30d"` |

"有可数效果" = 账本里存在 `state === "workflow-effect"` 且 `workflowId` 相同、
`at ≥ 窗口起点`、`count > 0` 的记录。差 1 毫秒都不提前处理。

## 13. 第七轮 B4：情绪池与连发

情绪是**账本的纯函数**，不新增状态文件：`lib/emotion.js` 的 `emotionOf(entries, opts)` 从
`ledger.jsonl` 的既有条目重建四根轴（耐心/在意/火气/兴致），重启不丢、也不会出现
"状态文件和账本各记一半"。它**不参与任何锁、额度、判定**——只决定「怎么把这句话说出去」。

### 13.1 `/request` 回包的 `extra.burst`

生成出来的那一球，`/result` 的 body（以及 `/request` 回包）在 `extra` 里带一份连发计划：

```json
{ "v": 1, "state": "generated", "text": "全文…", "extra": {
    "burst": { "tone": "hot", "burst": 2, "maxChars": 60,
               "delayMs": [4000, 7000], "channel": "voice" },
    "emotion": "[情绪] 火气 62（敷衍了 3 次）· 耐心 31" } }
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `burst` | `1`–`3` | 这一轮分成几条说完。`1` = 一次说完，手机侧不分段 |
| `maxChars` | 正整数 | 单条上限。**手机侧不许把一句话从中间截断** |
| `delayMs` | 数组，长度 2（取值下标 `0..burst-2`） | 第 2 条起每条之前的间隔（毫秒） |
| `channel` | 只有 `text` / `voice` | `voice` = 这几条还要念出来（念在 B5，未接时照样分段上屏） |
| `tone` | `calm`/`flat`/`poke`/`eager`/`hot`/`blaze` | 档位标签，只给面板和排查看 |

`emotion` 是**一行已经拼好的中文**（和状态层那一行同源），不是结构化对象——手机侧只显示，不解析。

- `text` **始终是全文**。`burst` 是「怎么发」，不是「发什么」：分段之后拼起来等于 `text`。
- **`channel` 不拦连发**：火气最高的三档（`hot`/`blaze`/`eager`）都是 `voice`，按 channel 拦会让
  「火气高 → 连发 2–3 条」这个核心场景永远不触发。
- 硬上限：每小时总条数 ≤ `12`（`BURST_HOURLY_CAP`，按账本里各球 `burst.burst` 累加），
  安静时段 `burst = 0`（不连发，也不发）。
- 账本每一球会记下当时的 `burst` 与 `emotion`，所以「火气为什么高」可以从账本复算。

### 13.2 手机侧（Kotlin）怎么用它

`AgentWire` 解码时把 `extra.burst` 解析成 `BurstPlan`（`loop/core/BurstPlan.kt`），
随 `AgentReply.Generated` → `Content.burst` 到投递层：

- 只有拿到 `extra.burst` 且能切出 ≥ 2 段时才排队；没有就还是原来的一次说完。
- 第一段立刻上屏，第 2 段起按 `delayMs` 追加到**同一个浮层**（`ProactiveOverlay.say`）。
- 窗口已经不在了就直接丢掉这一段，不另开一个窗口补白。
- 只走浮层：`ProactivePageActivity` 是一次性页面，追加不了话，回退时整段发一次。
- 连发计划**不持久化**（`CoreCodec` 只存 `text`/`source`/`agentTurnId`）：进程重启后再恢复出来
  已经晚了，整段发一次正好是这个行为（读回来 `burst` 为 `null`）。

### 13.3 情绪以一行进状态层

`chatPersonaText` 的状态层里多一行（`priority 48`，可被挂载卡/信用/作息挤掉）：

```
[情绪] 火气 62（敷衍了 3 次）· 耐心 31
```

只在有非日常值时才出现；四根轴都回到日常值就不写这一行。

### 13.4 `extra.emotion` 的边界

- 情绪**不许**影响锁、额度、判定：`emotion.js` 不被 `wall*.js`、`force.js`、`machine.js`
  import（源码扫描测试 `H1–H3` 守住），反过来也一样。
- 不许说伤害性的话：情绪只在人设卡「能说多狠」的上限内移动，`toneOf` 不改变上限。

## 14. 夜间整理（B2）

暗思考分两层，别混：

| 层 | 文件 | 调不调模型 | 出口 |
|---|---|---|---|
| 客观整理 | `muse.js` | **永不调** | 只写账本 `state:'muse'`，不发消息 |
| 夜间整理 | `nightly.js` | 调 | 只产出 `links/gaps/carry`，**不发消息** |

`muse.js` 那四条硬边界（不依赖用户消息、不读屏幕文字、不发消息、无变化不产出）一条都没动。
两侧互不 import（源码扫描 `N33/N34` 守住）。

### 14.1 触发

- 每天两次，按当地时区：`NIGHTLY_SLOTS = [13, 22]`，每个槽宽 2 小时（`NIGHTLY_SLOT_SPAN`）。
- 挂在 `/plan` 上（引擎里没有第二个后台面，和 `museSweep`/`anchorSweep` 同一限制）。
- **对话中不跑**（`inConversation`）、**一天最多 2 次**、**同一个槽只跑一次**、**不并发**
  （`nightlyRunning` 挡住 `/plan` 被频繁问到的重入）。
- 异步跑，`/plan` 不等它 —— 它绝不许把发球路径拖住。

### 14.2 模型通道：**不占会话**

走 `ctx.inject(['llm'])` 拿到的 `llm.stream`，和判球（`judgeReply`）同一条通道：

```js
stream({ provider, model, system, messages, maxTokens: 1600, temperature: 0 })
```

这就是为什么它「产物不是消息」：

- **不经过 `chat`/`desk`**：整理的内容一个字都不会变成聊天记录里的一条用户消息，
  也不占会话上下文（`N33` 扫源码守住：`nightly.js` 不 import `core.js`、不出现 `.request(`/`.wait(`）。
- 代价：这条通道**没有工具面**。所以「每次整理工具调用 ≤ 5 次」在结构上是 **0 次**，
  不是靠模型自觉；`nightlySystem()` 明写「你手里没有工具」。
  要真给工具只能走 `desk` 通道，代价是那一轮会以一条用户消息的样子出现在会话里——本轮不选它。

模型路由：`config.nightlyProvider` / `config.nightlyModel` 单独配；没配就跟会话自己的模型
（和判球同一套优先级）。

### 14.3 输入只有索引

```js
nightlyInputs({ entries, candidates, stances, notes, tz }, now)
// → { at, dayStart, counts, objects: [{ id, kind, label }], ledgerLines }
```

- `objects` 是**唯一允许被引用的 id 表**，最多 24 条（`NIGHTLY_OBJECTS_MAX`），`label` 切到 60 字：

| id 形态 | 来源 |
|---|---|
| `topic:<id>` | 记忆库 `topics`（标题） |
| `fact:<id>` | 记忆库 `facts`（钉住/重要） |
| `event:<at>` | 记忆库 `episodes` |
| `stance:<id>` | 立场账本里 `status='held'` 的 |
| `note:<相对路径>` | 笔记库**今天改过**的文件名（只给文件名） |

- **不给原文**：笔记正文一个字都不进去。`counts` 是今天账本的条数摘要。
- `ledgerLines` = 这次交给模型的账本行数，`carry.evidence` 的行号上限就是它。

### 14.4 产物与校验

```json
{ "links": [{"a":"<id>","b":"<id>","why":"≤40 字"}],
  "gaps":  [{"about":"<id>","missing":"≤40 字"}],
  "carry": [{"text":"≤60 字","evidence":[1]}] }
```

- 每类最多 3 条（`NIGHTLY_ITEMS_MAX`），超出的**丢**，不排队、不截成半条。
- 整段不是 JSON → 失败（不重试）；单条不合格 → 只丢那一条（`N12`–`N16`）。
- **证据绑定（代码说了算）**：
  - `links`/`gaps` 的 id 必须在 `objects` 里，不在就丢；
  - `carry.evidence` 必须是存在的账本行号（1 起），或一句能在账本里对上的原话
    （**少于 4 个字不算证据**，和 `stance.js` 的 `resolveEvidence` 同一口径）；
  - 解析不到的条目直接丢，`resolveNightly().dropped` 记账（`N17`–`N20`）。

### 14.5 存放与衰减

状态文件 `companion/nightly.json`（只在本插件自己这侧，**不写 fish-memory**）：

```json
{ "v": 1, "items": [ { "kind": "links|gaps|carry", "...": "…",
    "madeAt": 0, "until": 0, "usedAt": 0, "used": 0, "day": "" } ] }
```

- 每条 `until` 默认 `+3 天`（`NIGHTLY_TTL_MS`）；`until <= now` 就不是活的了。
- 同一条再整理一次是**刷新 `until`**，不是堆第二条（按内容 key 去重）。
- 被用过一次续期（`touchNightly`），没用过的到期就没了。
- 每类活着的封顶 3 条，留最新的。

> 为什么不写进记忆库：`fish-memory.sqlite` 里**没有关联表**——`facts` 只有 `kind`/`tags`，
> `topics`/`episodes` 也没有关系列（见 `dsh-go-memory/lib/store.js` 的 DDL）。
> 跨插件事务写别人的库不归这个插件的职责，所以 `links` 留在 `nightly.json` 自己这侧。
> 这是**已知的与工单字面的差异**，写在 `第七轮进度.md` 的 B2 一节「没做到的」里。

### 14.6 三个去向

| 产物 | 去哪 | 怎么生效 |
|---|---|---|
| `links` | B3 的 `keywordCard` | `linkWords()` → `renderVibe({ keywords })` 的 `links` 参数（此前一直传 `[]`） |
| `gaps` | C 组出题 | `gapTexts()` → `buildPrompt({ gaps })` → `opLines(op, gaps)` 多点一句「往这个缺口上出」；**合格线仍在代码里，不受缺口影响** |
| `carry` | B3 的 `innerOS` arm | `carryTexts()` → `renderVibe({ carry })`，接在 `INNER_OS` 后面 |

另外 `nightlyLines()` 出**一行**（`cap 240`）进 `chatPersonaText` 的内容层
（`id: 'nightly'`，`priority 16`，可裁）：

```
（这是你自己整理的底稿，不是要你现在说出去的话，合适的时候用）关联：… 。没交代清楚的：… 。你自己记着：…
```

### 14.7 `/status` 多一块

```json
{ "nightly": { "today": 1, "max": 2, "slots": [13, 22], "lastAt": 0,
               "live": { "links": 1, "gaps": 1, "carry": 1 } } }
```

`live` 只数还活着的（`until > now`）。账本里每次整理留 `state:'nightly'`

## 15. 第七轮 B5：念出来（系统 TTS）

第一步只做**系统 TTS**：不联网、不花钱、今天就能用。云端语音只写调研，不选型（见 15.7）。

这条工单的分界线是「能算的在插件、能看的在手机」：

| 归谁 | 判什么 | 为什么 |
|---|---|---|
| 插件 `lib/emotion.js` | 总开关、安静时段、渠道、语速、音高、单条字数 | 全都能从账本算出来，能写真断言 |
| 手机 `VoiceOut.kt` | 媒体音量为 0、勿扰、连麦舱、TTS 引擎在不在 | 只有手机知道；本机测不了，所以挤到极小一块 |

### 15.1 `/result` 回包的 `extra.voice`

和 `extra.burst` **并列**，不是它的字段：

```json
{ "v": 1, "state": "generated", "text": "全文…", "extra": {
    "burst": { "tone": "hot", "burst": 2, "maxChars": 60, "delayMs": [4000], "channel": "voice" },
    "voice": { "rate": 1.15, "pitch": 1, "maxChars": 60 } } }
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `rate` | `1` 或 `1.15` | 语速倍率。火气 ≥ 60（即 `hot` 档）时快 15% |
| `pitch` | `1` 或 `0.9` | 音高倍率。兴致 ≤ 25（即 `flat` 档）时低 10% |
| `maxChars` | 正整数，≤ 60 | 念出来的单条上限，取「档位字数」与 `VOICE_MAX_CHARS=60` 里小的那个 |

**为什么另起一个键而不是塞进 `burst`**：`burst` 在「每小时连发额度只剩 1 条」时是
`burst: 1`，手机侧的 `BurstPlan.of()` 对 `burst < 2` 直接返回 `null`——把 voice 放进去，
这一条就永远念不出来。两件事各有各的生命周期。

### 15.2 三道闸（都在插件侧，都是代码判）

`lib/emotion.js` 的 `voiceOf(emotion, {enabled, quiet, channel, stage})`，返回 `null` 就是不念：

1. **总开关** `config.voice`，默认 `false`。不开就只是浮层，手机一句都不出声。
2. **安静时段**：`burst=0` 的那段时间一条都不念（不是「小声念」）。
3. **渠道**：档位是 `voice`（`hot`/`blaze`/`eager`），**或者**漠视阶梯走到了
   `stage='channel'` 那一级。后者是 `silence.js` 从第四轮就写进账本、一直没人接的那个意图。

调子只有两个旋钮，且都取在 `toneOf` 已有的档位门槛上，不按数值连续插值：TTS 的语速/音高
是可听的整数档，连续插值的听感差不出来，测试也没法说清「62 分和 65 分该差多少」。

### 15.3 手机侧 `VoiceOut.gate()` 的降级

`loop/proactive/VoiceOut.kt` 的 `gate(Gate)` 是个吃三个布尔的纯函数，顺序即优先级：

| 条件 | `why` | 为什么在这个位置 |
|---|---|---|
| 连麦舱内 | `session` | 出声会真的打断 Gemini 那边的对话，第一顺位 |
| 勿扰 | `dnd` | 改音量也救不回来，所以压过音量 |
| 媒体音量 0 | `muted` | |
| 引擎没起 / 语言不支持 / 说不出 | `no-tts` | 在 `speak()` 那条路径里判，不在 `gate()` 里 |

**总开关刻意不在这里**：关着插件根本不下发 `extra.voice`，手机再存一份开关就多了一个会和
插件对不上的状态。安静时段同理。

读不到服务（没起、没权限）时一律按「勿扰 + 静音」处理——宁可退回文字，也不在她开会时突然出声。

### 15.4 念什么

`VoicePlan.brief(text)`：不超过 60 字就整条念；超过就截在**第一个句读点**上（`。！？；`
换行 `!?;`），往后 60 字内没有句读点才硬截。不从一句话中间切断，比少念半句更难听。

连发（`burst ≥ 2`）时**只念第一段**：`QUEUE_FLUSH` 会把前一段掐掉，几秒内连念三条听着像抢话。
后面几段只上屏。

### 15.5 账本记 `voice-out`

手机念完（或不念）回报一次 `POST /event`：

```json
{ "v": 1, "type": "voice-out", "requestId": "<球的 token>",
  "ok": false, "why": "dnd", "chars": 18, "rate": 1.15, "pitch": 1 }
```

- `ok` 只在 TTS 的 `onDone` 之后才为 `true`：`speak()` 返回 `SUCCESS` 只是「引擎收下了」，
  那时还没出声。所以「有没有真的念出来」这个问题的答案是可信的。
- `why` 缺省写 `unknown`；`ok=true` 时不写 `why`。
- 这条**不进任何判定**：`silence.js` 只认 `generated`/`replied`/`human`/`said`，
  `emotion.js` 只认 `replied`/`defied`/`stance-settled`，所以记在同一个 `requestId`
  下面也不会被当成「他回过话了」（`test/voice.test.mjs` V16 守着）。

### 15.6 设置页

`主动设置 › 大肥鱼自己的参数` 里两行：

- **念出来**：点一下切换 `念` / `不念`，写插件的 `config.voice`（`POST /config`）。
  和「说话模式」一样是点击换档，不是 `Switch`。
- **试听一下**：走 MethodChannel `voiceTry`，绕开总开关（关着也能试），回 `null` = 念完了，
  否则是上表里的降级原因。
