# 计划编译器（统一计划模态 v3）· Claude 评审结论与 P0 落地（2026-11-20）

> 评审对象：《2026-11-20 · 大肥鱼「统一计划模态 × 长期战役体系」技术方案（v3）》。基线 fish-build-195。
> 结论：方向对，痛点准；三处与代码不符，已在 P0 里按下面改过来。P1 / P2 按本文的取舍继续。

## 一、方案里与代码不符、必须改的三处

1. **`horizons.js` 的 `cleanHorizons` 是字段白名单**：新加的 `nodes` / `resources` 每次读写都会被洗掉。
   P0 已扩展 `cleanHorizons`（`cleanNode` 逐字段清洗、条数上限），并加了测试。
2. **两套进度会打架**：老的 `doneSteps/targetSteps`（手动 +1）和节点达成数。
   P0 定规矩：**有节点的目标，进度 = 达成节点数 / 节点总数，自动推导**（`withDerivedProgress`）；老的 `bumpStep` 对有节点的目标不再生效。
3. **编译器不发明放行规则**：方案让 `compileBoutFromNode` 在 `video_extract` 下临时放行娱乐 App——
   这条逻辑契约（`plan_modality.js`）里已经有一份，含「逾期 1 分钟剔除视频 App」。编译器再写一份，就又是两套锁规则。
   P0：编译器**一律剔掉娱乐 / 游戏层 App**（I13），并把剔掉了哪些告诉他；要边看网课边记，走契约。

另外确认了一点方案是对的：`work.json` 按天清空，所以节点里的 `executionLog` 是唯一历史，必须存。

## 二、五个争议的取舍

| # | 争议 | 结论 |
|---|---|---|
| 1 | 契约页要不要并进局 | 终局同意（契约 = 局的一种验收配置），**P2 做**；先让节点能生成契约 |
| 2 | JSON 还是 SQLite | **JSON**。10 目标 × 16 节点 × 30 条 ≈ 4800 条，几百 KB；SQLite 会把两个插件绑死 |
| 3 | 资源怎么自动采 | **AI 工具为主**（只有它判得了采纳 / 否决）；规则提取只抓**他自己发的** URL / 笔记路径，模型输出里的链接不抓（会编）；候选 7 天不确认自动消失；不弹气泡 |
| 4 | 重排全自动还是半自动 | **半自动**（预览 → 他点确认）；姐妹可以提醒，但走现有主动发球通道、每天最多一次；重排**不碰锁**（推迟后面的局不解当前这局） |
| 5 | P0 够不够小 | **不够**。资源 Tab 挪到 P1（没有采集机制时它是空的）；P0 只做节点主干 |
