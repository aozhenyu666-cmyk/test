## 1. 总体判断：方向对，需要局部修正；有一个结构性风险

方向对的地方：程序负责节奏、期限和状态，模型负责内容，小满退回陪伴角色。保存本人回答和防止旧结果覆盖新任务这两部分做得扎实（见第 5 节）。

**结构性风险：按现在的代码，系统默认是沉默的，强约束在结构上不可能触发。** 如果不改，最后会退化成"需要自己打开、自己点按钮的问答笔记"，正是报告第 2 节担心的那种偏航。证据：

1. 观测器把三类覆盖范围写死为 `partial`（`toolpkg/device-observer.js` 末尾 `coverage` 对象），而提出限时约束的前提之一是三类覆盖都为 `complete`（`toolpkg/control-plane.js` 中 `propose_timed_restriction` 分支）。所以无论配置什么，`propose_timed_restriction` 都不会出现。【代码确认，已复现】
2. 小满账本里的每一条"暂停"都被读成"范围不明、没有结束时间、一直有效"（`device-observer.js` 读取 `progress/*.jsonl` 的部分），只要它还在最近两天的文件里，就会触发 `PAUSE_SCOPE_UNRESOLVED`，主动触达随之被拒。唯一的出路是用户手动点"接续本任务五分钟"。【代码确认，已复现】
3. 主动窗口每次都要手动开，最长 1 小时（`live-control.js` 的 `configure`）。没有任何"平时维稳"的默认节奏。【代码确认】

用户要的是"平时也在、抽离时能把我接回来、必要时真有约束"。现在这三点都还没有路径，只是被诚实地标成了"未接通"。

## 2. 优先问题

### P1　AI 接续失败一次，这道题就再也拿不到 AI 帮助　【阻断真实使用｜交 Codex】

- **位置**：`toolpkg/live-control.js` 的 `claim()` 和 `coach()`；`toolpkg/panel.js` 的 `coach()`。
- **问题一**：`claim()` 中 `if(type==='coach'&&same.length) throw COACH_ALREADY_ATTEMPTED`。同一道题只要有过一次尝试，不管结果是 failed 还是 unknown，都不能再调用模型。面板按钮固定用 `'panel-coach:'+qid` 作为 ID，所以用户再点只会拿回那条失败记录。
- **问题二**：`coach()` 直接 `JSON.parse(receipt.text)`。模型很常见的输出是用 ```` ```json ```` 代码块包住 JSON，这种情况会被判为失败。
- **我的复现**：第一次返回带代码块的 JSON → `failed`；同一 ID 再点 → `duplicate` 返回旧失败；换 ID → `COACH_ALREADY_ATTEMPTED`；模型只被调用了 1 次。【代码确认，已复现】
- **用户感受**：答完一题，界面停在模板问题上，按钮点了没反应。这正好对上用户自己说的困难："不知道下一句说什么就退出"。
- **最小修改**：
  - 解析前去掉代码块标记，取第一个完整的 `{…}`；
  - 上一次尝试是 failed，或 unknown 已超过约 90 秒时，允许用户在面板上重试，每题最多 3 次，每次都留记录；
  - 自动 tick 仍然每题只试一次。
- **验证**：加单元测试（代码块包裹、超时后重试、第 4 次被拒）；A-026 第 5、6 步看到 job 状态为 `saved`。

### P2　manifest 声明的 API 版本可能让模型调用整体不可用　【可能阻断｜交 Codex，需实测】

- **位置**：`toolpkg/manifest.json` 写的是 `"api_version": "1.0.0"`；`live-api.js` 依赖 `Tools.Chat.call`，而官方类型声明标注它 `@since ToolPkg API 1.0.1`。官方 ToolPkg 格式说明写明"使用这些能力时，manifest 的 api_version 需要不低于对应版本"。
- **后果**：如果宿主按声明版本提供能力，`Tools.Chat.call` 就不存在，`coach()` 直接抛出 `MODEL_API_UNAVAILABLE`，"AI 接续"整条线不可用。【文档判断＋需实测】
- **最小修改**：把 api_version 改为 `1.0.1`。设备报告的 Operit 是 1.12.2，按官方表格支持 1.0.1。
- **验证**：A-026 第 1 步就读 `live_status.capabilities.model`；为 false 时先不要请用户进场。

### P3　暂停没有终点，主动性只剩手动的五分钟　【影响核心目标｜Codex 实现，语义由用户定】

- **位置**：`device-observer.js`（读暂停）、`control-plane.js`（`pauseUnknown`）、`live-control.js`（`resume_prior_pauses`）。
- **问题**：
  - 暂停记录没有 `until`、没有"结束"条目，也没有范围；
  - 对小满说一句"我歇会儿"，会让新主控沉默一到两天；
  - 绕过的办法是按钮上的 `resume_prior_pauses=true`，但按钮文字"接续本任务五分钟"没有说明它会让之前的暂停失效。
- **最小修改**：
  1. 暂停默认有终点：用户说了时长就按时长；没说就到次日 08:00；`progress` 里出现 resume/done 时立即结束。
  2. 小满账本里的暂停默认只让小满安静（scope=companion），除非用户明确说"全部都停"。
  3. 用一个明确的"我回来了"按钮代替隐含授权，文字写清："之前的暂停作废，接下来 N 分钟会主动问我。"
  4. 允许用户自己设定每天的自动窗口（例如 09:30–11:30、20:00–22:00），到点自动开启。这会改变系统的打扰程度，属于用户拍板的规则。
- **验证**：单元测试覆盖三种暂停终止方式；真机上对小满说"歇半小时"，半小时后新主控能恢复触达。

### P4　强约束没有时间表　【不阻断本轮，但要定期限｜Codex＋A】

- **现状**：finite-lease 合同要求的 6 项能力，目前一项也没有可用的执行载体；staging 稿也说明了"冻结前安排解除"和"控制器退出后恢复"都没解决。这个判断是诚实的，问题在于没有截止时间，会被一直顺延。
- **建议**：给强约束一个 2 天的可行性验证，结果只有通过或不通过：
  - **候选 1：不做手机控。** 这是用户在 10-01 需求文档里已经选定的锁机执行者，有自己的前台服务和计时。先查它能否接受外部触发（Intent、自动化接口）。能的话，Operit 只做决定，执行和到期解除都交给它，归属自然唯一。
  - **候选 2：Shizuku `pm suspend`，并在冻结之前先挂好一个独立的解除进程**（`nohup sh -c 'sleep N; pm unsuspend 包名'` 在 suspend 之前启动）。测它在 Operit 被强制停止后是否仍按时解除。
  - **候选 3：设备所有者（DevicePolicyManager）。** 最可靠，但需要重新配置设备，代价大，放到最后。
- **通过标准**：冻结 60 秒，期间强制停止 Operit，到 60～75 秒时 `dumpsys package` 显示 `suspended=false`；同一 App 不会被两个执行者同时处理。
- **配套修改**：覆盖范围的"完整"应限定为"本主控自己发出的约束"，而不是"手机上所有约束"，否则 P4 即使通过，约束也依然不可达。

### P5　开始任务的门槛太高　【影响使用意愿｜交 Codex】

- **位置**：`toolpkg/panel.js` 一屏有 17 个按钮、9 个输入框，并出现"事务""接续窗口""调度""施工记录"等术语。开始任务要求填对象和目标，材料还有 4 个字段。【代码确认】
- **最小修改**：
  - 首屏只保留"现在在做什么"、"材料（粘贴或链接，可以空着）"和一个"开始"按钮；目标用默认值。
  - 开始之后只显示：当前问题、AI 的示范、回答框、"保存并继续"、"歇一会儿"、"我回来了"。
  - 其余功能收进"更多"。

### P6　两个主控台并行开发　【需用户决定】

- Claude 前一轮写了"主控中枢"（`operit/toolpkg`，提供对话门、Gemini 伴读、收线），也有一个"主控台"面板；Codex 这版有"认知主控台"。两边都往同一本账写。
- 我发现主控中枢 0.1.0 在 preview.3 下有冲突：它会把材料挂到施工记录上，也会绕过"真实任务绑定"直接开始任务。**已在 0.1.1 修正**：只往用户亲自选定的真实任务写，否则先存在本地，并提示去认知主控台开始任务。已加测试。该包的安装任务单已标为暂缓。
- 另一个缺口：创建真实任务的逻辑 `task-entry` 只在面板里直接调用，没有暴露成工具，其他包无法正确创建真实任务。建议 Codex 增加 `cognitive_core:begin_task`。
- **我的建议**：
  - 只保留一个任务入口，即 Codex 的认知主控台（按 P5 简化后）。
  - 伴读继续独立：它只是 Gemini 里的一个 Gem，零代码。
  - 对话门并入 control_plane，作为它"引导返回"（redirect_to_task）这一步的交互形式；P4 通过后，再作为限时钥匙的入口。约束归属在 control_plane，对话门放在那里，执行者才能唯一。

## 3. 逐条回答委托书第 7 节

1. **需求与主线**：认知闭环在服务主线；自律目前只有"引导返回"的提案，没有真正的执行。强约束应作为并行线推进，并给出期限（P4），不要等真人闭环全部完成后再开始。
2. **结构与复杂度**：cognitive_core / control_plane / live 的分层清楚。重复的地方有两处：两个主控台（P6）；观测器仍以已停用 19 天的棋盘 PTR 作为任务来源。棋盘里只要还有一张 ACTIVE 卡，就会一直产生 `TASK_PROJECTION_CONFLICT`。建议以 task-entry 绑定为唯一任务权威，旧来源只作参考。旧执行者（S4/P4）与新主控之间暂时没有冲突，因为新主控不执行任何约束。
3. **入口与交互**：输入过多（P5）。追问是否可持续，关键在 P1：模型失败后必须能再要一次帮助。核心的模板问题在用户回答很短时会补"可以从半句话开始"，这一点做得好。
4. **暂停与主动性**：五分钟不足以覆盖目标场景。授权旧暂停的语义合理，但应改成显式的"我回来了"，并且暂停要有终点（P3）。
5. **可靠性**：
   - 保存回答后不会丢失下一入口：answer 先由 core 生成模板题，模型失败只是不替换。【代码确认】
   - 模型返回时如果局面已变，结果会被丢弃，不会覆盖新问题。【代码确认，有测试】
   - 触达前核对代次和 revision，旧窗口不会投递到新任务。【代码确认】
   - 后台延迟：调度大约每分钟重挂一次单次工作流，每次都要更新工作流。实际延迟和频繁更新的代价，只能实测。【需实测】
6. **强约束路线**：见 P4。缺的设备能力是"冻结之前就有一个独立于 Operit 进程的解除保证"和"唯一归属"。
7. **证据可信度**：报告整体区分得当。需要补的一点：报告写了"模型接续已实现"，但它依赖 `Tools.Chat.call` 在当前 API 声明下可用（P2），这一点应标为"需实测"。
8. **下一步取舍**：见第 4 节。
