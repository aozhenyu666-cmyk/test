# 详细设计

日期：2026-10-04　主控中枢 v0.1.0　依据：《工作流详解说明书 v1.1》（10-03 盘点）、cognitive_core v0.2.0 源码、Operit 官方类型声明（`examples/types/*.d.ts`，main 分支）

## 1. 组件与职责

| 组件 | 形态 | 新建 / 复用 | 职责 | 不负责 |
|---|---|---|---|---|
| 思考线 | cognitive_core v0.2.0（ToolPkg） | 复用（A 组安装中） | 保存当前问题、材料、用户原话、下一入口；暂缓/接续 | 不开口（提醒、弹窗保持关闭） |
| 主控中枢 | `com.community.zhukong` v0.1.0（ToolPkg，本仓库 `operit/toolpkg`） | 新建 | 对话门与钥匙、伴读启动、收线、定时邀请；主控台面板 | 不直接冻结/解冻；不另建思考账本 |
| 伴读 | Gemini Live + 「伴读」Gem（`operit/gemini`） | 外部能力 | 看屏、语音、追问、反驳 | 不能被程序直接启动 Live 或读取对话记录 |
| 守门人 | Operit 角色卡（`operit/roles`） | 新建 | 1 分钟对话问三题，调用 gate_* 工具 | 不改规则 |
| 小满 | 现有角色卡 a2a22c7c | 复用，只加两条 | 日常陪伴；替主控中枢说邀请和提醒 | 不接手对话门 |
| 执行 | S4_Lock_Queue_Worker、解锁闸门 unlock_gate.sh | 复用 | 真实的冻结与解冻 | — |
| 感知 | P3/P4 采样、判断官 G2 | 复用 | 用时、前台、偏离 | — |
| Skill | `operit/skill/zhukong/SKILL.md` | 新建 | 告诉 Operit 里的 AI 怎么用这些工具 | — |

**一个声音原则**：伴读进行中，邀请类提醒自动跳过；对话门只由守门人说；其他时间由小满说。

## 2. 思考线如何写入

主控中枢不保存第二份思考记录，而是调用 cognitive_core 的 `status` / `apply`：

| 动作 | 写入 cognitive_core 的事件 |
|---|---|
| 开始伴读，且没有进行中的思考线 | `start`（标题=材料标题，目标="和伴读一起把这份材料想透，留下自己的结论和下一步"） |
| 开始伴读（每次） | `attach_material`（来源 web/file/user，状态 reported，正文注明"由 Gemini 实时看屏，未复制"）、有位置时 `set_return_point`、`set_activity=watching` |
| 收线（伴读结束或任何对话之后） | `answer`（source=USER，对当前问题作答），cognitive_core 随后生成下一入口 |

规则：

- 思考线处于**暂缓**时不自动接续；收线先存在主控中枢本地（`pending_takeaways`），面板提示待写入。
- cognitive_core 未安装或报错时，主控中枢照常运行，所有返回都标明 `backend: missing` 和 `saved: local`。
- 只写用户原话。工具描述和 Skill 都要求不得代答、润色。

## 3. 伴读流程

```
主控台「开始伴读」
  → zhukong:reading_start(title, ref)
      ├ 写思考线（第 2 节）
      └ Tools.System.startApp(com.google.android.apps.bard)
  → 用户：打开「伴读」Gem → Live → 共享屏幕（Android 规定必须本人点授权）
  → 主控台「打开材料」→ zhukong:reading_open_material（网址走 VIEW intent，App 走 startApp）
  → Gemini 边看边聊（设定见 operit/gemini）
  → 用户：「今天到这」→ Gemini 问"聊出了什么"
  → 主控台「收线」→ zhukong:reading_finish(takeaway, next_step) → 思考线 answer
```

已知限制（Gemini 官方说明）：锁屏或暂停时屏幕共享停止，恢复后要重新共享；锁屏时不能新开 Live。程序无法读取 Live 对话记录，所以结论靠用户收线带回来。

**第二阶段（用满一周且值得时再做）**：自建伴读 App，用 Gemini 的实时接口（Live API）接收屏幕画面和语音。好处是伴读的性格完全可控、对话文字可回收进思考线、可接着昨天聊；代价是开发量和按量计费，价格需核实。

## 4. 对话门

### 4.1 触发

- **现在**：现有 S4 冻结时会显示"已按你批准的规则冻结，回 Operit 说一句即可走解锁审讯"。用户回到 Operit，在主控台点「我想打开 B站」，或对守门人说。
- **以后**（需 B 组核实）："不做手机控"能否在打开重度 App 时直接触发；或用系统用时事件做到分钟级感知。

### 4.2 状态机

```
gate_open ──▶ asking ──三题有效──▶ answered ──grant──▶ granted ──▶ 钥匙
                │                      └─deny──▶ denied ─┐
                └─超过 3 分钟没答完──▶ expired ──────────┴▶ 当天失误 +1，冷却按阶梯延长
钥匙：pending_unlock ─解锁成功─▶ active ─到期（gate_tick）─▶ 回锁 ─▶ closed
                      ├未绑定通道─▶ unbound（只记账）
                      └调用失败/结果不明─▶ unknown（如实报告，不当成功）
```

### 4.3 判定规则（程序强制，AI 不能越过）

- 回答为空、属于敷衍词（随便、不知道、看看、刷刷……）、少于 4 个字（时长回答除外，例如"十分钟"）、与前一题相同 → 无效。
- 第二题说的时长比默认短，就按用户说的给；任何情况下不超过上限。
- 每天钥匙数到上限后，当天不再开门。
- 已有钥匙未到期，不重复开门。
- Operit 不能进入重度名单（UP-08）。

### 4.4 参数：当前默认值 与 立法提案

默认值对齐现有解锁政策（UP-01 每日人工解锁 2 次；UP-05 条件放行 10 分钟后自动回锁）。表中"提案"一栏需要你批准后，才可用 `configure` 修改。

| 参数 | 默认 | 提案（待你批准） |
|---|---|---|
| 每把钥匙默认时长 | 10 分钟 | 15 分钟 |
| 钥匙上限 | 15 分钟 | 30 分钟 |
| 每天钥匙数 | 2 | 4 |
| 回答超时 | 3 分钟 | — |
| 冷却阶梯 | 5 → 10 → 20 → 40 分钟 | — |
| 重度名单 | B站、抖音、贴吧、小红书 | 是否加入微博、快手（即 `p2/ent.list` 组 C） |
| 默认锁定时段 | 不启用 | 工作时段内重度 App 默认冻结，只能用钥匙打开（这是"对话门"真正起作用的形态） |

### 4.5 执行通道

主控中枢不直接调用 `app_suspender`（遵守说明书 X8 和"唯一真手"，避免说明书 S-1 那样的双执行器）。钥匙通过两个可绑定路由执行：

```json
{"routes": {
  "unlock": {"tool": "<B 组核实的锁队列/解锁闸门工具>", "params": {}},
  "lock":   {"tool": "<同上>", "params": {}}
}}
```

调用时附带 `package`、`action`（unlock/lock）、`minutes`、`key_id`、`reason`。工具返回 `success:false` 记为 failed；抛错记为 unknown；只有正常返回才记为 accepted。路由未绑定时钥匙状态为 `unbound`，面板明确提示"钥匙只记账，不改手机限制"。

**未绑定时也有用**：1 分钟的三个问题本身就是一次停顿。第一周建议先这样跑，看问题问得是否合适，再接真实执行。

## 5. 说话通道

| 模式 | 做法 | 用途 |
|---|---|---|
| notification（默认） | `Tools.System.sendNotification` | 未绑定小满时 |
| chat | `Tools.Chat.sendMessage` 发【可用事实】到小满会话（隐藏用户消息、回复时通知），由小满用自己的口吻说一句 | 绑定后的日常声音 |

守门人语音：`gate_voice` 先把对话门简报发到守门人会话，再 `Chat.switchTo` + `Chat.startService({initial_mode:'VOICE_BALL', auto_enter_voice_chat:true})`。实际能否出声，要等 B 组核实（说明书显示主控台"语音"按钮只唤起语音球，不直接 TTS）。

## 6. 工作流

由 `zhukong:install_workflows` 创建，**默认停用**；同一个 key 重复安装时会更新原工作流，不会重复创建。

| 名称 | 触发 | 执行 |
|---|---|---|
| 主控·钥匙巡检 | 每 15 分钟（Operit 最短间隔） | `zhukong:gate_tick` |
| 主控·伴读邀请 09:30 / 20:00 | 每天定时（cron，设备本地时区，已实测为 Asia/Shanghai） | `zhukong:reading_invite` |
| 主控·收线 21:30 | 每天定时 | `zhukong:thread_nudge` |

钥匙到期最晚会延迟 15 分钟才被收回（受 Operit 最短间隔限制）。要更准，需要回锁一侧由现有队列自带到期时间，这一点等 B 组导出 `lock_queue.sh` 后再定。

## 7. 与现有系统的关系

- **不修改**任何现有工作流、脚本、规则表。
- 新增三条（共四个）定时工作流，默认停用。
- 现有说明书里与这套设计直接相关、建议优先修的三项（另行处理，不在本包内）：
  1. B-b / O-15：暂停期小满和判断官不同步。会影响"一个声音"和收线提醒。
  2. F-13：日报"在任务"比例虚高（真实约 11%）。会影响一周后的效果判断。
  3. 语音能否真正出声（B 组核实中）。会影响守门人语音和小满提醒。
