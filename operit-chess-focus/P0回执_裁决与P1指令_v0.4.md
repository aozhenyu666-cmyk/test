## 1. 三项裁决（用户已批准）

### 裁决 1：计时口径 —— 同意，并加两条

- 所有用于**判定**的时间字段一律由 shell `date +%s` 生成（字段名统一加 `_ts` 后缀，如 `round_started_ts`、`expected_return_ts`）。模型或节点写的 iso 串**只作展示，永不作判定输入**。
- **补充 1**：差约 4.5 小时，不像是简单的时区差（时区差应是整 8 小时）。请查明两件事：`super_admin:shell`（Android 侧）与 `super_admin:terminal`（proot Ubuntu 侧）的 `date +%s` 是否一致、各自的 `TZ` 是什么。**状态机只用一个固定通道取时间**，在脚本头注释写明是哪个。
- **补充 2**：展示用的人类时间统一由脚本把 `_ts` 按 `Asia/Shanghai` 格式化得到，不再由模型手写。

### 裁决 2：时限冲突 —— 保留 `ladder.conf`，分两层

同意你的建议：**不改已批立法**。但用户的核心诉求是"分钟级反馈"，所以分成两层，互不覆盖：

| 层 | 管什么 | 时限来源 | 有无惩罚 |
|---|---|---|---|
| **对局内提醒**（L1、L2） | 回合超时、断点提示、要求选状态 | 回合自身的 `expected_return_ts` + 5 分钟 → L1；之后**按 `ladder.conf` 的 GAP 升档** | 无，只是提醒 |
| **强制**（L3 拉回、L4 冻结） | 切屏、冻结 | **完全服从 `ladder.conf`**：LOCK_MIN、冷静期、每日上限、静默时段、`manual_release_only` | 有 |

- **CHANNEL_GUARD 必须保留**，写进合并稿：通道断或健康证据过期时，**只提醒、不入队锁机**。09-20 的事故不能重演。
- **P1–P3 全程在 `SHADOW_MODE=on` 下跑**：状态机照常计算并写 journal（"本应 L2 / 本应冻结 X"），但不真正切屏、不真正冻结。这样可以在不打扰用户的前提下统计误判率，作为第一阶段验收的数据来源。是否关闭 SHADOW 由用户在 P3 之后决定。
- v0.3 §14 中 L1→L2=3 分钟、L3→L4=2 分钟、休息配额、认输上限，**全部作废**，以现行 `ladder.conf` / `unlock_gate` 为准。

### 裁决 3：冻结名单

- 删除未安装的 3 项：抖音极速版、快手、知乎。
- **小红书分身（user 999）**：先用一次受控实验确认 `app_suspender` 能否按 user 冻结（只冻分身、立即回读、立即解冻，全程留证）。
  - 支持 → 双冻；
  - 不支持 → 用户考虑**手动删掉小红书分身**（最便宜的堵法），删之前记为已知绕过口。

- 请确认两份 BOSS 是否都在使用（只读：各自的最近使用时间）。

### 风险 C：实时性的真正载体是什么
schedule 最快 15 分钟、还会迟到数小时，所以分钟级检测只能靠常驻采样。`p2/watch.sh` 已在生产运行（obs_log 117KB）：
- 它现在由什么驱动？采样间隔多少？锁屏后、Operit 被杀后还在不在？

- 若不可靠，P2 增加一项"常驻存活测试"：连续 2 小时，覆盖一次锁屏和一次切到后台，按行数与时间戳空洞统计存活率。

## 3. P1 范围（批准执行）

按你 §4 的合并判断执行，补充如下：

1. `chess/state.json` + `chess/journal/<YYYYMMDD>.jsonl`；写法沿用 `.new` → 校验 → 原子换入。
2. `thread_id / next_step / resume_point` **指回** P1 棋盘 PTR 与任务卡，不复制内容；`state.json` 只新增 `mode / round / expected / expected_return_ts / intervention_level / state / rev` 及 `_ts` 时间字段。
3. 校验规则（写入前）：`rev` 严格 = 旧值 + 1；`state` ∈ {THINK, EXEC, REST, DRIFT, IDLE}；所有 `_ts` 为整数且不早于上一版；任一不过 → 拒写并记 journal。
4. `chess/state_machine.sh`：纯 sh，无 `set -e`；输入为 `state.json` + `watch.sh` 的最新观测行 + `ent.list` / `classes.tsv`；输出为建议级别（ALLOW / L1–L4），写 journal。**在 SHADOW 下只记录不执行。** 沿用 `watch.sh` 的禁令："两个采样点同 App ≠ 连续时长"。
5. 断点显示：一个只读命令，输出一段人话（目标 / 上一判断 / 下一步 / 已完成 / 已用时），供 L1/L2 通知直接引用。
6. **冻结吞吐（Q10）放到 P4 再改**，P1 不动 `lock_queue.sh` 与 S4。届时建议的方向（供你评估，不是指令）：开局与终局各一条**手动触发**的独立工作流（锁、解分开），批量处理名单、逐个回读 `dumpsys`；队列行加 `game=<id>` 字段，使"冻结到对局结束"有承载位。

### P1 验收（以盘上回读为准）

- 手动走 3 次状态迁移（IDLE → THINK → EXEC → THINK）：journal 有 3 行，`rev` 连续，`_ts` 单调。
- 杀掉 Operit 重开、锁屏再解锁：断点显示与杀前一致。
- 故意写一条 `rev` 跳号的 `.new`：被拒，journal 有拒写记录，`state.json` 未变。
- 状态机在 SHADOW 下跑 30 分钟：journal 中有判定行，无任何真实切屏或冻结（`dumpsys` 回读黑名单全部 `suspended=false`）。
