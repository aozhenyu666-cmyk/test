# 超级 AI 伙伴整合需求说明
## 供 Claude 制定实施计划
版本 1.0　2026 年 10 月 19 日

本文综合用户提供的 Claude、Gemini 讨论，以及已读取的仓库第二版蓝图和任务书。目标是让下一位设计者理解完整愿景、识别关键缺口，再制定可执行计划。本文是需求与设计约束，尚不代表代码已经实现或真机已经验证。

核心结论：在现有总控、一手和 GPT／Gemini 之上，建立一个持续维护共同情境、主动发起互动、组织思考与行动、检查效果并调整策略的协调核心。长时间语音优先复用已有会员服务；系统的记忆、议程、决策和执行回执由自己掌握，不能随一次外部对话结束而消失。

## 一 用户真正要得到的体验

用户希望拥有一个主动、连续、有记忆的 AI 伙伴。它可以表现为熟悉的女性角色和声音，有稳定的交流风格，会陪伴、追问、提出新方向，也能在约定范围内坚持要求。人格是交互体验；可靠性来自持续的状态、行动和反馈。

理想体验是：用户没有准备话题、没有汇报近况、没有主动打开管理页面，系统仍能依据已有信息提出下一步；需要深聊时，带着问题和上下文转入 GPT 或 Gemini；结束后接回结论，追踪现实行动；失败时同时检查任务、交互设计、感知能力和执行故障。

目标也包括空闲时的陪伴、探索和游戏交流。不能把所有闲聊与娱乐判成问题。系统需要区分工作、训练、休息、陪伴和技术降级等模式，各自采用合适的成功标准。

用户愿意接受较强外部约束，但不能把“没有它我一无所有”作为设计前提。产品应提供支撑，并逐步降低用户启动、恢复和组织任务所需的成本。

## 二 现有方案应保留什么和修正什么

| 来源 | 值得保留 | 需要修正 |
|---|---|---|
| Claude 第一版 | 事件触发、决策核心、干预层次、执行器、回执与任务拆分 | 不能把每个生活例子直接固化成一个预算、时间段或新页面 |
| Claude 第二版 | 复用现成语音服务、话题卡、收线、独立健康监测、减少人工传话 | 持续谋划不能完全寄托于一次 Gemini 会话；Google Tasks 不能未经验证就承担整条系统主干 |
| Gemini 的构想 | 跨应用提词、情境推演、记录系统失败、动态调整策略、伙伴连续性 | 观察不能当读心；自动进化不能等于自行扩权；支付拦截、实时读取外部对话和瞬时恢复不能写成保证 |
| 现有总控与一手 | 已有控机、训练、断点、记忆和交互资产 | 先查清真实实现与使用效果，再决定合并、保留、隐藏或停止开发 |

“规则”仍有价值：权限边界、去重、超时、恢复和稳定承诺需要确定性逻辑。模型负责解释情境、生成问题、比较方案。二者需要配合；删掉规则不会自动产生智能。

当前真正需要补的，是把分散功能组织成连续过程的能力，并验证它能否提高现实中的推进率。

## 三 统一的系统结构

建议从职责上区分以下六部分；这不要求制作六个 App 或部署六个模型。

| 部分 | 核心职责 | 必须留下的结果 |
|---|---|---|
| 感知与健康监测 | 收集授权范围内的应用事件、任务进展和权限状态 | 带时间、来源、质量标记的事件 |
| 共同情境与记忆 | 保存当前目标、断点、证据、疑问及最近干预 | 各入口引用的同一版本状态 |
| 协调与推演核心 | 解释局面、提出下一问、选择交互方式、安排后续 | 可解释且可撤销的行动提案 |
| 伙伴交互 | 文字、语音、通知、悬浮窗，以及 GPT／Gemini 接力 | 用户回答、问题进展和会话结果 |
| 策略边界与执行 | 校验权限，执行允许的提醒或限制 | 实际执行回执与到期状态 |
| 效果复盘 | 比较预期与结果，发现误判和系统摩擦 | 待验证的策略调整及回退条件 |

一次完整过程是：出现事件 → 更新局面 → 判断是否介入 → 选择一个下一步 → 交互或执行 → 收到回执 → 检查现实结果 → 更新记忆。

所有介入共享一份议程，避免提醒、收集箱、训练和强督导同时各说各话。一次只突出一个主要问题，其他内容排队。

## 四 协调核心的能力要求

### 1 不依赖主动汇报也能工作

系统应依据日程、最近断点、事件流和设备健康形成最小判断。但必须知道自己能看见多少：没收到产出，不等于没有做事；屏幕关闭，不等于睡觉；在购物软件停留，不等于冲动消费。

信息不足时，用成本最低的一次确认补齐，例如“你正在做饭、休息，还是卡住了？”这类点选用于确定情境，不承担深度训练。不能为了坚持简答原则，连恢复系统都要求用户长篇解释。

用户不回应时，先检查是否可达、是否忙碌、提醒是否重复、设备是否失联，再按事先约定的时段和边界处理。沉默本身不足以证明逃避，也不应自动触发无限升级。

### 2 会推演但不把推测写成事实

每次关键判断至少分开记录：

- 事实：具体观察到了什么，以及来源与时间。
- 假设：可能发生了什么，当前把握如何。
- 替代解释：还有哪些合理可能。
- 最小验证：下一步怎样低成本区分。
- 行动及复查：现在做什么，何时检查是否有效。

例如观察到“任务尚无新回执，购物软件停留十二分钟”，可以提出“任务阻力较大”的假设，也应保留买菜、休息、比价等解释。不能直接断言用户在用糖补偿多巴胺，更不能据此加重限制。

反复使用“识破借口”会奖励模型编造心理故事。系统的权威应来自准确的事实、稳定的约定和可纠正的判断。

### 3 能提出用户没有想到的方案

核心不应只催执行，还应承担谋划职责：发现目标冲突、重新组织任务、减少前置条件、寻找替代路线、指出不值得继续的投入。

例如求职与备考争夺时间时，它应呈现可选安排和代价，而非分别为两个目标生成更多待办。发现任务连续卡住时，应判断是下一步不清楚、能力缺口、目标不再合适，还是单纯需要休息。

每次谋划都落到一个可检验变化：改变了哪个判断、补了什么证据、做了哪项决定、开始了哪个动作。保留开放探索空间，但避免只生成更长的方案。

### 4 知道何时停止对话

对工作和训练会话，系统应推动一个明确节点：澄清问题、推一步、验证或者开始行动。若继续讨论的收益低于实践，就提出结束讨论并做一个小动作。

对陪伴和休息会话，愉快交流本身可以是结果，不强迫每次提交生产力证据。伙伴感不能全部依靠考核和拦截建立。

## 五 持续交流与一手训练如何结合

简答题有训练价值，但简答并不天然等于思考，选择题也并不天然无效。应保留一手的断点续接、逐步追问、依据检查和复习等资产，而非只抽走“答题才能放行”。

推荐根据状态调整交互深度：

| 当下状态 | 交互方式 | 要得到什么 |
|---|---|---|
| 难以启动或信息不足 | 一个点选、一个词或一句语音 | 建立连接，识别卡点 |
| 能进行一步加工 | “你的依据是哪一句？”或“接下来会怎样？” | 一个真实推理步骤 |
| 正在学习 | 判断、解释、反例、迁移与必要的重复 | 对知识或思路的掌握 |
| 需要做决定 | 方案、代价、反对证据和选择 | 明确决策 |
| 已经足够清楚 | 展示第一个现实动作，保留断点 | 开始行动 |
| 明确在休息 | 陪伴或安静，不持续催问 | 恢复与自主休息 |

对用户的常见断裂，系统需要能在中断后用一句话接续：“刚才停在这里，现在只回答这一小问。”不让恢复过程再次变成资料阅读任务。

可以设固定陪练时段，但全天互动不能只靠定时题目。主动性需要体现在问题的选择、上下文的接续以及对反馈的响应上。

## 六 GPT 和 Gemini 如何成为可替换的协作端

长时语音优先复用用户已有的 Gemini Live；GPT 承担适合它的深度讨论与其他任务。具体路由由质量、额度、延迟和可用性决定，不把任何一家固定成永远的“主脑”。

协调核心负责议程和持续记忆。外部模型可以提出建议、帮助推理和形成会话结果；不能仅凭它说“完成了”，就修改全部状态或解开限制。

### 会话接力需要四步

1. 准备：把当前事实、一个核心问题、已知断点和所需结果写成短上下文包。
2. 交接：通过已经验证的接口、分享入口或用户可见操作送入目标服务，记录成功或失败。
3. 伴随：悬浮窗显示现在这一问、已得到的结论和下一节点；读取不到对话时明确降级。
4. 接回：获取结果，区分用户确认、模型总结和实际证据，再安排后续行动。

最低可用的上下文包应包含：会话标识、状态版本与时间、当前模式、主线和断点、相关事实、一个问题、预期结果。不要每次发送完整生活档案。

返回结果应包含：结论、仍未解决的问题、下一步、证据或验证方式。自动解析失败时保留原文，不默默丢失，也不擅自当作完成。

### 悬浮窗的重点

默认显示一个当前问题，其他问题折叠排队，避免“大量问题”再次增加负担。至少提供“继续这一问”“卡住了”“已有结论”“需要休息”这几种简短反馈。

它可以在 GPT／Gemini 页面提供提示与接力，但外部会话没有可读字幕或正式接口时，不能假装掌握完整对话。此时用阶段性确认代替实时语义监工。

在 Gemini 里停留十分钟，只能证明停留时长。关于工作推进，应检查新判断、证据或现实动作；不能只按聊够时间解锁。

## 七 信息连通应建立在统一状态上

需求是“信息自动连通”，Google Tasks、日历、Notion、剪贴板都只是候选通道。Claude 应先设计清楚共同状态的内容、所有权和同步语义，再选择第一条实现路径。

建议由一个逻辑上的权威状态源维护：

- 稳定目标、偏好和已经约定的边界。
- 当前主线、下一步、断点和待决问题。
- 有来源的近期事实，以及分开保存的推测。
- 对话、干预、执行与现实结果的对应记录。
- 系统健康、可观测范围和待验证策略。

每条关键记录需要标识、来源、时间、版本、处理状态；外部返回必须能去重、识别过期、处理冲突。手机和电脑不能同时重复处罚；离线后先保存事件，恢复时合并。

Notion 可以保留为档案和查看入口。迁移前要验证现有事项与行动链路，不能仅因出现新总线就重建全部内容。

自动化分级：

| 级别 | 体验 | 判断 |
|---|---|---|
| 一次操作接力 | 自动准备，上下文由用户点击分享或念出，结果简短确认 | 可作为早期可用版本，明确仍有人操作 |
| 自动双向接力 | 自动送达、自动接回、带回执与重试 | 产品的主要升级目标 |
| 全程实时协作 | 可靠读取过程、持续纠偏、跨端同步 | 长期目标，依赖实际可用接口 |

早期允许少量手动接力，但不能把长期人工搬运包装成自动连通。

## 八 场景需求与验收方向

| 场景 | 系统应怎样工作 | 不合格表现 |
|---|---|---|
| 用户没汇报且主线未启动 | 读取现有断点，低成本确认，给一个可开始动作 | 只继续催用户填表 |
| 四个折扣蛋糕 | 区分采购、进食与替代做饭等情况，结合已有约定提出选择 | 自动断言心理动机，未经讨论写死每周三十元 |
| 打开 GPT 后不知道说什么 | 自动提供有事实背景的一问，支持接回结论 | 再让用户挑选几十个话题 |
| 工作会话越聊越散 | 在能观测的范围内检查议程，提示收束或实践 | 只看时长就认定口水话，或聊够时间即通过 |
| 一手持续未使用 | 检查入口、响应、题目难度、输入成本和实际收益 | 先判定用户不配合，再增加惩罚 |
| 无障碍开着但失效 | 区分权限、连接、事件和页面内容异常，记录恢复过程 | 把开关为开当作健康 |
| 手机管住后转移电脑 | 电脑事件进入共同情境，保持同一议程和断点 | 单独宣布手机时长下降就是成功 |
| 正常休息与游戏陪伴 | 按休息模式陪伴，约定到点再接主线 | 持续责问，或者依赖未验证的实时游戏读屏 |
| 网络或模型不可用 | 保留状态，用缓存问题和有限本地流程继续，恢复后接续 | 空白卡死或反复加锁 |

例子用于定义适应能力，不意味着现在就开发完整消费系统或游戏助手。

## 九 可靠性与约束

用户要求的严格性应落实为事先约定、可解释、在忙乱时不轻易变更的执行流程。它不是模型获得永久独立权力。

- 模型可以在授权范围内选时机、提问和建议策略；不能自行扩大监控范围、延长限制上限或修改紧急退出。
- 手动撤销权限与系统意外掉线必须分开处理。恢复机制不能与明确撤权对抗。
- 系统误判、无可观测数据和执行失败都应允许纠正，并保留依据。
- 必需通信、紧急操作和基本生活通路不应成为惩罚工具。
- 重复无回应可能来自提醒疲劳、故障或不合时宜；应能降低打扰、切换方式和暂停，而非只会加码。
- 不能把用户绕过限制自动等同于道德或信用问题；先区分约定违背、误拦、正常需要与故障。

无障碍健康监测至少要分别看：权限配置、服务连接、事件通路、目标应用的可读情况，以及执行器回执。没有事件要结合亮屏和操作情境判断。

独立哨兵是候选实现，不是先验结论。它可以隔离部分故障，但与主程序仍共享操作系统和设备限制。Claude 应比较独立 App、独立进程与现有健康服务的收益和维护成本。

## 十 必须核实的技术事实

本节基于 2026 年 10 月 19 日读取的官方资料；真实账号、机型、语言和版本仍需验证。

| 原说法 | 可靠表述与计划要求 |
|---|---|
| 用 Gem 给 Live 固定人格 | 当前 Gemini Live 官方帮助明确写着 Gems 暂不能用于 Live。不能把 Gem 指令自动继承作为前提，需验证其他上下文路径。[1] |
| Live 能读写 Tasks，所以可作完整信息总线 | 官方列出 Tasks、Keep、Calendar 等 Connected Apps，但分批开放；指定列表、精确格式、长上下文、同步延迟与回执均需实际验证。[1][2] |
| Tasks 有 API，整条双向同步就成立 | 官方确有 Tasks REST API；API 能操作数据，与 Live 能按预期使用同一记录，是两段不同链路。[3] |
| 支付时浮窗必然挡住按钮 | Android 允许应用隐藏其他应用的叠加窗口，敏感窗口也可限制截屏。消费干预需寻找可靠且可见的前置节点，不能承诺覆盖所有支付页。[4] |
| 后台随时强制跳进 Gemini Live | Android 对后台拉起界面存在限制与例外，必须按目标版本和授权验证。打开 App 也不等于自动建立带上下文的 Live 会话。[5] |
| Shizuku 三秒内无感修好任何掉线 | Shizuku 自身依赖启动、授权、后台存活和设备环境；官方说明非 root 启动在重启后需要重新执行。不得宣称绝对可靠。[6] |
| 字幕存在就能持续读取全部对话 | Live 官方支持字幕，但第三方无障碍能否获取、后台是否持续可用，仍需真机测试。[1] |
| 轻量本地模型例如 DeepSeek V3 | 本地推理与远程 API 是不同部署方案。不能把大型服务模型名字当作手机可运行证据，应按内存、速度、电量和质量选型。 |
| 文字每天必然几毛钱 | 当前材料不足以保证。必须计入历史输入、输出、摘要、重试、同步与复盘，依据实际调用和当前官方价格估算。 |

用户会持续续费 GPT／Gemini，可优先利用现有交互额度；额外 API 费用、客户端额度以及自动化接口权限应分别核算。不能用包月会员推导出无限调用权限。

这次实际读取的是仓库蓝图和任务书，未进行全部源码审计，也未完成真机测试。过去对话中“全部代码已读完”等说法不构成本次验证结论。

## 十一 有创造力的长期能力

以下方向应保留在总蓝图中，并拆成可验证假设，不能因为首版暂做不到就删除愿景。

1. 行动前预演：预测最可能卡住的具体节点，提前备好材料、替代路径和第一问，事后检查预测是否正确。
2. 中断后的接力：手机换电脑、白天换晚上、GPT 换 Gemini，都恢复到同一个尚未完成的推理或行动节点。
3. 互动难度调节：根据启动率、回答质量和疲劳反馈，调整语音、点选、简答和实践的比例。
4. 系统失败实验：每次只调整一个主要交互因素，比较效果；保留旧策略与回退条件，避免每天重写全部规则。
5. 伙伴主动带来材料：围绕既定主线准备问题、练习和决策备忘，不只等待用户下任务。
6. 游戏和生活陪伴：在已有语音服务可用范围内提供陪伴，再逐步验证屏幕、声音、延迟与游戏资源占用。
7. 适度撤去支架：启动和恢复更稳定后，减少不必要打扰，让伙伴在需要时在场，而非以全天控制量衡量成功。

“自主进化”应具体化为记录、提出修改、有限试验、评估、回退。不要用意识、懂你或人格一致等词代替这些机制。

## 十二 首个闭环与成功标准

第一轮应同时验证可靠性和认知协同。只修锁机无法证明升级了大脑；只做漂亮对话无法证明能持续落地。

建议首个纵向场景：约定工作时段内，主线没有新的已知进展，且发生娱乐应用使用。

最小闭环需要做到：

1. 保存观察依据和设备健康状态。
2. 协调核心提出一个带不确定性的判断。
3. 生成一个当前问题或现实动作。
4. 用浮窗或通知呈现；需要深聊时准备接力上下文。
5. 接收回应并保存断点、结论或失败原因。
6. 在合理时间检查是否产生现实推进。
7. 未推进时区分任务、交互、判断和技术故障，调整下一步。

第一轮可以只支持一个手机、一条主线、一种外部语音服务和一个接力通道。完整设计仍应包含电脑及其他服务的接入边界。

成功指标由 Claude 在取得基线后给出目标值，至少包括：

- 可观测时段内主动发现并发起的比例。
- 从触发到第一次有效回应、再到现实动作的时间。
- 有效推进率与中断恢复率。
- 误判率、误拦率、重复打扰和用户负担。
- 接力成功率、信息过期和重复处理次数。
- 掉线发现与恢复时间，以及无法恢复时的行为。
- 实际日成本、耗电、网络使用与维护负担。

不能以聊满时长、问题数量、扣分数量、提醒次数或锁机力度作为主要成功指标。初期与现有流程比较只能提供个人实践证据，不应夸大为已证明因果。

## 十三 Claude 应交付的实施计划

请直接依据本文推进计划。当前已经明确的需求无需再要求用户重复解释。能通过仓库、文档和原型确定的事项先查清，只保留真正会改变方向的少量问题。

应交付以下内容：

1. 仓库现状盘点：核实总控、一手、语音原型、共享记忆、运行器及电脑版实际位置；列出可复用、重复、失效和缺失部分，并注明分支、提交和文件依据。
2. 能力验证矩阵：列出关键假设、官方依据、真机试验、通过条件和替代路线。尽量准备可直接执行的探针与最少操作步骤。
3. 系统边界与数据设计：确定协调核心、状态源、接口、接力记录、执行回执、冲突与降级逻辑。
4. 首个纵向闭环计划：一个场景从观察到现实结果跑通，每项任务具有依赖、产物、验收、失败回退和可估算工作量。
5. 渐进整合方案：说明一手和总控哪些共用、迁移或保留。不要先删除独立入口或训练资产；先验证合并后能覆盖实际用途。
6. 交互样稿：给出正常工作、难启动、无回应、休息、误判、断网和掉线时的具体一句话与可见操作。
7. 完整愿景路线：区分已实现、近期可做、需要实测和长期研究，保留伙伴、谋划、跨端接续与系统复盘能力。
8. 成本与可靠性估算：明确模型、请求规模、历史长度、重试与预算上限；分别报告已测值和估计值。

不要直接沿用旧版“每周三十元”“每日两份”“必须聊够十分钟”等未经用户确定的数值。不要把增加页面数量当成整合，也不要为了减法把持续推演的大脑删掉。

最终计划应让用户看清：系统下一次主动出现时，依据是什么，会说什么，怎样接上外部 AI，如何确认产生了结果，以及失败后如何继续。
