# 从语音浮窗到手机助手

## 产品目标

让用户在使用其他 App 时，仍能自然地与助手交流，并让助手利用当前屏幕和明确授权的手机工具完成小任务。

用户说一句「打开地图」，应用被唤起；接着说「看一下屏幕，这个地方怎么走」，助手看到当时的页面并解释。切换应用后，会话继续。用户可以打断或暂停，不需要不断返回聊天主页。

## 第一阶段：可安装的交互闭环

当前原型已实现浮窗、系统中文识别/播报、连续轮流对话、少量本机指令、模型聊天和单次屏幕截图接口。先在目标手机验证麦克风/系统识别、浮窗和后台服务的实际可用性，再决定语音供应商。

它不会像系统预装助手一样天然拥有所有权限。App 内组件、桌面小组件和跨 App 浮窗是三种不同入口：小组件不能承担完整的连续会话，跨 App 入口需要独立系统权限。

## 第二阶段：把“高频互动”做好

改进重点是语音链路，而不是增加更多按钮：

1. 流式输入：说话时持续获得识别结果，保留短暂停顿，不把每次停顿都当作完整指令。
2. 流式输出：模型先生成的句子先播报，缩短等待。
3. 自然打断：结合语音活动检测与回声消除，区分用户声音和助手自己的播报；用户开口时停止播报和旧请求。
4. 会话恢复：处理耳机切换、来电打断、网络断开、权限撤回和进程终止。
5. 资源预算：区分主动会话和待机。会话暂停后释放识别资源；唤醒词单独评估设备支持和耗电。

在这些能力稳定前，不承诺全天候免触摸对话。当前版本采用系统识别器和按键打断，真实设备端到端延迟尚未测量。

## 第三阶段：理解用户正在做什么

屏幕是一份即时上下文。优先使用目标 App 主动提供的结构化内容，其次是用户触发的截图。截图只能解释当前可见信息，不能证明隐藏页面、历史行为或用户意图。

可逐步增加：

- 「继续看这一页」：明确开启的短时观察会话，有可见状态、停止按钮和频率限制。
- 当前任务记忆：保留“正在找酒店”“已比较过两个选项”等会话摘要。
- 长期偏好：用户明确要求记住的偏好，提供查看、修改、删除入口。

不能把每张截图直接写成永久事实。例如看到一条商品广告，不能推断用户喜欢或购买了这个商品。

## 第四阶段：扩大行动能力

工具注册表让模型了解“手机到底能做什么”。每个能力包含：

| 字段 | 用途 |
|---|---|
| 名称和说明 | 区分打开应用、跳转页面、查询数据、提交操作 |
| 参数定义 | 明确目标应用、对象和动作，避免猜测 |
| 可用状态 | 区分未实现、未授权、当前页面不支持、可以执行 |
| 执行与取消 | 一个入口执行，一个入口中止 |
| 完成证据 | 官方接口返回值或页面结果，避免“已发出请求”被当成“已经成功” |

接入顺序建议：宿主 App 内部能力 → Android 官方 Intent/系统接口 → 目标 App 的 Deep Link/API → 设备厂商提供的系统能力。面向应用商店的产品需要按实际分发渠道检查自动化接口的使用条件。

当用户要求发消息或提交订单时，最终执行应绑定具体收件人、内容或金额；把“帮我处理一下”直接扩展成任意动作会让产品难以控制。

## 组件化方向

```text
宿主 App / 浮窗 / 耳机入口
              ↓
会话控制器：听、想、说、打断、暂停
       ↙                ↘
模型与上下文             手机工具注册表
       ↓                ↓
短期/长期记忆       Intent / 官方 API / 系统适配
```

原型中的 `AssistantService` 管理会话，`CommandParser` 处理明确指令，`PhoneActions` 处理手机动作，`PhoneAccessService` 提供导航和截图，`ModelClient` 负责模型请求。后续可将它们抽成独立库，再提供 App 内视图和浮窗两种 UI。当前交付尚不是通用可嵌入 SDK。
