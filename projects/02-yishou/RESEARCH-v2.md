## 0. 一页结论

1. **合并方向不变**：以一手为底座，总控做中枢，哨兵只做总控无障碍服务的看门狗，思维驾驶员停止开发。
2. **这套系统真正的对手不是“拦不住”**，是“过早闭合 + 没有结算”：在每个需要付出或会被评价的节点，用一个最便宜的动作结束当下不适，之后没有任何机制把它拉回来。
3. **先修可用性，再谈训练**。无障碍服务被杀/被冻结是当前第一优先级；“练思维”排在其后。
4. **训练只练一步**：选项题落笔前的终审（回原文抄一句证据 + 说出最犹豫的另一个选项错在哪）。这一步能在离开 App 后继续用，其他训练要么远迁移接近零，要么证据不足。
5. **四个纯规则模块已落地并跑通 45 个单元测试**，本次交付见第 5 节。

### 1.4 模拟器实测（2026-11-05，Android 14 / API 34）

装齐三个 APK（总控、哨兵、一手）后实测：

- 两个无障碍服务同时绑定，无障碍列表里没有一手的 `GateService`。
- 严格窗口 + `blocked=YouTube`：打开 YouTube 5.3 秒内被总控 `GateActivity` 弹回。
- `kill -STOP` 冻结总控：哨兵 **51 秒**判定掉线；收回哨兵重绑权限后再冻结，打开 YouTube 被 `com.zongkong.sentinel/.BlockActivity` 拦下，日志「拦下 com.google.android.youtube」。
- 原参数（90 秒阈值 + 30 秒轮询）下同一场景要 150 秒以上；已调为 **45 秒阈值 + 5 秒轮询**。

结论：独立哨兵方案成立，`:guard` 拆分不需要。45 秒已经是“容忍两次心跳丢失”的下限，再低会误判；要进 20 秒，得给总控加 5 秒一次的轻量心跳，而不是继续压哨兵阈值。

还有一条结构性事实：`fix/gate-loop-break`（一手 0.25.4）**不含 `zongkong/` 目录**。一手和总控虽然在同一个仓库里，但分支已经分叉到“一棵树只有一个项目”的程度。这意味着必须先建一条同时容纳两者的集成分支，否则永远在两条线上各改各的。

## 2. 问题模型

### 2.1 四个环节

| 环节 | 失效表现 | 真正的机制 | 对应干预 |
|---|---|---|---|
| 启动 | 知道要做，一直没开始 | 线索缺失 + 意图-行为落差 | if-then 计划、线索装进已有场景、第一步缩到 2 分钟 |
| 维持 | 被打断就回不去 | 推理状态没有外置 | 外置账本，回来时由系统重放 |
| 闭合控制 | 提前锁定答案/结论 | 停止规则缺失 | 作答前强制说出“排除了什么、依据哪句、什么会让我改主意” |
| 重返 | 逃了之后不再回来 | 逃离被默认为失败 | “没做”合法化，下次开口只结算、不评价 |

### 2.2 统一签名

四个环节表层不同，底层是同一个动作：**用当前最便宜的动作结束当前的不适**。

- 行测：选一个看起来对的，结束“不确定”。
- 对话：随便答一句，结束“被追问”。
- 独处：切 App，结束“要开始一件难事”。
- 项目：去改工具，结束“要面对真实任务和真实评价”。

这个模型有两个直接推论，和上一版设想相反：

1. **加大压力会加快闭合，也就是加快逃逸。** 所以“严格模式”的问题不是不够严，而是方向错了。
2. **系统不该做动机设计。** 缺的不是动机，是“此刻具体做什么”。

不是因为它“更好”，是因为它已经有的东西无法在短期重写：

- 判卷链路、题库、思维线程、专注流、拦截体检；
- 58 个测试文件、450 个 `@Test`；
- 三万多行已经跑在真机上的代码。

原先以为思维驾驶员有三块独占能力，核实后只剩一块：

1. ~~无障碍被系统关掉后自己开回来~~ —— 总控 0.17.0 的 `SelfHeal` 已有，而且能区分“系统摘掉”和“用户关掉”，重绑要求“新实例 + 真 ack”，比 0.11 版本更完整。
2. ~~无障碍掉线时用“使用情况访问”兜底~~ —— 0.17.0 已有本地规则与有限兜底。

所以思维驾驶员没有必须搬的代码，可以直接停更。

当前真正重复的只有一处：一手还留着自己的无障碍拦截器 `GateService`。几个 App 各开一个无障碍服务互相抢页面，这才是拦不住的原因。删掉一手的拦截，只保留总控。

## 5. 本次交付：四个纯规则模块

位置：`yishou/app/src/main/java/com/yishou/app/core/`；测试在 `app/src/test/java/com/yishou/app/core/`。全部为纯 Kotlin/JVM，不碰 Android。

### 5.1 `Stall.kt` — 没接话时怎么接

- 区分 6 种：正常回答 / 沉默 / 敷衍 / 没看懂 / 卡住了 / 太累 / 不想做。
- 四个按钮直接映射；**点了不罚**：太累和不想做立即收手。
- 同一问题最多追 3 次；沉默超过 30 分钟直接要一个回来的时间。
- 有测试保证所有回复里不出现“懒 / 借口 / 拖延 / 必须 / 应该 / 又 / 罚 / 欠”。

### 5.2 `NextAction.kt` — 下一步动作

必须同时有三样：开始时刻、第一个物理动作、时长。

| 写法 | 结果 |
|---|---|
| `复习行测` | 退回：太大 |
| `认真学习` | 退回：太空 |
| `有空的时候背 20 个单词` | 退回：没有开始时刻 |
| `吃完饭坐到桌前，打开粉笔做言语第 3 套前 5 题，15 分钟` | 通过，识别为 15 分钟、触发器“吃完饭” |

“有空 / 晚点 / 改天 / 抽空 / 看情况”被单独点名，不允许蒙混过关。

### 5.3 `FinalReview.kt` — 落笔前终审

- 证据必须能在原文里按去标点后比对找到，不能用自己的话；
- “它错在哪”先去掉口头禅（我觉得 / 反正 / 就是 / 嗯 / 吧……）再数字数；
- 必须指向最犹豫的那个选项（B / 第二项都认）；
- 长句子挑不出可引用片段时，取最后一个短句；还长就取最后 12 个字。

### 5.4 `Weekly.kt` — 周报

### 5.6 伴读（全部在一手内）

一句话：在关注的应用里待够时间，就截一屏，逼一个判断；不答有后果。

链路：

1. **触发**：一手自己的无障碍服务每秒看一次前台包名；同一个关注应用连续待够 N 秒（默认 45）。
2. **截屏**：`AccessibilityService.takeScreenshot()`，不弹 MediaProjection 授权；缩到 720p、JPEG 55，只在内存里。
3. **识屏**：一手的识图模型（`scrollLook`）把屏幕转成文字；黑屏或少于 10 字不发问。
4. **出题**：`scrollJudge` + `JudgementRules.SYSTEM`，一句、不超 30 字、必须引用屏幕原词；引不出来就用兜底句「原文「…」——你同意吗？因为什么？」。
5. **判卷**：`JudgementRules` 只认“判断 + 理由/反例”，不合格的回答不发给模型；第一次退回可重答，第二次记一次没做到。
6. **交付**：`CoachFloat` 浮窗；点“回答”进 `FloatingReplyActivity` 的 `companion` 模式。
7. **不答**：N 秒提醒（默认 90），M 秒收回桌面并记一次没做到（默认 150）。

上限（全部可在“设置 → 伴读”里调）：

| 参数 | 默认 |
|---|---|
| 连续用多久开始 | 45 秒 |
| 两次之间至少 | 180 秒 |
| 30 分钟最多 | 6 次 |
| 不答多久提醒 | 90 秒 |
| 不答多久收回 | 150 秒 |
| 一天几次没答就停 | 3 次 |

边界：

- 没配识图或模型时**完全不启动**，不会空转截屏。
- 伴读开着时，一手**不再拦截**，拦截交给总控，避免两个无障碍服务抢页面。
- DRM 视频（Netflix 这类）截出来是黑屏；黑屏不发问。

模拟器实测（API 34）：YouTube 前台 10 秒触发，日志 `截屏成功：1080x2400`；未配模型时停在 `识屏失败：NotConfigured`，且不会重复截屏。

### 5.7 伴读的三个优化（本轮）

1. **上下文注入**：出题前读当前任务、目标、断点里的卡点/上次问题、上一轮回答、最近 3 条判断。有卡点就先问卡点，屏幕只当素材；不再泛泛地问“这讲了什么”。（`CompanionContext.kt`，5 个测试）
2. **问题去重**：字符二元组 Jaccard，相似度 ≥0.72 视为重复。重复时换兜底句；兜底句仍重复就跳过这一拍，不硬发。最近保留 20 条。（`QuestionLedger.kt`，7 个测试）
3. **判断写回记忆**：通过 → 写一条 `EchoKind.CONCLUSION`（scene=companion）；两次没答 → 写一条 `EchoKind.DELTA`（带题目）。下一轮出题会把这 3 条读进上下文，形成“越问越知道你卡在哪”的闭环。

这三条都只作用在伴读这一条链路上，不改原有答题/判卷逻辑；关掉伴读即完全失效。

### 5.8 无 AI 也能跑的最小闭环（本轮）

没有配置识图/模型时，伴读不再静默退出，而是走本地提醒：

- 读当前任务、断点卡点、在关注应用里的连续时长；
- 生成一句话：有卡点先问卡点，否则问任务，最后才泛泛问“休息还是回去”；
- 回答标准放宽为“做一个选择”（休息 / 现在回去 / 定个时间，或一句解释），仍然拒绝“嗯/随便”；
- 通过后写 `EchoKind.CONCLUSION`，两次没答写 `EchoKind.DELTA`，下一轮会读回来。

交互上修了三个真机上会踩的坑：

1. **浮窗自动展开**：原来只显示一个“一手 ●”小气泡，问题文字是折叠的，用户不会点。现在新内容出现时自动展开一次，手动收起后不再强行弹回。
2. **浮窗内直接回复**：Android 10+ 不允许后台 App 直接 `startActivity`，从悬浮窗打开回复页会被系统静默拦掉。现在“回答”会把同一浮窗切换成输入框（聚焦、可弹键盘），不启动 Activity。
3. **回复中不提醒**：30 秒的“还剩 N 秒”提醒会把正在输入的框顶掉；现在 `replyOpen` 期间跳过提醒和自动收回。

实测（API 34）：YouTube 前台 10 秒触发，日志 `本地提醒：你在YouTube 待了 1 分钟…`；浮窗自动展开并显示问题与“回答/不想答”；点“回答”切换到输入框。

**已确认的缺口**：模拟器上无障碍服务会被系统清空（`Enabled services:{}`），伴读随之静默停止。只开一手时没有任何组件会把它重新挂上。这是下一轮必须补的自检与恢复。

### 5.9 伴读完整页与浮窗视觉（本轮）

新增 `ui/CompanionScreen.kt`，从“主控台 → 伴读”进入，一屏完成：

- **顶部**：开关、无障碍/模型两个状态点、近 30 分钟问了几次、今天没答几次、上次开口时间；
- **现在**：有待答问题时直接显示问题、输入框、交这一句 / 不想答；没有时说明下一次会带任务或卡点；
- **它看到的**：当前任务、卡点、上次留下的问题、关注应用数与模型模式；
- **节奏**：轻盈 / 标准 / 紧一点三档预设，外加六项时间全部可调；
- **它记得你**：最近 4 条 companion 场景的 `Echo`（结论/差值）。

浮窗同步重做：20dp 圆角深色卡片、金色细描边；操作按钮改成自绘胶囊（主操作金色、次操作深灰描边）；输入框深底圆角；标题加粗。收起时仍是一个“一手 ●”小气泡，新内容出现自动展开一次。

实测（API 34）：从主控台进入页面正常渲染；无障碍未开时顶部红点如实显示，本地模式用金色点区分。

### 5.10 第一阶段闭环验收（2026-11-06）

实测通过的链路（无 AI、仅一手）：

| 项 | 结果 |
|---|---|
| 无 AI 触发 | YouTube 前台 10 秒，日志 `本地提醒：你在YouTube 待了 1 分钟…` |
| 浮窗自动展开 | 卡片显示问题、金色“回答”、深色“不想答”、倒计时 |
| 浮窗内输入 | 点“回答”切到输入框（休息 / 现在回去 / 定个时间），不启动 Activity |
| 提交判定 | 输入 `xianzai` → 日志 `判断通过：xianzai` |
| Echo 落盘 | `echo` 表 `kind=conclusion, scene=companion, text=xianzai` |
| 进程重启 | force-stop 后重启，Echo 仍在 |
| 下一轮召回 | 日志 `上次你说「xianzai」。现在又在YouTube 待了 1 分钟…` |
| 双服务共存 | 总控 + 一手同时启用时两个服务都绑定 |
| 失能提醒 | 清空无障碍后通知“伴读看不到你在用什么”，点开直达设置 |

本轮修掉的真实断链：

1. `readContext` 在没有当前任务时直接返回空上下文，导致已存的 Echo 不被读取、召回失效。现在任务可空，记忆照读。
2. 本地模式把“问题 → 回答”整段写进 Echo，下一轮引用到的是问题。现在只存回答。
3. 重复提交会写两次记忆；现在 pending 已空直接返回，不再写。
4. 取消输入后 `replyOpen` 没复位，会导致之后不再提醒；`showQuestion` 统一复位。
5. 服务断开后没有任何提示；新增 `CompanionHealth` 通知 + 设置入口，只有在调试授权 `WRITE_SECURE_SETTINGS` 存在时才尝试追加自身。
6. 总控 `SelfHeal` 放回时用的是 1–2 秒前的旧列表，且第二档会清空整表；现在放回前重读并合并，有其他服务时不再清表。

已知未解决：

- 一手服务重新连上时，如果用户已经停在一个应用里，要等下一次窗口切换才会开始计时（没有补读当前前台应用）。
- 总控的自动重绑受“用户主动关闭不覆盖”这道门限制；在模拟器上从设置里移除总控会被判为用户行为，不会自动加回。保留这个判断，合并逻辑本身由 6 个单测覆盖。
- 模拟器反复把无障碍服务列表清空，是本轮测试最大的环境干扰。

## 6. 指标与判据

### 6.1 四个指标

1. **结算率**：上次承诺的事，下次接触时已完成的比例。
2. **启动延迟**：从提示出现到第一个物理动作的时间。
3. **核验率**：作答前是否说出“排除了什么 + 依据 + 什么会让我改主意”。
4. **裸考**：每月一次，不开一手，限时做一套。

前三个是过程指标，第四个是唯一能回答“是否只在软件里有效”的指标。

### 6.2 两周判据（事先写死）

- 结算率没有明显高于基线 → 换机制，不加功能。
- 结算率上去了但现实产物没变 → 系统在制造“感觉在推进”，立刻降温。
- 只有状态好时才有效 → 它是顺风车，不是系统。

### 6.3 第四周移除测试

停用一周，看结算率掉多少。

- 大幅回落 → 它是拐杖。拐杖可以是正确答案，但要知道自己在用拐杖。
- 基本维持 → 有真实行为改变，继续投入。

## 7. 明确不做

| 不做 | 理由 |
|---|---|
| 认知训练 / 脑力游戏 / 工作记忆训练 | 远迁移在主动对照下接近零 |
| 反应抑制训练 | 效应小、实验室化，现实迁移证据不足 |
| 以限时答题为主干 | 时间压力会诱发过早闭合，可能在强化病灶 |
| 连续打卡 / 排名 | 断裂 streak 会降低后续参与，对你尤其危险 |
| 进度仪表盘 | 看仪表盘是最舒服的逃避 |
| 禁止卸载 | 越难退出，越容易把精力花在研究怎么退出上 |
| 第二个拦截器 | 已经证明会互相抢页面 |
| 长篇输出 / 说教 / 重复提醒 | 现有数据已否掉 |

## 8. 需要本人拍板的三件事

1. **合并方向**：建议同意，先做“止血”任务卡（只留一手拦截 + 搬自愈/哨兵）。
2. **禁止卸载**：建议先不开。
3. **每周做系统的时间上限**：建议要。每周 6 小时上限；专注时段默认拦住开发工具（IDE、终端、GitHub 网页）。这一条只有你本人同意才有意义。

## 9. 风险（写在最前面，避免自欺）

1. **做这套系统本身已经是最顺手的逃避通道。** 仓库里 17 个项目、上百个分支，“拦截 App 再出题”做了三遍。所以先冻结功能，验证机制。
2. **body doubling 证据很弱**，而且他人在场会损害复杂任务。同桌可以帮你“开始写”，不要用它陪你“想得深”。
3. **一个真人学习伙伴 + if-then 计划，效果可能超过整套软件。** 如果真是这样，软件的正确目标不是替代那个人，而是让那个人不必一直在场。
4. **n=1，没有统计显著性。** 只看结算率、启动延迟、核验率和裸考这四个能数出来的东西，不看自评。
